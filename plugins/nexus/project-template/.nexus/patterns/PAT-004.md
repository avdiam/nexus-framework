# PAT-004: LLM Behavioral Programming
*Version: 5.0.3 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: Practice
- **Composite**: No
- **Domain**: Prompt Engineering / LLM Programming
- **Created**: 2025-09-25 (Session 008)
- **Major revision**: Sprint 048 — selective revalidation after 60+ file rewrites

## Problem

LLM instruction files ("system files") often suffer from behavioral drift, token waste, and inconsistent execution. Common failure modes:

- Verbose prose that buries actionable guidance under meta-explanation
- Vague language ("consider...", "should...") that invites improvisation instead of compliance
- Redundant rules restated across multiple files, creating confusion about which is authoritative
- Missing error recovery, leaving the LLM to improvise when things break
- Assumed context from previous conversations that a fresh instance cannot access

## Context

- **Use When**: Creating or refactoring system files, operation workflows, agent behavioral specifications
- **Not When**: Human documentation, API specs, data schemas, non-LLM systems
- **Key Insight**: LLM instruction files are behavioral programs for an intelligent agent — not code for a deterministic interpreter, and not documentation for human readers. The executor understands context, exercises semantic judgment, and collaborates with the user.

## Solution

### Core Philosophy

Every instruction either triggers correct behavior or wastes tokens. But "correct behavior" for an LLM means *guided reasoning*, not scripted execution. The LLM can figure out mechanics — tell it *what* to achieve, *why* it matters, and *what to watch for*.

**Clarity over compression.** The goal is not smaller files but clearer files. A fresh instance starts from zero every conversation — files ARE its memory. Remove noise (meta-explanations, emotional vocabulary, identity claims), redundancy (same rule stated in 4 places), and poor formatting (verbose YAML wrapping simple rules). Preserve structure, methodology wisdom, format specifications, and field-level guidance that prevents drift.

**Litmus test for every change:** "Will a fresh instance follow this more clearly, or did I just remove something it needs?"

## The 10 Principles

### STRUCTURAL (How to organize)

#### 1. Section Tags for Partial Loading
Section markers (`[Section: Name]` / `[/Section: Name]`) enable loading only what's needed — 70-90% token savings on large files. Every major section needs paired tags.

#### 2. Format Matches Content
Choose the format that fits. Mismatched format is the single biggest source of bloat.

| Content Type | Best Format | Why |
|---|---|---|
| Behavioral rules, principles, philosophy | Prose | Captures reasoning for edge cases |
| Sequential procedures | Numbered steps | Creates order, prevents skipping |
| Conditional logic, multiple paths | Decision table | All paths visible at once |
| Parallel items with same fields | Table | Dense, scannable |
| Field mappings, registry patches | YAML | Structure IS the information |
| Display output for user | Code block template | Exact layout control |

**Anti-pattern**: YAML wrapping simple "do A then B" sequences. Prose for conditional branching. Nested YAML for rules that fit in one sentence.

**Nesting depth**: Keep hierarchical structures to 2-3 levels maximum. Flat lists obscure relationships; deep nesting (4+ levels) buries content and increases LLM parsing errors.

#### 3. Procedural Chains (Numbered Steps)
Sequential processing with numbered steps prevents skipping. Each step has a single responsibility — if it does two things, split it. User approval gates deserve their own steps. Limit: 7±2 steps per procedure.

Clean renumbering on delivery: no orphaned sub-steps (4.a1, 4.a2), no gaps from removed steps. Final output reads as written fresh.

### GUIDANCE (How to instruct)

#### 4. Guide Reasoning, Don't Script Execution
The LLM is an intelligent agent. Describe *what* to achieve and *what matters*, not every micro-step. It can figure out how to patch a YAML field — tell it which field and why.

```markdown
# Over-scripted (treats LLM as code interpreter)
1. Open file X
2. Find line containing "score:"
3. Replace the number after "score:" with the new value
4. Save the file

# Guided (treats LLM as intelligent agent)
Patch the score field in registry. Use prefixed format (ISS-XXX.score) 
for unique matching.
```

**When to be specific**: Field names, file paths, display formats, registry schemas — anything where drift across conversations would cause errors. **When to guide**: Decision-making, assessment, judgment calls, user interaction.

Quick diagnostic: read the instruction aloud. If it sounds like explaining to a colleague, it's behavioral guidance. If it sounds like pseudocode, rewrite it.

**LLM strengths to leverage, not bypass:**

| Leverage (good) | Bypass (anti-pattern) |
|---|---|
| Semantic matching — LLM judges relevance by meaning | Keyword algorithms — regex/string matching for conceptual tasks |
| Flexible input — accept natural language intent | Rigid parsing — formal parameter syntax, structured contracts |
| Context awareness — use what's already in memory | Redundant requests — re-loading or re-asking for known information |

#### 5. Imperatives Over Suggestions
Commands trigger execution. Suggestions invite deliberation and drift.

```markdown
# Weak: "You should check memory first"
# Strong: "Check memory before every read operation."
# Weak: "Consider validating the input"  
# Strong: "Validate scores are 1-5 before patching."
```

Use clear imperatives: check, verify, load, patch, display, wait, skip. Reserve MUST/NEVER/ALWAYS for genuinely critical rules — overuse dilutes them.

#### 6. Single Source, Then Reference
Every rule lives in one authoritative location. Other files reference it, never restate it.

```markdown
# Anti-pattern: Same rule in 4 places (confusing, not reinforcing)
NEXUS-CORE: "Check memory before reads"
Analyze.md: "Always check memory before loading"  
Build.md: "Memory-first: verify cache before MCP calls"
Validate.md: "Before reading, check your memory mantra"

# Correct: Define once, reference elsewhere
NEXUS-CORE: [Section: Memory-Context-Management] — full rule
Analyze.md: "Load context per memory-first protocol"
Build.md: "Load context per memory-first protocol"
```

Exception: a brief anchor (2-3 lines maximum) is acceptable for genuinely non-obvious principles that no single step captures — things the LLM wouldn't infer from the procedure alone. But anchors that restate what numbered steps already say are pure duplication.

Previous guidance (PAT-004 v4.0.0 Principle 14) recommended "strategic repetition" — restating rules 3-4 times for reinforcement. Sprint 048 found this is a primary cause of complexity and confusion. A fresh instance seeing the same rule worded differently in 4 places doesn't know which is authoritative. Single source with clean references is both clearer and more token-efficient.

### EFFICIENCY (How to compress)

#### 7. Tables Over Prose for Parallel Data
When multiple items share the same fields, tables are 40-60% more token-efficient and far more scannable.

```markdown
# Prose (50 tokens)
When you encounter a yellow zone at 70%, you should recommend 
saving. When you hit red zone at 85%, you must auto-save immediately.

# Table (25 tokens)
| Zone | Threshold | Action |
|------|-----------|--------|
| Yellow | 70% | Recommend save |
| Red | 85% | Auto-save (mandatory) |
```

**Common conversions — when refactoring existing files:**

| When you see | Convert to |
|---|---|
| Nested YAML with parallel items sharing same fields | Table |
| `step_1:` / `step_2:` in YAML | Numbered markdown steps |
| `if_X:` / `if_Y:` / `if_Z:` branches | Decision table |
| Multi-line YAML wrapping a one-sentence rule | One prose sentence |
| `error_handling:` as a separate distant section | Inline at point of failure |

#### 8. Preserve What Prevents Drift
Compress explanations, but never compress structures that a fresh instance needs to produce correct output.

**Always preserve (100%)**:
- Schemas and field specifications (JSON/YAML structures)
- Exact formulas and calculations
- Display templates (user-facing formats)
- Full file paths (never abbreviate)
- Section tags (enable partial loading)

**Safe to compress**:
- Meta-explanations ("This section explains...") → DELETE
- Redundant examples (keep 1-2, not 5)
- Verbose prose restating what a table shows → TABLE
- YAML wrapping one-sentence rules → PROSE

### SAFETY (How to protect)

#### 9. Explicit References, Never Assumed Context
Every conversation starts from zero. Never assume the LLM remembers previous sessions.

```markdown
# Broken: "See above for details" / "As we discussed"
# Correct: "Per [Section: Memory-Protocol] step 3"
# Correct: "Formula: effectiveness = 0.50 + ((rate - 0.50) × confidence)"
```

File paths are always full paths from project root. Field names always include the entity prefix (ISS-XXX.score, not just "score").

#### 10. Failure Recovery at Point of Use
Define what happens when known, common operations fail. Don't try to anticipate every edge case — the LLM can recognize unexpected situations and collaborate with the user. But for operations that commonly fail (file not found, patch mismatch, write failure), inline the recovery next to the operation.

```markdown
Patch registry with createBackup: true.
If patch fails: check whitespace match, retry with more context 
in find string, fallback to patch_between_markers.
```

**Anti-pattern**: Separate "Error Recovery" sections far from the operations they support. By the time the LLM encounters a failure, the recovery guidance is pages away.

## Retired Principles

These were in PAT-004 v4.0.0 and actively removed during Sprint 048 after evidence from 60+ file rewrites:

| Former Principle | Why Retired | What Replaced It |
|---|---|---|
| **Emotional Anchoring** (#4) — "SACRED", "VIOLATION", charged vocabulary | Created noise, not compliance. Overuse diluted all emphasis. Anthropomorphic framing ("breaking yourself") adds no behavioral value. | Clear imperatives with MUST/NEVER reserved for genuinely critical rules (Principle 5) |
| **Identity Integration** (#6) — "YOU ARE X. This file IS your mind." | Identity claims don't improve compliance. Role descriptions with clear responsibilities work better. | Operations-template: "Nature of Operations" section describes role without identity claims |
| **Strategic Repetition** (#14) — Repeat rules 3-4 times across files | Primary cause of cross-file confusion. Fresh instance can't tell which version is authoritative when a rule appears differently in 4 places. | Single source + reference (Principle 6) |
| **Mantras for Automaticity** (#7) — Short rhythmic phrases repeated | Only one mantra proved useful (memory check). The rest were slogans with no behavioral effect. | Retained memory mantra as a specific protocol step, not a general principle |
| **Template Rigidity** (#13) — "NEVER vary borders, spacing, or structure" | Structural consistency matters; pixel-perfect rigidity doesn't. Display templates should define layout, not forbid all variation. | Display templates in operations with "use this format" (not "NEVER vary") |

**Key finding**: Principles 4 and 14 were themselves primary sources of the complexity that Sprint 048 (ISS-092) was created to eliminate. Emotional anchoring added noise vocabulary throughout system files. Strategic repetition caused the same rule to appear in 3-4 places with slight wording differences, making it unclear which was authoritative.

## Application Guidelines

### When Creating New System Files

1. Start with the operation's purpose — what does a fresh instance need to do?
2. Choose format per Principle 2 for each section
3. Write procedures as numbered steps (Principle 3)
4. Guide reasoning for judgment calls, be specific for deterministic outputs (Principle 4)
5. Use imperatives (Principle 5), reference NEXUS-CORE protocols don't restate them (Principle 6)
6. Compress meta-text, preserve schemas and templates (Principle 8)
7. Inline failure recovery for common failure modes (Principle 10)

### When Refactoring Existing Files

1. Identify NEXUS-CORE protocol restatements → replace with references
2. Find YAML wrapping simple rules → convert to prose or tables
3. Find emotional vocabulary (SACRED, VIOLATION as emphasis) → replace with clear imperatives
4. Find same rule in multiple places → consolidate to single source
5. Find identity claims ("you ARE this") → replace with role descriptions
6. Verify: field specs, schemas, display templates preserved
7. **Litmus test per section**: "Will a fresh instance follow this more clearly?"

### Validation Checklist

Before deploying a behavioral programming file:

- [ ] Can I find what to DO in <5 seconds per section?
- [ ] Are all steps numbered sequentially with single responsibility?
- [ ] Would a fresh instance get this right without improvising?
- [ ] Is every format matched to its content type?
- [ ] Does removing any sentence lose actionable guidance? (If yes: keep. If no: remove.)
- [ ] No rules restated from NEXUS-CORE (reference only)?
- [ ] No emotional vocabulary used as enforcement mechanism?
- [ ] Error recovery inline with operations that commonly fail?
- [ ] All schemas, field specs, and display templates preserved?

## Relationships
- **Synergies**: None
- **Enhances**: Any system file creation or refactoring
- **Conflicts**: None
- **Alternatives**: Traditional documentation style (when human readers are primary audience)

## Consequences
- **Benefits**: 40-80% size reduction with improved clarity, consistent execution by fresh instances, single-source enforcement eliminates cross-file confusion
- **Tradeoffs**: Less readable for humans unfamiliar with the format, requires judgment about what to preserve vs compress
- **Risks**: Over-compression removing field specs or schemas that prevent drift; under-compression leaving redundancy that confuses
