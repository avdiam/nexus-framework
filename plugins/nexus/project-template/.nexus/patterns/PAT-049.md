## Problem Statement
Complex systems built on broken foundations inevitably fail, regardless of how sophisticated the upper layers are. The non-obvious part isn't knowing this — it's having the discipline to STOP new development when foundation issues surface mid-work. The natural instinct is to work around problems and keep building; this pattern codifies the counter-instinct: halt, repair, then resume.

## Context
This pattern applies when:
- A foundation issue is discovered that blocks or invalidates in-progress work
- Building intelligence layers on top of base functionality that isn't working correctly
- Tempted to work around a problem rather than fix it (the behavioral signal)
- Cascading failures suggest a base-layer root cause

## Solution
**Always repair foundation issues before building new layers.**

1. **Identify Foundation Issues**:
   - Test base functionality thoroughly
   - Look for missing operations or broken logic
   - Check if existing features actually work

2. **Prioritize Foundation Repairs**:
   - Stop new development immediately
   - Add foundation repair as priority objective
   - Block dependent work until foundation solid

3. **Validate Foundation**:
   - Test repaired foundation thoroughly
   - Ensure all base operations work
   - Verify data accuracy and consistency

4. **Build on Solid Ground**:
   - Only proceed with enhancements after validation
   - Leverage the repaired foundation fully
   - Document the foundation dependencies

## Implementation Example
From Sprint 020:
```yaml
discovered: "Pattern effectiveness tracking broken"
impact: "ISS-044 and ISS-047 would fail without accurate data"
solution: 
  - Created FIX-TRACKING as priority objective
  - Repaired pattern tracking MCP operations
  - Validated with actual pattern updates
  - THEN built ISS-044 extraction pipeline
  - THEN added ISS-047 proactive intelligence
result: "3.5x synergy from solid foundation"
```

## Consequences
### Benefits
- Prevents cascading failures
- Reduces technical debt
- Enables true synergy between layers
- Increases system reliability

### Trade-offs
- Delays new feature delivery
- Requires admitting existing problems
- May reveal more issues than expected

## Relationships
- **Synergies**: None
- **Conflicts**: None

## Anti-Patterns
- **Band-Aid Stacking**: Adding workarounds on top of broken foundation instead of fixing it
- **"We'll Fix It Later"**: Deferring foundation repairs indefinitely while building more layers
- **Feature Creep Over Foundation**: Prioritizing new features over stability and correctness
- **Denial of Foundation Issues**: Attributing problems to upper layers when foundation is broken

## When Not to Use
- Emergency hotfixes where speed critical
- Isolated features with no dependencies
- Temporary prototypes or experiments

## Success Metrics
- No foundation-related bugs in new features
- New capabilities work first time
- Synergy multiplication achieved
- Reduced rework and debugging time

## Validation
- **Success Indicator**: New features work first-time after foundation repair
- **Metrics**: No foundation-related bugs in features built on repaired base
- **Edge Cases**: Emergency hotfixes may require temporary workarounds (document debt)
