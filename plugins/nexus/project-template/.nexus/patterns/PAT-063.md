# PAT-063: Systematic Validation for Complex Systems
*Version: 4.1.0 | Date: 2026-08-21 | Sprint: 110*

## Metadata
- **Type**: Methodology
- **Composite**: No
- **Domain**: Testing / Validation
- **Created**: 2025-09-29

## Problem

Complex systems require testing beyond individual components:
- Component testing misses integration failures
- Ad-hoc testing overlooks critical interaction points
- System-wide changes have unpredictable cascade effects
- User experience depends on complete system coherence

## Context
- **Use When**:
  - Multi-component features or changes
  - System-wide architectural modifications
  - Integration of new capabilities
  - Complex workflow implementations
  - Periodic health check of an operation domain, or after a schema / spec version update (from PAT-082)
- **Not When**:
  - Simple, isolated component changes
  - Single-file modifications with no dependencies
- **Prerequisites**:
  - System with multiple interacting components
  - Clear user journey or workflow to validate

## Solution

Four-phase systematic validation that scales with complexity.

### Implementation

```yaml
# PHASE 1: COMPONENT VALIDATION
component_validation:
  verify: "Each component works in isolation"
  check:
    - Input/output contracts maintained
    - Internal logic correct
    - Error handling appropriate
  scope: "Individual modules/functions/files"

# PHASE 2: INTEGRATION TESTING
integration_validation:
  verify: "Components interact correctly"
  check:
    - Data flows between components
    - Interface contracts honored
    - Cascade effects contained
    - Boundary-crossing map drawn ({Domain}::{op} ──CALLS──> {Other}::{op}); caller provides what callee expects; mode (manual/batch/backend) and every return case handled
    - Consumers of a changed spec / section / field verified, not just the file — search ALL callers for stale references
  scope: "Component boundaries and connections"

# PHASE 3: SYSTEM COHERENCE
system_validation:
  verify: "Complete system works as unified whole"
  check:
    - No conflicting behaviors
    - System maintains consistency
    - Edge cases handled gracefully
    - Shared-artifact CRUD flows: who creates / reads / updates / deletes each state file and registry — consistent format, same schema version
    - Scales and units consistent across files (0-100 vs 0-10, sprint numbers vs dates)
  scope: "Entire system"

# PHASE 4: USER JOURNEY
user_experience_validation:
  verify: "End-to-end workflows succeed"
  check:
    - Complete user scenarios work
    - Interface remains intuitive
    - Error messages guide appropriately
  scope: "Real user workflows"
```

### Complexity Scaling

```yaml
complexity_scaling:
  low_1_2:
    phases: [1, 2]
    depth: "Component + basic integration"
    
  medium_3:
    phases: [1, 2, 3]
    depth: "Add system coherence"
    
  high_4_5:
    phases: [1, 2, 3, 4]
    depth: "Complete end-to-end testing"
```

### Variations
- **Lightweight**: Phases 1-2 for simpler changes
- **Integration-Focused**: Emphasis on Phase 2 for API/interface changes
- **User-Centric**: Heavy emphasis on Phase 4 for UX changes
- **Tiered depth** (from PAT-082): match rigor to component importance rather than applying uniform depth — *critical* (core registries, primary state files): field-by-field against the authoritative schema · *important* (operations, secondary files): structural integrity — sections exist, formats correct, cross-refs valid · *supporting* (templates, guides, archived): existence / not-corrupted audit only
- **Post-modification coherence** (from PAT-082, originally PAT-086): after changing 3+ files in one domain, load them in dependency order (producers first, then consumers, batches of 3-5), trace shared state formats, delegation chains, scale conventions and deprecated references; triage findings IMPORTANT (fix now) vs MINOR (note for later)
- **Domain-coherence checklist** (from PAT-082 — the NEXUS instance of Phases 2-3, applied per operation in a domain): 1 routing-table entry · 1b scale/units · 2 memory-first before loads · 3 update protocol (N-place) · 4 CALL targets exist, formats match · 5 template/structure compliance · 6 information flow WHAT/WHERE/HOW/WHEN · 7 fields/sections match schema; plus 3-5 mental execution traces of realistic scenarios (PAT-067). In NEXUS this checklist is operationalised by `/nexus-subsystem-verification` — invoke the skill rather than re-deriving the list.

## Anti-Patterns

- **Component-Only Testing**: Testing in isolation without integration
  - Misses interaction failures and emergent behaviors
  
- **Skip-To-Integration**: Jumping to system testing without component validation
  - Makes debugging extremely difficult when failures occur
  
- **No User Validation**: Technical testing without user journey verification
  - System works technically but users can't accomplish goals

- **Changed-Files-Only Review** (from PAT-082): verifying only the files that were edited
  - Drift in untouched consumers is what breaks — the stale caller was never in the diff

- **Working ≠ Compatible** (from PAT-082): concluding an operation is fine because it works alone
  - Integration failures live at the boundaries; per-operation success says nothing about the crossing

## Consequences
- **Benefits**: Catches integration issues early, scales appropriately, ensures UX quality
- **Tradeoffs**: More time-intensive than simple testing, requires architecture understanding
- **Risks**: Can become over-comprehensive for simple changes

## Examples

### Success: Sprint 026 Experience DNA System
Applied all 4 phases to complex multi-component feature:
- Phase 1: Individual persona components validated
- Phase 2: Persona interaction with sprint-state verified
- Phase 3: Full system coherence confirmed
- Phase 4: User journey through complete workflow tested
- Result: Caught critical integration issues invisible at component level

### Success: Sprint 045 / 048 domain verification (from PAT-082)
Phases 2-3 run as the domain-coherence checklist across the Issue, Sprint, Project and Pattern operation domains (Sprint 045) and six domain coherence checks (Sprint 048): every run found real issues invisible to per-file review — stale `ready_for_archive` / `switch-mode.md` / `EVOLUTION_LOG` references, missing template fields, registry schema drift (4.0.0 vs 5.0.0), scale mismatches (0-10 vs 0-100), orphan menu options — 22+ findings in Sprint 048 alone.
