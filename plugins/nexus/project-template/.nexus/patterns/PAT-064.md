# PAT-064: Phased Feature Implementation
*Version: 4.0.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: methodology
- **Composite**: false
- **Status**: active
- **Created**: 2025-10-01

## Problem
Complex features face challenges: high context usage, delayed delivery waiting for 100% completion, dependencies blocking progress, and all-or-nothing delivery reducing feedback opportunities.

## Context
- **Use When**: Feature has clear value separation (core vs enhanced), dependencies not immediately available, users need value quickly, context limits approaching, complexity > 3
- **Not When**: Feature is inherently atomic, all parts equally critical, dependencies already available, simple features (complexity ≤ 2)
- **Prerequisites**: Understanding of what delivers core user value

## Solution
Split complex features into phases based on value delivery:

**Phase 1 (Immediate Value - 80%)**
- Core functionality users need most
- Simple implementation without complex dependencies
- Deliverable quickly, provides immediate value
- Enables early user feedback

**Phase 2+ (Enhanced Value - 20%)**
- Complex features requiring dependencies
- Nice-to-have enhancements and optimizations
- Can be deferred without blocking value

### Implementation
```yaml
step_1_analyze_value:
  core_value: "What provides 80% of value? What works standalone?"
  enhanced_value: "What requires dependencies? What adds polish but isn't critical?"

step_2_define_boundaries:
  phase_1: "Immediate user value, no blocking dependencies, testable independently"
  phase_2: "Requires dependencies, enhancement rather than core"

step_3_implement_phase_1:
  - Build core functionality
  - Create stubs for Phase 2 sections
  - Fully integrate and test
  - Mark as complete (not partial)

step_4_defer_phase_2:
  - Create new issue for Phase 2
  - Document dependency requirements
  - Link back to Phase 1 issue
```

## Rationale
- **Theoretical Basis**: Pareto principle - 80% of value from 20% of features
- **Empirical Evidence**: ISS-058 delivered Phase 1 in Sprint 028, Phase 2 deferred to ISS-069
- **Design Decisions**: Value delivery time reduced 60-80%, context usage ~50% less

## Anti-Patterns
- **Artificial Phasing**: Creating phases that don't align with value delivery
  - **Why It's Wrong**: Adds complexity without benefit
  - **Example**: Splitting login and logout into separate phases
- **Phase 1 Too Minimal**: Delivering no real value in Phase 1
  - **Why It's Wrong**: Users wait without benefit
- **Phase 1 Too Complex**: Including dependencies in Phase 1
  - **Why It's Wrong**: Defeats the purpose of phasing

## Relationships
- **Requires**: None
- **Enhances**: PAT-051 (File Modularization)
- **Conflicts**: None
- **Alternatives**: Complete feature delivery (when atomic)

## Consequences
- **Benefits**: Faster value delivery, reduced context usage, early user feedback, manageable scope
- **Tradeoffs**: May need refactoring when Phase 2 arrives, temporary stubs needed
- **Risks**: Phase 2 might be deprioritized if priorities change

## Examples
### Success Example: ISS-058 Documentation Management
- Phase 1: Help Interface, Documentation Browser, Learning Path Generator → 80% value delivered
- Phase 2 (deferred to ISS-069): Staleness Checker, Guide Creator → Complex features without blocking
