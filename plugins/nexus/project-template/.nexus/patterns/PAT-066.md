# PAT-066: User Navigation Flow Design
*Version: 4.0.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: methodology
- **Composite**: false
- **Status**: active
- **Created**: 2025-10-10

## Problem
Menu interfaces become mis-configured when options are presented without considering user navigation flow and operation dependencies - operations requiring prior selection appear alongside context-setting operations, users encounter invalid states, backend operations appear in user menus.

## Context
- **Use When**: Creating/updating menu interfaces, validating user navigation flows, designing command interfaces
- **Not When**: Simple single-level menus with no dependencies, operations truly independent
- **Prerequisites**: Understanding of operation dependencies and user mental models

## Solution
Mentally simulate the complete user navigation flow before creating or updating menus.

### Mental Simulation Process

For each operation, ask:

1. **Context Requirements**: What selection/information does this need? Can user execute without prior context?
2. **Context Sources**: Where does user obtain necessary context? Which operations provide it?
3. **User vs Backend**: Is this user-facing or internal? Should users invoke directly?
4. **Natural Sequence**: What's the logical order? Does structure match user's mental model?

### Menu Structure Guidelines

```yaml
top_level_context_setters:
  - "List/search operations that establish context"
  - "Status displays and system information"
  - "Entry points to workflows"

second_level_context_dependent:
  - "Operations requiring selection from level 1"
  - "Detail views, modifications, applications"
  - "Actions on specific items"

not_in_menus_backend:
  - "Operations called only by system components"
  - "Internal delegation chains"
  - "Operations with complex prerequisites"
```

### Implementation
```yaml
step_1: "List all operations, note purpose and requirements"
step_2: "Classify: context-setters vs context-dependent vs backend-only"
step_3: "Structure: context-setters at L1, dependent at L2, backend not in menu"
step_4: "Validate: walk through user journeys, check for missing context scenarios"
```

### Key Features (from 6 applications)
- **Single-section consolidation**: All menus in one section marker (60-80% token savings)
- **State-aware adaptation**: Menus adapt based on system state
- **Operation dependency hints**: Document when Op B requires Op A first
- **Natural language emphasis**: Prominently display conversational alternatives

## Rationale
- Users think in goals and sequences, not system capabilities
- Making dependencies explicit in structure prevents invalid states
- Progressive disclosure reduces visual clutter and decision paralysis

## Anti-Patterns
- **System-Centric Design**: Listing all operations without considering flow
  - Wrong: "1. List patterns 2. View details 3. Apply" (2,3 need selection!)
- **Flat Everything**: All operations top-level regardless of dependencies
- **Backend in Frontend**: Exposing internal operations to users

## Relationships
- **Enhances**: None
- **Conflicts**: None

## Consequences
- **Benefits**: Natural mental models, reduced errors, clearer journeys, less cognitive load
- **Tradeoffs**: More upfront design thinking, may need multiple levels
- **Risks**: Over-hierarchical menus can frustrate (balance needed)

## Examples
### Success: Menu System Redesign (Sprint 029)
- Pattern Menu: 13→6 ops, selection flow → view → actions
- Issue Menu: 11→6 ops, backend removed, clearer workflow  
- Sleep Menu: 11→3 ops, dependency documentation added
- **Overall**: 58→27 operations (53% reduction), 60-80% token savings
