# PAT-067: Mental Execution Validation
*Version: 5.1.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: methodology
- **Composite**: false
- **Status**: active
- **Created**: 2025-10-15

## Problem
Work artifacts (operations, documentation, designs) appear complete but contain gaps that only surface during actual execution - leading to failed first attempts, user confusion, and late-discovered quality issues.

## Context
- **Use When**: Before marking work complete, before delivering specs/docs, when quality uncertainty exists, when output confidence is high (>85%) — apply adversarial mode
- **Not When**: Quick informal communications, work you'll execute yourself immediately, simple/routine operations with obvious outcomes
- **Prerequisites**: Completed draft of the work artifact

## Solution
Before delivering any substantial work artifact, execute it mentally from the perspective of someone who would use it.

### Mental Execution Protocol
```yaml
step_1_fresh_perspective:
  action: "Clear your context knowledge"
  question: "If I knew nothing about this, could I execute it?"

step_2_walk_through:
  action: "Execute each step mentally"
  note: "Where do you pause? Where do you guess?"

step_3_struggle_test:
  question: "Would I struggle at any point?"
  threshold: "60-70% complete = would struggle"
  if_yes: "Work is incomplete"
  if_no: "Ready for delivery"

step_4_gap_fill:
  action: "Add all missing details"
  verify: "Re-execute mentally until smooth"
```

### Quality Indicators
- Can execute without pausing for missing information
- No ambiguous instructions or undefined terms
- All dependencies and prerequisites specified
- Edge cases and error conditions addressed

### Adversarial Mode (merged from PAT-089)
Apply when confidence is high (>85%) or after generating complex proposals, designs, or recommendations. High confidence correlates with unchecked assumptions — that's when scrutiny matters most.

```yaml
adversarial_protocol:
  step_1_perspective_shift:
    action: "Shift from generator to reviewer"
    treat_as: "Reviewing someone else's work"

  step_2_must_find_mandate:
    rule: "You MUST find at least one issue or concern"
    if_zero_found: "Scrutiny was insufficient — look harder"
    rationale: "Prevents rubber-stamp reviews"

  step_3_surface_tradeoffs:
    question: "What was optimized for? What was sacrificed?"
    question_2: "What could go wrong (10% failure scenario)?"
    action: "Make costs visible to the decision-maker"

  step_4_synthesize:
    action: "Confirm, adjust, or present alternative"
```

### E2E Integration Simulation (merged from PAT-090, Sprint 105)
For ecosystem-wide changes (5+ interconnected files; routing / phase-transition / cross-file workflow changes; or adding a persistent field with multiple writers), extend mental execution from single-artifact to end-to-end:

1. **Construct 3-6 scenarios** traversing distinct paths through the modified files (happy path + key variations + edge + error recovery). Lightweight (3) for 5-7 files; thorough (6) for 8+ or core routing/lifecycle.
2. **Trace state across every boundary** — where one file's output becomes another's input. Check producer output matches consumer expectations, all enum values handled, references resolvable. Integration failures live at file interfaces, invisible to per-file checks.
3. **Enumerate distributed writers** — for any persistent field, list every file that creates/updates/carries it forward; verify each produces correct values for all transitions.
4. **Fix immediately, re-simulate** — each fix can introduce new boundary issues; re-run affected scenarios.

Compositional correctness ≠ component correctness. Evidence: ISS-113 (10 files) caught 3 integration issues per-file checks missed; ISS-094 caught 2 distributed-write gaps invisible to 6 passing tests.

## Rationale
- **Theoretical Basis**: Pre-delivery validation catches gaps before users encounter them
- **Empirical Evidence**: Revision rate dropped from 40-50% to <20% after adoption
- **Key Insight**: Investing 10-15% more time in mental execution saves 40-60% in rework

## Anti-Patterns
- **"Looks good to me"**: Visual review without mental execution
- **"I know what I meant"**: Assuming implicit context is clear
- **"Good enough"**: Accepting 60-70% completeness
- **"They can figure it out"**: Delegating gap-filling to users
- **"Zero-finding acceptance"**: Accepting "no issues found" as valid for complex outputs — it almost never is. Triggers adversarial mode re-check.

2. Update the field

```

**Step 2**: patch_file(..., createBackup: true) - on_failure: rollback
**Step 3**: search to verify - if_not_found: CRITICAL ERROR
```
