## Problem
Plans are created with incomplete information. When early analysis reveals fundamental flaws - better architectures, failed assumptions, simpler solutions - continuing with the inferior plan accumulates waste. But pivoting too easily leads to analysis paralysis.

## Context
- **Use When**: Early analysis (0-20% progress) reveals fundamental design flaws, better architecture, or failed assumptions; when progress is under 20% and a fundamentally simpler approach has been discovered
- **Not When**: Implementation challenges (not design flaws), minor adjustments would fix, past 30% progress
- **Prerequisites**: Clear original plan, evidence-based reasoning, concrete superior alternative

## Solution

### Timing Windows
| Progress | Pivot Cost | Recommendation |
|----------|-----------|----------------|
| 0-20% | Low | Optimal pivot window |
| 20-30% | Medium | Investigate carefully |
| >30% | High | Rarely justified |

### Signal Classification

**Strong Pivot Signals** (design flaws):
- Original approach fundamentally flawed (not just hard)
- Better architecture discovered that contradicts plan
- Core assumptions proven false by investigation
- Simpler solution exists (aligns with the `elegant_minimum` core preference; formerly PAT-009, retired as framework-subsumed)

**Weak Signals** (persist through):
- Implementation harder than expected
- Different approach might be slightly better (marginal)
- First obstacle encountered
- Just requires more thinking/effort

### Decision Matrix
```yaml
pivot_if: "2+ strong signals AND <20% progress"
investigate_if: "1 strong signal OR mixed signals AND <30% progress"  
persist_if: "Only weak signals OR >30% progress"
```

### Execution Protocol
1. **Document original**: Plan and reasoning (preserve learning)
2. **Articulate discovery**: Evidence that invalidates plan
3. **Present alternative**: Why demonstrably superior
4. **Get user buy-in**: Shared decision, not unilateral
5. **Update scope**: Issue file, sprint-state
6. **Commit fully**: No half-measures or second-guessing

## Rationale
- **Cost curve**: Pivoting cost grows exponentially with progress
- **Plans are hypotheses**: Analysis tests them, discovering flaws is success
- **Sunk cost prevention**: 3 conversations analyzing ≠ commitment to bad approach

## Anti-Patterns
- **Premature Pivoting**: Changing after <1 conversation (insufficient analysis)
- **Late Pivoting**: Recognizing need after 50%+ (should have caught earlier)
- **Analysis Paralysis**: Continuous pivoting, never committing
- **Convenience Pivoting**: Pivoting because easier, not better

## Examples

### Application: ISS-076 (Sprint 038)
**Situation**: Early analysis of a planned implementation revealed the architectural approach was fundamentally incompatible with an existing system constraint.
**Signals**: Core assumption proven false (strong signal 1), better architecture discovered (strong signal 2). Progress: ~15% (within optimal window).
**Decision**: pivot_if triggered — 2 strong signals + <20% progress.
**Execution**: Documented original plan + reasoning, articulated the constraint conflict, presented alternative architecture, got user buy-in, updated issue scope.
**Outcome**: Avoided ~5 conversations of work on an unviable path. New approach succeeded on first implementation attempt.

## Consequences
- **Benefits**: Avoid technical debt, save 5-20 conversations, discover better solutions
- **Tradeoffs**: Requires 1-3 conversations analysis investment
- **Risks**: Analysis paralysis if threshold too low
