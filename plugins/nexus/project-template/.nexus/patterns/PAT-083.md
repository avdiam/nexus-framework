# PAT-083: Structured Persistence Ownership
*Version: 1.0.0 | Date: 2026-02-08 | Sprint: 045*

## Metadata
- **Type**: principle
- **Composite**: false
- **Status**: active
- **Created**: 2026-02-08

## Problem
When multiple components produce data and multiple save points exist, unclear ownership of "who writes what when" causes either lost work (gaps) or redundant saves (duplication). Components may assume another will persist their output, or multiple components write the same state inconsistently.

## Context
- **Use When**:
  - Systems with multiple components producing state that must be preserved
  - Checkpoint/save workflows touching shared state files
  - When "who saves what" is ambiguous or causing bugs
  - When debugging reveals lost work or inconsistent state
- **Not When**:
  - Single-component systems with one obvious writer
  - Trivial state with no persistence requirements
  - Ephemeral data that doesn't need saving
- **Prerequisites**: Identifiable components that produce and consume shared state

## Solution
Assign explicit persistence responsibility per component. Separate concerns into two roles:

### Decision Framework for New Components
When adding a new component that produces or consumes shared state:

1. **Map producers** — which components generate data that must persist?
2. **Assign roles** — for each piece of state, designate exactly ONE persister. Two questions:
   - Does an existing persister already own the target file? → Producer PREPARES, existing persister WRITES.
   - No existing persister? → Component owns its own persistence (self-persister).
3. **Choose granularity** — full writes for initial saves, incremental patches for subsequent updates
4. **Document the boundary** — each component knows: "I prepare, X writes" or "I own this file"
5. **Verify at handoff** — when producer hands to persister, validate content completeness before write

**Key decision rule**: If multiple components could write the same file, centralize to ONE persister. If a component is the sole writer of a file, it self-persists.

### Example: NEXUS Persistence Map

| Producer | Data | Persister | Target File |
|----------|------|-----------|-------------|
| Analyze/Build/Validate.md | Phase scores, decisions, experience | Checkpoint Protocol | sprint-state.md |

Key insight: Methodology files (Analyze/Build/Validate) never write sprint-state directly — Checkpoint Protocol owns that file's persistence. This prevents both gaps and duplication.

## Rationale
- **Theoretical Basis**: Separation of concerns applied to state management. Just as read/write separation improves data systems, separating preparation from persistence prevents ownership ambiguity.
- **Empirical Evidence**: Validated in ISS-091 — Checkpoint.md extraction resolved confusion about whether methodology files or checkpoint workflow owned sprint-state writes. Clear assignment eliminated both gaps and duplication.
- **Design Decisions**: Chose "producers prepare, persisters write" over "everyone writes their own state" because centralized persistence provides consistent save format and atomic transactions.

## Anti-Patterns
- **Anti-Pattern 1**: Assumed Persistence — "Someone else will save it"
  - **Why Wrong**: Leads to lost work when no component actually writes
  - **Example**: Capability file generates analysis but assumes checkpoint will capture it — checkpoint doesn't know about it
- **Anti-Pattern 2**: Everyone Writes — Multiple components writing same state file
  - **Why Wrong**: Race conditions, inconsistent format, partial overwrites
  - **Example**: Both evaluation and checkpoint writing sprint-state scores independently

## Consequences
- **Benefits**: No lost work, no duplicate saves, debuggable persistence flow, clear component boundaries
- **Tradeoffs**: Requires upfront ownership mapping; adds coordination between producer and persister
- **Risks**: Over-centralization — if the single persister fails, nothing gets saved. Mitigate with backup mechanisms.

## Examples

### Before/After Comparison
**Without Pattern**: Methodology file (Validate.md) generates evaluation results. Checkpoint.md also tries to capture evaluation state. Neither knows the other exists — sometimes both write (conflict), sometimes neither writes (data loss).
**With Pattern**: Validate.md PREPARES evaluation results in memory. Checkpoint.md OWNS the write to sprint-state.md. Clear boundary — no conflict, no gaps.

### Application Example
NEXUS Checkpoint.md extraction (Sprint 045): Separated "capabilities assess and prepare" from "checkpoint persists." Checkpoint.md became the single owner of sprint-state writes, while methodology files (Analyze/Build/Validate) prepare content but never write state directly.
