# PAT-084: Spec-as-Authority
*Version: 1.0.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: principle
- **Composite**: false
- **Status**: active
- **Created**: 2026-02-08

## Problem
Specifications drift from implementations over time. Drafts linger alongside finished specs creating ambiguity about which is authoritative. When conflicts arise, the natural tendency is to update specs to match reality rather than fixing implementations — eroding the spec's authority until it becomes unreliable documentation rather than a governing contract.

## Context
- **Use When**:
  - Any system with specification/implementation pairs (APIs, schemas, templates, operation definitions)
  - When discovering drift between "how it should work" and "how it does work"
  - After major changes that may have introduced spec violations
  - When drafts and finished specs coexist ambiguously
- **Not When**:
  - Rapid prototyping where spec doesn't exist yet
  - Exploratory work where implementation IS the spec
  - When spec is genuinely wrong (update spec FIRST, then realign)
- **Prerequisites**: At least one authoritative specification that implementations should conform to

## Solution
Establish unidirectional authority: specs govern implementations, never the reverse.

### Implementation
1. **Designate authority explicitly** — for each spec/implementation pair, declare which is the source of truth
2. **Graduate drafts** — drafts explicitly become specs and originals are removed. Never keep both alongside each other.
3. **Fix implementations, not specs** — when conflict is found, update the implementation to match the spec. Only update the spec if the spec itself is genuinely wrong (not just out of sync).
4. **Spec-first updates** — when changing behavior, update the spec FIRST, then realign implementations. Never change implementation and "plan to update spec later."
5. **Periodic realignment** — as a maintenance activity, verify implementations still conform to their governing specs. Caller verification catches drift that self-inspection misses.

## Rationale
- **Theoretical Basis**: Authority must flow one direction to prevent systemic drift. In any system with multiple representations of truth, ambiguity about which is canonical leads to progressive divergence. This is the single-source-of-truth principle applied to the spec/implementation relationship specifically.
- **Empirical Evidence**: Validated in ISS-091 Stages 5-7 — template/spec alignment work discovered widespread drift in operations, registries, and state files. Realigning implementations to specs (not the reverse) restored system consistency. Caller verification (Stage 6) caught 60+ issues that spec inspection alone missed.
- **Design Decisions**: Chose "fix implementation" over "update spec to match" because specs represent intentional design decisions. Weakening specs to match accidental drift normalizes degradation.

## Anti-Patterns
- **Anti-Pattern 1**: Reality-Wins — Updating spec to match implementation drift
  - **Why Wrong**: Normalizes degradation. Each "reality wins" decision weakens the spec's authority until it's merely descriptive.
  - **Example**: Template says field X is required, but 3 operations skip it. Removing X from template instead of fixing operations.
- **Anti-Pattern 2**: Parallel Drafts — Keeping draft alongside finished spec
  - **Why Wrong**: Creates ambiguity about which is authoritative. Consumers may follow either version.
  - **Example**: discuss.md proposals file kept alongside ISS files that already contain the finalized decisions.

## Consequences
- **Benefits**: Consistent system behavior, reliable specs, clear authority, drift caught early
- **Tradeoffs**: Requires discipline to update spec first; resisting "just fix it quick" in implementation
- **Risks**: Stale specs that never get updated become blockers. Mitigate with periodic realignment cycles.

## Examples

### Before/After Comparison
**Without Pattern**: Operation files implement their own field handling. Template says 18 fields required. Over 5 sprints, 3 operations drift to 15 fields. Nobody notices because "it works." New operations copy from drifted ones, propagating the error.
**With Pattern**: Periodic spec-alignment pass compares operations to template. 3 operations found non-conformant. Fixed to match template (not template weakened to match them). New operations reference authoritative template.

### Application Example
ISS-091 Stage 5-7 (Sprint 045): Templates (specs) were compared against live state files and operations (implementations). Where drift was found, implementations were fixed to match templates. When templates themselves were wrong (e.g., stale version numbers), templates were corrected FIRST, then implementations realigned. 60+ fixes across 19 files.
