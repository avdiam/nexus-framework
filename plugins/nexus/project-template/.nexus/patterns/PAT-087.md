# PAT-087: Reframe Before Design
*Version: 1.0.0 | Date: 2026-02-19 | Sprint: 050*

## Metadata
- **Type**: principle
- **Composite**: false
- **Status**: active
- **Created**: 2026-02-19

## Problem
Designers anchor to the initial framing of a problem, constraining the solution space before exploration begins. The first description becomes a cognitive anchor that shapes all subsequent design thinking, often leading to incremental improvements rather than fundamentally better solutions.

## Context
- **Use When**: Starting design work on new components, methodologies, or significant features. When the problem description feels like it already implies a solution. When early designs feel constrained or incremental. When a request uses language like "create a simpler version of X" or "trim X down" (implies solution structure). When multiple stakeholders frame the same need differently (competing frames reveal hidden assumptions).
- **Not When**: Framing is well-established and validated by prior analysis. Incremental changes to existing, proven designs. Time-critical fixes where reframing would delay action.
- **Prerequisites**: First Principles thinking capability (MM-001). Willingness to challenge the initial problem statement.

## Solution
Before designing, apply First Principles to reframe the problem. Ask "What is this REALLY about?" — strip inherited framing, identify the core need, and name the reframed problem explicitly. Naming forces clarity and prevents drift back to the original frame.

### Implementation
1. **Receive the problem statement** — note the implicit framing and any solution hints embedded in the description
2. **Apply First Principles** — break down to fundamentals: What is the actual need? What constraints are real vs assumed? What would we build if we had no prior context?
3. **Name the reframe** — articulate the reframed problem in a single sentence. Compare it to the original. If they differ meaningfully, the reframe has revealed hidden assumptions.
4. **Design from the reframe** — use the reframed problem as the design anchor, not the original description

### Variations
- **Lightweight reframe**: For medium-complexity work, a single "What is this REALLY about?" question before designing may suffice
- **Full reframe**: For high-complexity or novel work, dedicate a step to systematic First Principles decomposition before any design thinking

## Rationale
- **Theoretical Basis**: Anchoring bias operates at the framing level, not just the solution level. The way a problem is described constrains which solutions feel natural. Reframing breaks the anchor.
- **Empirical Evidence**: ISS-112 demonstrated this directly — "trimmed Build.md" framing led toward a subset of Build's features, while "batch execution controller" reframing led to a fundamentally different and better design (5 steps vs 11, 69% size reduction, distinct lifecycle identity).
- **Design Decisions**: Paired with First Principles (MM-001) rather than creating a standalone technique, because the decomposition skill already exists — this pattern is about WHEN to apply it (before design) and WHY (to counter framing bias).

## Anti-Patterns
- **Design-from-description**: Starting design work directly from the initial problem statement without questioning its frame
  - **Why Wrong**: Inherits the requester's implicit assumptions and solution hints, constraining the solution space
  - **Example**: "Create a trimmed version of Build.md" → designs a subset of Build features instead of rethinking the need
- **Reframe-everything**: Applying deep reframing to trivial or well-understood problems
  - **Why Wrong**: Wastes time when the framing is already correct; not every problem needs First Principles decomposition

## Consequences
- **Benefits**: Reveals fundamentally better solution directions. Prevents incremental thinking on novel problems. Forces explicit articulation of what's actually needed.
- **Tradeoffs**: Adds a step before design begins. May feel unnecessary when framing happens to be correct.
- **Risks**: Over-application to simple problems wastes time. Reframing without domain understanding can miss important constraints.

## Examples

### Before/After Comparison
**Without Pattern**: "We need a lighter version of Build.md for repetitive tasks" → designs by removing Build features → ends up with an awkward subset that doesn't quite fit
**With Pattern**: "What is this REALLY about?" → "A batch execution controller that references a playbook" → designs a distinct 5-step methodology with its own identity and lifecycle position
