# PAT-093: Entry Ramp Architecture

## Problem
Complex systems accumulate deep reference documentation that serves experienced users well but overwhelms newcomers. The typical response — writing a single "getting started" guide or duplicating content in simplified form — either creates a wall of text or an unsustainable parallel documentation set that drifts from the source material.

## Context
- **Use When**: System has extensive existing documentation but poor newcomer onboarding; users abandon before reaching first value; documentation organized by system architecture rather than user need; multiple user types need different entry points; creating documentation for any project with existing reference material (software, research, process, creative); building a documentation gateway / index / catalog front door over an existing guide library (the gateway IS the entry ramp — structure it by journey stage, not by system component)
- **Not When**: System is simple enough for a single README; target audience is already expert; documentation doesn't exist yet (write reference docs first); system changes too rapidly for staged guides to stay current
- **Prerequisites**: Existing reference documentation must be substantially complete; user journey stages must be identifiable (typically 3-5 stages from discovery to proficiency)
- **Scope**: Applies to ANY project type managed by NEXUS — not just NEXUS itself. When a project has accumulated reference docs and needs onboarding, this pattern structures the entry experience.

## Solution
Structure onboarding as one document per user journey stage, layered on top of existing deep reference material. Each document serves exactly one stage and links forward to the next stage and backward to the previous one. Entry ramp documents never duplicate reference content — they provide context, motivation, and navigation to reach the right reference at the right time.

### Implementation
1. **Identify journey stages**: Map the path from "never heard of this" to "productive user." Typical stages: Discover (why should I care?) → Install (how do I get it?) → First Use (walk me through it) → Troubleshoot/Grow (what when stuck?)
2. **One document per stage**: Each document has exactly one job. Resist combining stages — if a user is installing, they shouldn't be reading philosophy.
3. **Layer, don't duplicate**: Reference existing guides for depth. Entry ramp provides the "what to read and when" navigation that reference docs lack.
4. **Link bidirectionally**: Each document links forward ("next: First Project Tutorial") and backward ("if you haven't installed yet: Installation Guide"). Users who land in the middle can orient themselves.
5. **Validate per stage**: Test each document independently with the persona who needs it. A newcomer reading the install guide shouldn't need to have read the overview first.

### Variations
- **Multi-audience ramps**: Different entry points for different user types (developer vs. manager vs. operator) that converge at the same reference library
- **Progressive depth**: Each stage document has a "quick path" (minimum to proceed) and "deep dive" (full understanding) sections
- **Domain variations**: Within a single tutorial, show how choices differ by domain (software vs. research vs. operations) using inline variation boxes rather than separate tutorials

## Rationale
- **Theoretical Basis**: Users have a journey, not a question. Reference documentation answers questions but doesn't guide journeys. Entry ramps provide the narrative arc that connects questions in the right order. The architecture mirrors how humans naturally learn — motivation before mechanics, overview before detail, guided experience before independent exploration.
- **Empirical Evidence**: 4-document starter kit (what-is-nexus, installation-guide, first-project-tutorial, troubleshooting-guide) tested with 3-persona struggle tests across all 4 documents. 20 friction points caught and resolved. Key finding: users who hit trouble in the install stage need help immediately (inline troubleshooting), not in a separate document they haven't found yet.
- **Design Decisions**: Inline troubleshooting callouts in stages 2-3 rather than only in stage 4 — users encounter problems where they are, not where the documentation architect organized them. Domain variations inline rather than separate documents — users learn more from seeing how domains diverge at decision points than from reading a catalog of examples.

## Anti-Patterns
- **Anti-Pattern 1**: The monolithic "Getting Started" guide
  - **Why Wrong**: Tries to serve all stages at once, becomes too long, users can't find where they are
  - **Example**: A 50-page document covering philosophy, installation, first project, and troubleshooting in sequence
- **Anti-Pattern 2**: Duplicating reference content in simplified form
  - **Why Wrong**: Creates maintenance burden, drifts from source, confuses users about which version is authoritative
  - **Example**: Rewriting the setup wizard documentation in "simple terms" rather than guiding users through the actual wizard
- **Anti-Pattern 3**: Organizing onboarding by system component
  - **Why Wrong**: Maps to developer mental model, not user journey. Users don't think "I need the sprint module" — they think "I need to start my first project"
  - **Example**: Separate guides for "Projects," "Sprints," "Issues," "Patterns" when the user needs a single walkthrough that touches all of them in order

## Consequences
- **Benefits**: Newcomers reach first value faster; existing documentation preserved and leveraged; each document is independently testable and maintainable; clear ownership (one doc = one stage = one author)
- **Tradeoffs**: Requires existing reference docs to be solid (entry ramp links to them); adds 3-5 documents to maintain; journey stages may shift as system evolves
- **Risks**: Stale links if reference docs restructure; entry ramp becomes a bottleneck if it's the only path to reference docs; over-simplification in early stages may set wrong expectations

## Examples

### Before/After Comparison
**Without Pattern**: 11 reference guides (~240KB) covering all system aspects in depth. New users see a documentation index with titles like "Sprint Management Guide" and "Pattern System Guide." They don't know which to read first, read the wrong one, get confused, and give up.
**With Pattern**: 4 entry ramp documents (Discover → Install → First Project → Troubleshoot) guide newcomers through their natural journey. Each links to the relevant reference guides at the right moment. The 11 reference guides remain unchanged — they now have a front door.

## Notes and Observations
The First Principles analysis that shaped this pattern asked: "What does a newcomer actually need at each point?" The answer was never "comprehensive information" — it was "just enough to take the next step, with confidence that help exists if something goes wrong." The inline troubleshooting callouts (not just in the troubleshooting doc) emerged from struggle testing — real friction happens at the install and tutorial stages.

**Post-meta-project applicability**: This pattern is valuable for any project that accumulates reference documentation (API docs, architecture guides, process manuals). The journey stages adapt to domain: software projects (Discover → Install → Build First Feature → Debug), research projects (Discover → Setup → First Analysis → Iterate), creative projects (Discover → Setup → First Draft → Refine). The principle — one doc per stage, layer don't duplicate — is universal.
