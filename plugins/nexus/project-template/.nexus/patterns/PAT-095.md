# PAT-095: Isolated Context Advantage
*Version: 1.0.0 | Date: 2026-03-23 | Sprint: 065*

## Metadata
- **Type**: methodology
- **Status**: active
- **Created**: 2026-03-23

## Problem

Certain cognitive tasks suffer when performed by an agent with full conversation context. The accumulated history creates biases that impair specific task types:

- **Anchoring bias**: Defending prior decisions because "we already decided"
- **Confirmation bias**: Seeking evidence that supports established direction
- **Creative convergence**: Ideas constrained by what's already been discussed
- **Perspective lock**: Inability to see alternatives after committing to a path
- **Sunk cost attachment**: Reluctance to critique work that took effort to produce

These biases stem from having "too much" context — the very continuity that enables coherent work becomes a liability for tasks requiring fresh perspective.

## Context

- **Use When**:
  - Reviewing work just completed in the same conversation (adversarial review, quality gates)
  - Need for genuinely fresh perspective on established direction
  - Creative exploration that keeps converging on the same ideas
  - Brainstorming where existing discussion is constraining possibilities
  - Devil's advocate or red team exercises
  - Objective assessment where sunk cost bias is a risk
  - Any task where "knowing too much" is the problem

- **Not When**:
  - Task requires deep understanding of conversation context to perform well
  - Continuity of reasoning is essential (multi-step analysis building on itself)
  - Sub-agent would need most of the context anyway (overhead without benefit)
  - Quick check where full isolation is overkill
  - Collaborative refinement where shared context IS the value

- **Prerequisites**: Platform supports isolated sub-agent spawning; task is well-defined enough to specify without full context

## Solution

Recognize when isolation is the feature, not a limitation. Offload specific tasks to isolated sub-agents that receive only curated context — no conversation history, no prior decisions, no established direction.

### When Isolation Helps

| Task Type | Why Isolation Wins |
|-----------|-------------------|
| **Adversarial review** | Reviewer didn't write the code, has no stake in defending it |
| **Brainstorming** | Fresh perspective unconstrained by "we already decided X" |
| **Devil's advocate** | Genuine opposition without self-censoring due to social history |
| **Creative alternatives** | Ideas not anchored to established direction |
| **Objective assessment** | Evaluation without sunk cost bias |
| **Quality gates** | Independent verification without knowledge of shortcuts taken |
| **Fresh eyes critique** | Sees what insiders have gone blind to |

### Context Design Principles

The key skill is deciding what context to pass. This is creative design work, not mechanical extraction.

**1. Include** (what the sub-agent needs):
- Artifacts to evaluate (files, code, designs, proposals)
- Standards to apply (criteria, requirements, constraints)
- Task definition (what exactly to do)
- Output format (how to structure the response)

**2. Exclude** (what would create bias):
- Reasoning that led to the artifacts
- Prior decisions and their rationale
- Discussion history and rejected alternatives
- Emotional context ("we worked hard on this")
- Social dynamics ("the user prefers X")

**3. Scope** (boundaries):
- Narrow enough for focused task completion
- Broad enough for informed judgment
- Include adjacent context only if essential for the task

**4. Framing** (presentation):
- Present artifacts neutrally, not as "our solution"
- State the task without implying expected outcome
- Provide standards as objective criteria, not preferences

### Result Contract

Define how the sub-agent delivers results BEFORE spawning:

```
CONTRACT TEMPLATE:
- Task: {specific task definition}
- Input: {what sub-agent receives}
- Output format: {structured result specification}
- Deliverable: {data structure, not conversation}
```

**Contract principles**:
- Sub-agent returns DATA, not dialogue
- Structured format enables programmatic use of results
- Main context synthesizes and acts on returned data
- Disagreement between sub-agent and main context is SIGNAL, not error

### Implementation Steps

1. **Recognize the trigger**: Identify that you're about to do a task where your context is a liability
2. **Design the context**: Decide what to include/exclude per the principles above
3. **Specify the contract**: Define exactly what the sub-agent should return
4. **Spawn with curated context**: Pass only what was designed, not "everything relevant"
5. **Receive structured result**: Get data back per the contract
6. **Synthesize**: Integrate sub-agent findings with your context — you have information they lacked

### Variations

**Light isolation** (minimal context): For adversarial review — just the artifacts and standards. Maximum fresh perspective.

**Moderate isolation** (task context): For brainstorming — problem statement and constraints, but no existing solutions.

**Scoped isolation** (domain context): For creative alternatives — domain knowledge included, but no current direction.

## Rationale

Different cognitive tasks benefit from different context states. The main conversation accumulates decisions, rationale, and direction — valuable for continuity but creating bias for certain tasks.

**The paradox**: An agent with LESS context may perform BETTER on specific tasks precisely because it lacks the biasing information.

This isn't a workaround for sub-agent limitations — isolation is a deliberate cognitive tool. Just as human organizations use external auditors, peer review, and red teams, LLM workflows can use isolated sub-agents for tasks where independence matters more than continuity.

**Design insight**: The effort of specifying context for a sub-agent is itself valuable — it forces clarity about what the task actually requires.

## Anti-Patterns

- **Passing "everything relevant"**: Defeats the purpose — the bias travels with the context
  - **Why Wrong**: Sub-agent inherits the same anchoring
  - **Example**: Sending conversation summary along with code for "fresh" review

- **Treating disagreement as error**: Sub-agent finds issues you missed — that's the point
  - **Why Wrong**: Discounting isolated perspective removes its value
  - **Example**: "The sub-agent found 3 issues but we already considered those" (did you though?)

- **Vague contracts**: "Review this and tell me what you think"
  - **Why Wrong**: Unstructured output is hard to act on
  - **Example**: Getting a paragraph of impressions instead of a findings list

- **Over-isolation**: Withholding context the task genuinely needs
  - **Why Wrong**: Sub-agent makes uninformed judgments
  - **Example**: Asking for code review without providing the requirements the code implements

## Consequences

- **Benefits**: Genuine fresh perspective; catches blind spots; higher-quality review and creative output; makes implicit biases explicit through context design
- **Tradeoffs**: Token cost of sub-agent spawning; overhead of context design; loss of nuance that full context provides
- **Risks**: Over-reliance on isolation when integration is needed; poorly designed context leads to uninformed judgment

## Examples

### Before/After Comparison

**Without Pattern**: 
Build.md STEP 9 asks Claude to review code it just wrote. Claude finds few issues — it knows why every decision was made and defends them implicitly.

**With Pattern**:
STEP 9B spawns isolated sub-agent with: ISS file (requirements), modified files (code), coding standards. Sub-agent has no knowledge of implementation discussion, design rationale, or rejected alternatives. Returns structured findings list. Catches issues the main context was blind to.

### Application Example: Brainstorming

Main conversation has been exploring authentication approaches. Discussion has converged on OAuth. User wants alternatives.

**Poor approach**: "What are some alternatives to OAuth for our auth system?" (Context includes why OAuth was chosen — alternatives will be weak)

**Isolated approach**: Spawn sub-agent with: "Design authentication for a B2B SaaS platform. Requirements: [list]. Constraints: [list]. Propose 3 distinct approaches with tradeoffs."

Sub-agent has no knowledge that OAuth was already chosen. Returns genuinely different approaches, one of which may be better.

### Application Example: Contract Design

```
Task: Adversarial code review
Input: 
  - ISS-XXX.md (requirements only, not implementation discussion)
  - Modified files: [file1.py, file2.py]  
  - Standards: coding-standards.md
Output format:
  - findings: [{severity, location, description, suggestion}]
  - summary: {critical_count, major_count, minor_count}
  - recommendation: "approve" | "revise" | "redesign"
```

## Validation

- **Success Indicator**: Sub-agent findings include issues the main context missed or dismissed
- **Edge Cases**: Tasks requiring synthesis of conversation history; creative tasks needing to BUILD ON existing ideas rather than diverge from them

## Notes and Observations

This pattern emerged from ISS-121's discovery that Cowork sub-agents run without conversation history. Initially this seemed like a limitation for Build.md adversarial review. Reframing revealed it as a feature — the isolation eliminates anchoring bias that makes self-review unreliable.

The pattern extends beyond review: any task where "knowing too much" creates bias benefits from deliberate isolation. The effort of designing what context to pass is itself clarifying — it forces explicit articulation of what the task actually needs.
