# PAT-097: Multi-Source Verification
*Version: 1.0.0 | Date: 2026-04-09 | Sprint: 070*

## Metadata
- **Type**: methodology
- **Status**: active
- **Created**: 2026-04-09

## Problem
Metrics and values from system APIs, instrumentation, or derived calculations can be unreliable — partial, stale, or measuring something different than assumed. Debugging based on a single data source leads to wrong conclusions about root causes, wasting effort on the wrong problem.

## Context
- **Use When**:
  - When debugging data accuracy or unexpected metric values
  - When API-reported values contradict observed system behavior
  - When validating instrumentation or monitoring output
  - When cross-checking derived calculations against their component sources
- **Not When**:
  - When only one data source exists (adapt: create a secondary measurement)
  - For subjective assessments where independent sources aren't meaningful
- **Prerequisites**: At least two independent sources of the same measurement must be available or constructible

## Solution
When a reported value doesn't match observed behavior:

1. Identify the metric in question and its expected value
2. Find 2+ independent sources that should report the same measurement
3. Compare values across sources — divergence reveals which source is unreliable
4. Trust the source closest to raw data over pre-aggregated or derived values
5. Investigate the failing source to understand its failure mode (partial data, caching, different semantics)

### Variations
- **Variant A — API validation**: Compare API field against alternative derivation (e.g., percentage × total vs. reported count)
- **Variant B — Instrumentation check**: Compare system metrics against manual observation or log analysis

## Rationale
- **Theoretical Basis**: Independent data sources have independent failure modes. Agreement across sources increases confidence; divergence isolates the fault.
- **Empirical Evidence**: ISS-153 — `total_input_tokens` reported ~2K when actual context was ~70K. Comparing against `used_percentage` (which matched observed behavior) revealed `total_input_tokens` only counts uncached tokens.
- **Design Decisions**: "Closest to raw data" heuristic works because aggregation and derivation introduce additional failure points.

## Anti-Patterns
- **Trusting the "authoritative" source**: Even official API fields can be misleading. "Authoritative" ≠ "accurate."
  - **Why Wrong**: API fields may have different semantics than assumed, report partial data, or lag behind actual state
- **Debugging based on one measurement**: Leads to chasing symptoms rather than root causes
  - **Why Wrong**: If the measurement itself is wrong, all conclusions drawn from it are wrong

## Consequences
- **Benefits**: Quickly isolates unreliable data sources, prevents wasted debugging effort, builds understanding of system instrumentation quality
- **Tradeoffs**: Requires finding or constructing multiple independent sources, which adds initial investigation time
- **Risks**: If all available sources share the same underlying data pipeline, they may all be wrong in the same way

## Examples

### Before/After Comparison
**Without Pattern**: Assumed `total_input_tokens` was correct, spent time investigating why sub-agents appeared to cause token overcounting. Wrong conclusion, wrong fix direction.
**With Pattern**: Compared `total_input_tokens` against `used_percentage × context_window`. Values diverged by 35x. Immediately identified `total_input_tokens` as the unreliable source. Root cause found in minutes.
