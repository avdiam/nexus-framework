# PAT-098: Grep-Before-Rename
*Version: 1.6.0 | Date: 2026-08-19 | Sprint: 108*

## Metadata
- **Type**: practice
- **Status**: active
- **Created**: 2026-04-14

## Problem

Renaming cross-referenced identifiers (section names, tags, labels, function/variable names, enum values) in multi-file projects without upfront reference discovery leaves stale references that fail silently until rediscovered later. Markdown links, string constants, documentation mentions, and comment references all appear to work while pointing to a ghost. Cost of one missed reference discovered later far exceeds cost of one grep upfront.

## Context

- **Use When**:
  - Renaming section names, tags, or labels that may be referenced across files
  - Renaming markdown or configuration identifiers in multi-file systems
  - Refactoring enum values, status labels, or severity levels used across a project
  - Any rename where cross-file references could plausibly exist
  - **(Generalized)** Any fix that must touch N surfaces for consistency (relabels, contract/charter reconciliation, doc-consistency cleanups) — encode the cross-surface completeness requirement as a grep/test acceptance criterion, not a manual re-read of an enumerated Files-Affected list
  - **(Cross-skill field/identifier)** Changing a field, key, or identifier whose consumers may touch it at runtime or via inheritance WITHOUT naming the literal token — derive the consumer set by walking the entity lifecycle (producer → finalizer → consumer), not by reading the Files-Affected list
  - **(Declared vocabulary)** Running a predicate whose vocabulary was DECLARED as a set (concept + variants + container term) over a file-class — treat the declaration as a contract and record evidence per **term × class**, including zero-hit combinations. A per-class-only evidence line cannot reveal that a declared term was never run
- **Not When**:
  - Renaming within a single file
  - Renaming private identifiers with no external references
  - Trivial renames where IDE refactor support reliably covers all sites
- **Prerequisites**: Grep/search capability over the project tree

## Solution

Before any rename that crosses file boundaries, grep for ALL occurrences of the old identifier first. Produce a complete reference list. Review the list — including unexpected or out-of-scope sites — to understand the full blast radius. Then execute the rename in one atomic pass, touching every listed site.

### Implementation

0. **Derive the consumer set first (when consumers may not name the token)**: a pure token-grep finds every site that *spells* the identifier — but a consumer that reads the entity positionally, by inheritance, or by lifecycle convention may touch it without ever naming it, so it survives a clean grep. For cross-skill fields/identifiers, derive the consumer set by walking the entity lifecycle (producer → finalizer → consumer edges) rather than trusting the authored Files-Affected list, then grep/inspect each derived consumer.
1. **Grep the old identifier** across the entire project tree (narrow by file type if needed — `.md`, `.ts`, etc.). **Search every token form** — both the canonical/prefixed name (`nexus-browse-docs`) AND the bare/colloquial form (`browse-docs`); rosters, inventories, and prose often use bare names that a prefixed-only grep silently misses.
2. **Review the reference list**:
   - Expected sites: sites you already planned to touch.
   - Unexpected sites: consider why they exist. Out-of-scope? Stale? Different concept with similar name?
3. **Decide**: proceed with full rename, narrow the scope, or abort if out-of-scope sites reveal a broader concept than anticipated.
4. **Execute atomically**: rename every in-scope site in one edit pass.
5. **Re-grep for the old name** after commit. Any remaining match is a miss.

### Quick Reference

```
BEFORE RENAME
├── grep old_name → list of sites
├── review: in-scope vs out-of-scope
└── ATOMIC rename every in-scope site

AFTER RENAME
└── grep old_name → must return 0 matches (in-scope files)
```

### Variations

- **Generalized — Executable completeness predicate (beyond rename)**: The rename case is one instance of a broader discipline. Whenever a fix must keep N surfaces consistent, make the completeness check *executable* — express it as a grep/test acceptance criterion over the whole file-class (e.g., a Success Criterion "grep confirms no residual contradiction X across all surfaces") rather than relying on a manually enumerated Files-Affected list. The executable predicate catches touchpoints the human/LLM enumeration missed, because enumeration is memory-based and fallible while a predicate over the whole class is not. Apply the same before/after-grep convergence signal: define the predicate as the acceptance test *before* implementing, run it *after*, and treat any hit as an unfinished surface.

- **Fidelity needs diff, not presence-grep (Sprint 101, ISS-211/212)**: The grep-completeness predicate proves a required block is PRESENT across N surfaces — it does NOT prove each copy is EQUIVALENT to its canonical source. For delta/duplication work (inlining shared content into discriminator-loaded variant files, reproducing a canonical block into multiple homes), verify fidelity by DIFFING each reproduced block against its canonical source, not by presence-grep. Presence-grep and fidelity-diff are complementary: grep answers "is it there in all N places?", diff answers "is what's there actually correct?". **Refinement**: the fidelity standard is faithful *semantics in the host file's format*, not byte-verbatim — reproduced content should adopt the host's formatting (e.g. a 2-bullet canonical block rendered as single-line prose in a prose-style host); only the load-bearing meaning must be exact. Validated ISS-211 (presence-grep passed SC-2 while 2 copies were non-verbatim — caught at Validate diff) → ISS-212 (Build internalized: proactively flagged a format-adaptation rather than letting presence-grep hide it).

- **Namespace-scoped predicate for document integrity (Sprint 097, ISS-205)**: When checking integrity of a file whose anchor format (e.g., `[Section: X]`) is also used by OTHER files in the project (skills, agents), a raw cross-file grep over the whole project OVER-COUNTS — it returns hits from files that define their OWN sections with the same tag syntax, not external references to the audited file. Correct predicate = two-part intersection: (1) audited-file paired tags intact (all `[Section: X]` have a matching `[/Section: X]` within the file), AND (2) external refs that explicitly reference the audited file's specific anchors still resolve. This was validated at ISS-205 Validate (Sprint 097): naive grep found 64+ cross-file hits but the refined predicate found 0 broken anchors — the 50+ apparent extras were skills owning their own `[Section:]` namespaces.

## Rationale

- **Theoretical Basis**: Rename is a one-way door. Once committed, stale references don't always cause errors — many runtimes tolerate missing references at parse time. The feedback loop on a miss is delayed, which is the most expensive kind of miss.
- **Empirical Evidence**: Sprint 072 ISS-145 Self-Evaluation → Quality Review rename missed 2 references in `nexus-build/SKILL.md` because they were located in a subsection not immediately adjacent to the primary edit site. The misses were caught at §POST-TYPE by independent reviewer — not during the rename itself. **(Generalized variant)** Sprint 095 ISS-202: the fix relabeled mislabeled `nexus-scanner` references across the architecture map; the Build plan enumerated 2 sites, but the SC-03 grep (defined as an executable acceptance criterion) surfaced a 3rd contaminated site (L1108) the enumeration missed — caught *within* Build rather than at independent Validate. Direct counter to the recurring touchpoint-under-enumeration system issue (2nd reproduction).
- **Design Decisions**: Grep takes ~1 second. Discovering one missed reference two sprints later takes ~30 minutes of context loading plus associated debugging. The asymmetry is 1000:1 or worse.

## Anti-Patterns

- **Anti-Pattern 1: Memory-Based Rename**
  - **Why Wrong**: "I know where this is referenced" relies on an inventory that is never complete, especially in LLM contexts where memory is fresh per conversation.
  - **Example**: Renaming a section and fixing the two references visible in current context, missing four more elsewhere.

- **Anti-Pattern 2: Fix-As-You-Find**
  - **Why Wrong**: Renames one site, then discovers another, fixes it, discovers another, ad infinitum. No convergence signal — you never know when you're done.
  - **Example**: Committing after fixing three references, then finding two more days later.

- **Anti-Pattern 3: Trust the IDE**
  - **Why Wrong**: IDE refactor tools cover language-level references but rarely catch markdown mentions, comment text, string constants, or documentation. For systems where config is markdown, the IDE is blind.
  - **Example**: Relying on "rename symbol" for a function used in documentation code blocks — docs go stale silently.

- **Anti-Pattern 4: Canonical-Form-Only Grep**
  - **Why Wrong**: Searching only one token form (e.g. the `nexus-`-prefixed canonical name) when rosters, inventories, and prose also use the bare colloquial form (`browse-docs`). The prefixed grep *feels* complete and returns a convergence signal, but bare-name references survive undetected. **Canonical-form grep ≠ all-form grep.**
  - **Example**: ISS-189 (Sprint 094) Build cross-grep searched `nexus-browse-docs` (prefixed) only and declared the disconnect clean; 4 dead-skill/template refs survived in `nexus-tech-ref.md`'s bare-name rosters (`browse-docs`, `learning-path`, `update-params`) plus a map mis-classification — caught only by a Conv-6 bare-name re-grep at independent Validate.

- **Anti-Pattern 5: Enumerated-List-As-Completeness-Check**
  - **Why Wrong**: Treating a manually enumerated Files-Affected / touchpoint list as the proof of completeness for an N-surface fix. The list is memory-based and inherits the same blind spot that caused the original incompleteness — it cannot reveal the surface nobody thought to list. Only an executable predicate over the whole file-class provides a true convergence signal.
  - **Example**: ISS-202 (Sprint 095) — the Implementation-Plan enumerated 2 of 3 contaminated sites; had the SC-03 grep not been defined as the acceptance test, the 3rd site (L1108) would have shipped as "complete."

- **Anti-Pattern 6: Presence-Grep-As-Fidelity-Check**
  - **Why Wrong**: A presence-grep confirms the block exists at each site but cannot detect that a reproduced copy has drifted from — or was paraphrased/condensed away from — its canonical source. Completeness ≠ equivalence; for duplication/inline work, verify the property the work actually asserts (faithful fidelity), not a proxy (presence). Use diff-against-canonical, not grep.
  - **Example**: ISS-211 (Sprint 101) — Build's presence-grep passed SC-2 while 2 inlined copies were non-verbatim (a calibration note condensed, an apply-note adapted beyond the logged framing); caught only by Validate's diff-against-canonical read. One issue later (ISS-212) the lesson was internalized — Build proactively flagged a §B format-adaptation rather than letting presence-grep hide it.

- **Anti-Pattern 7: Files-Affected-As-Consumer-Set**
  - **Why Wrong**: Trusting the authored Files-Affected / touchpoint list to enumerate the *consumers* of a changed field or identifier. The list captures what the author thought to touch; it omits the consumer that reads the entity positionally or by inheritance and never names it literally — so that consumer survives BOTH the file-list review AND a clean token-grep. The consumer set must be *derived* from the entity lifecycle, not read off a list. (Distinct from Anti-Pattern 5, which addresses the completeness *check*; this addresses how the consumer set is *constructed* in the first place.)
  - **Example**: ISS-224 (Sprint 105) — a cross-skill field change; the Files-Affected enumeration under-captured consumers that touched the field via lifecycle convention without spelling its name. Walking producer→finalizer→consumer surfaced the missed consumers a token-grep alone would not have flagged.

- **Anti-Pattern 8 — Declared-But-Unrun-Vocabulary**: declaring a predicate vocabulary of several terms, then running only a subset against a class, and recording a per-class evidence line.
  - **Why Wrong**: the evidence output reads identically whether one term ran or all of them did, because nothing re-reads the declaration against what was executed. The check reports clean over the terms it skipped. This is the execution-axis sibling of Anti-Pattern 6: AP6 says presence ≠ equivalence; AP8 says **declaration ≠ execution**.
  - **Example**: a census declaring `plug-seed`, `discoveries.jsonl`, `seeds_planted` and running only the first against the CLAUDE.md class — the two surfaces owned by the dropped term surfaced a phase later at adversarial review.
  - **Corrective**: record the evidence line as term × class, not class. Every declared term runs against every chosen class; zero-hit combinations are recorded, never collapsed.

## Relationships

- **Requires**: Grep or equivalent project-wide search
- **Enhances**: None
- **Enhanced by**: PAT-121 (match-remedy-form-to-failure-cause — supplies the selection principle for *when* an executable predicate is the right remedy form)
- **Conflicts**: None
- **Alternatives**: Full IDE refactor support (only works when all references are language-level)

## Consequences

- **Benefits**:
  - Converts possibly-incomplete renames into definitely-complete ones
  - Reveals out-of-scope sites that expose broader concepts
  - Provides a convergence signal (grep returns 0) that memory cannot
- **Tradeoffs**: Adds ~1-2 minutes to every multi-file rename
- **Risks**: False sense of completeness if grep pattern is too narrow (e.g., case-sensitive when the system uses mixed case, or searching only the canonical/prefixed form when bare/colloquial forms also exist — see Anti-Pattern 4)

## Examples

### Before/After Comparison

**Without Pattern** (ISS-145 initial attempt):
> Rename `Self-Evaluation` → `Quality Review`. Fixed 4 references I could see. Committed. §POST-TYPE found 2 more in SKILL.md subsection. 6 total, initially reported as 4.

**With Pattern**:
> `grep "Self-Evaluation" .claude/skills/nexus-build/` → 6 matches across 2 files. Reviewed list. All 6 in scope. Renamed atomically. Re-grep → 0 matches. Done in one pass with proof of completeness.

### Application Example

Renaming a status enum `WARNING` → `CONCERNS` across a methodology project:
1. `grep -rn "WARNING"` → 23 matches
2. Review: 18 are the status label (in-scope), 5 are generic English "warning" (out-of-scope)
3. Rename the 18 in-scope sites atomically
4. Re-grep `WARNING` → 5 remaining matches (the out-of-scope ones — confirmed)
5. Re-grep `CONCERNS` → 18 new matches (confirmed)

## Validation

- **Success Indicator**: Post-rename grep of the old identifier returns 0 matches in in-scope files. All new references use the new identifier.
- **Edge Cases**:
  - Identifiers that are substrings of other words — use word-boundary grep
  - Case-insensitive systems — use `-i` on grep
  - Identifiers that appear in binary files or git history — scope the grep to source files only
