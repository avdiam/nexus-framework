# PAT-103: Source-Fix Over Downstream-Bridge
*Version: 1.0.0 | Date: 2026-04-29 | Sprint: 076*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-04-29

## Problem
When an adversarial finding's evidence is "rule X enumerates A, B, C but not D, and the work depends on D inheriting from the rule," the LLM's default reflex is to mitigate at the consumer — adding bridging language ("mirroring rule X"), cross-references, or compensating documentation at the place that consumes the rule. This treats the bridge as the fix and the source rule as fixed. But the source rule is the cheaper, tighter, more honest fix: the rule's example list is the canonical surface where readers go to learn what the rule covers; extending it converts every downstream "bridge" into a citation. Bridge-as-fix recurs across protocol-amendment workflows because the find-the-evidence step naturally lands at the consumer (where the dependency is felt), not the producer (where the fix actually belongs).

## Context
- **Use When**:
  - Adversarial review surfaces a finding shaped "rule X enumerates A, B, C, and we need this work to inherit via D" — the evidence is a missing example, not a broken consumer
  - The rule lives at a single canonical location (CLAUDE.md protocol section, a registry schema header, a top-level skill rule table) and the missing example is small (one bullet, one row, one path)
  - Multiple consumers depend on the same inheritance — fixing one consumer doesn't help the others
  - Resolution menus surfaced for adversarial findings that match this shape — present "Fix the source rule" alongside Walk / Fix downstream / Skip
- **Not When**:
  - The rule is intentionally narrow and the missing example is genuinely out of scope (then it's a rule-scope question, not a source-fix question — a different decision)
  - The fix at the source would be Major-magnitude (rewriting the rule) when a citation at one consumer is actually cheaper for now
  - The "rule" is documentation rather than a live protocol — bridging at the consumer may be appropriate while the doc is curated separately

## Solution
At adversarial-finding emit time, when the finding's pattern matches "consumer compensates for missing rule example," surface "Fix the source rule" as an explicit option in the resolution menu. The default menu is Walk / Fix / Skip; this pattern adds Source-Fix as a fourth option (or replaces Fix when the source is the cheaper fix). Capture the source location, the proposed addition, and the rationale; treat as a citation update rather than a structural change.

### Implementation
- **Resolution menu shape**: `[Walk / Fix downstream / **Source-fix at {location}** / Skip]` — Source-Fix names the canonical surface (CLAUDE.md section, registry schema, rule table) and the proposed one-line addition
- **Detection cue**: finding evidence reads "rule X lists A, B, C but not D" — that wording IS the cue. Also: "we depend on D inheriting from the rule," "consumer mirrors the skill rule," "bridging language at template/agent/sub-file."
- **Rationalization to defeat**: "the consumer can document the dependency" — yes, but a citation at the consumer + the example at the source is one read for any future reader; bridge-only at the consumer makes future readers chase the inheritance through prose

### Variations
- **Variant A (protocol amendment)**: source = CLAUDE.md protocol section, fix = one-line example addition to the rule's enumerated list (e.g., add `.claude/agents/*.md` to the always-Major scope)
- **Variant B (registry schema)**: source = registry schema header or comment, fix = one-line schema documentation update
- **Variant C (skill rule table)**: source = top-level rule table in a skill SKILL.md, fix = one-row addition

## Rationale
- **Theoretical Basis**: Consumers compensate for producers when the inheritance pathway is implicit. The cost difference between source-fix and bridge-fix is asymmetric: source-fix is one edit at one canonical location and propagates by inheritance; bridge-fix is one edit at one consumer and must be repeated at every other consumer that exists or will exist. Even when only one consumer exists today, the source-fix is the same cost AND covers all future consumers.
- **Empirical Evidence**: Three reinforcements in Sprint 076 (Conv 1 design-tension footnote, Conv 2 user redirect post-Build, Conv 5 proactive Build application without redirect). Each instance: original mitigation framed as bridging at consumer; post-hoc redirect or proactive application chose source. Conv 5 internalization (no redirect needed) signals the preference is now stable enough to codify as pattern rather than further behavioral-preference iteration.
- **Design Decisions**: The pattern name is "Source-Fix Over Downstream-Bridge" rather than "Always Source-Fix" because variant cases exist where bridge is appropriate (intentionally narrow rules; documentation that's curated separately). The pattern guides menu shape and surfacing — it does not mandate the choice.

## Anti-Patterns
- **Anti-Pattern 1: Bridge-as-default**
  - **Why Wrong**: Treating bridging at the consumer as the default mitigation makes source-fix invisible. The user has to redirect explicitly each time, and downstream readers see the bridge prose rather than the canonical rule.
  - **Example**: Adversarial finding "CLAUDE.md scope rule lists skill sub-files but not agents" → mitigation "agent-template adds bridging language 'mirroring the skill rule.'" Cheaper fix: add `.claude/agents/*.md` to CLAUDE.md scope rule directly; agent-template cites it.

- **Anti-Pattern 2: Source-fix without removing the bridge**
  - **Why Wrong**: After landing the source-fix, leaving the original bridging language at the consumer creates duplication — both surfaces now state the same thing in different words. Future drift is guaranteed.
  - **Example**: CLAUDE.md scope rule extended to name agents AND agent-template still says "mirroring the skill rule" → reduce agent-template wording to a citation of the now-canonical rule example.

- **Anti-Pattern 3: Forcing source-fix when scope is genuinely narrow**
  - **Why Wrong**: Some rules are deliberately narrow; expanding them to cover the new case is a scope decision, not a citation update. Forcing a source-fix in this case rewrites the rule when bridging at the consumer is actually appropriate.
  - **Example**: A rule scoped to "skill sub-files only" intentionally excludes agents because they have a different lifecycle. Source-fix would broaden the scope; the right call may be a separate parallel rule for the new surface.

## Consequences
- **Benefits**: Canonical rules stay canonical; future readers find the example at the rule, not at a consumer's bridge prose; one fix covers all current and future consumers; reduces protocol drift surface area.
- **Tradeoffs**: Requires identifying the canonical surface up-front (sometimes ambiguous when multiple rules could host the example); slightly more analytical work at adversarial-finding time to name the source location.
- **Risks**: Over-broadening narrow rules to cover edge cases that don't really inherit; conflating "missing example in a narrow rule" with "rule scope is wrong."
