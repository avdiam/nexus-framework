# PAT-104: Resumption-Check Bypass on FAIL→Fix→Re-Run Paths
*Version: 1.0.0 | Date: 2026-04-29 | Sprint: 076*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-04-29

## Problem
Trigger mechanisms that log verdicts to `[DECISIONS]` (or any equivalent durable audit log) for resumption-detection purposes create a hidden state-machine edge on the FAIL → Fix-inline → re-run path. The resumption-check's purpose is to skip re-prompts when a prior verdict already exists this closure/run. But on the Fix-inline retry path, the prior FAIL verdict IS in the log — so the resumption-check would short-circuit the post-fix re-run, meaning the inline fix never gets validated. Table-based reasoning over the trigger spec misses this: each row (trigger, run, log, resumption) seems internally consistent. The gap is only visible by walking the post-fix re-entry path step-by-step, which Mental Simulation surfaces and table review does not.

## Context
- **Use When**:
  - Designing or reviewing a trigger mechanism that (a) logs verdict outcomes to a durable audit log used for resumption-detection AND (b) has a Fix-inline retry path on FAIL or CONCERNS
  - Adding resumption-check rows to skill flows — verify that every Fix-inline path explicitly bypasses the row added
  - Reviewing existing trigger+retry mechanisms for the same gap before adding new ones (audit-trail invariant: prior verdict + post-fix verdict both kept)
  - Pre-mortem or Mental Simulation step in Analysis or Build phase for any trigger+retry design
- **Not When**:
  - Triggers without retry paths (FAIL terminates the flow — no re-run possible, no gap)
  - Retry paths without verdict logging (no resumption-check to short-circuit)
  - One-shot validation gates with no resumption semantics

## Solution
Trigger mechanisms with Fix-inline retry paths must include explicit MANDATORY re-invocation language that bypasses the resumption-check. Both the original FAIL/CONCERNS verdict and the post-fix re-run verdict must be preserved in the audit log (not overwritten) for audit-trail integrity.

### Implementation
- **Spec language at Fix-inline branch**: "After fix: **MANDATORY** re-invocation of {trigger} that bypasses the resumption-check. The new verdict must {pass-criteria} before the flow resumes."
- **Audit-trail invariant**: log a fresh entry for the re-run verdict; do NOT overwrite the prior FAIL/CONCERNS entry. Both are kept for forensic completeness.
- **Resumption-check row addition**: when adding a row that detects "trigger already ran this closure," add adjacent language: "this row does NOT short-circuit Fix-inline re-invocation — see {Fix-inline branch reference}."
- **Detection cue at design time**: any Fix-inline branch that resolves a finding by editing one of the inputs feeding the trigger MUST be re-validated; otherwise the fix is unverified.

### Variations
- **Variant A (orchestrator-level trigger)**: e.g., /nexus-close-sprint STEP 0 Sprint-Level Validate Trigger — the resumption-check sits at the orchestrator; Fix-inline branch must invoke the validator with a flag or convention bypassing the check
- **Variant B (gated-write trigger)**: e.g., a write gate that re-validates after fix — the resumption-check sits at the gate-entry; Fix-inline branch must re-enter the gate
- **Variant C (cross-conversation resumption)**: when the trigger spans conversations and the audit log is a state file — same invariant: post-fix entry preserved alongside prior entry; resumption convention recognizes both

## Rationale
- **Theoretical Basis**: Verdict logging serves two purposes that are in tension on the retry path: (a) resumption-detection (skip if already ran) and (b) audit-trail (preserve verdict history). Without explicit bypass on Fix-inline, resumption wins over audit-trail-completeness because the resumption-check fires first on re-entry. The fix ships unvalidated. The pattern resolves the tension by making both purposes coexist: resumption recognizes the prior entry but Fix-inline mandates a fresh entry; audit-trail keeps both.
- **Empirical Evidence**: ISS-173 Conv 5 §POST-TYPE Mental Simulation surfaced this gap mid-Build. The original spec had Fix-inline language ("re-run sprint-level Validate") but added a resumption-check row in the same Build phase. Mental Sim walked the post-fix re-entry path: trigger fires → resumption-check sees `[SPRINT-VALIDATE]` FAIL entry → shortcuts → close proceeds with un-revalidated fix. Source-fix applied at close-sprint §3.4 (MANDATORY re-invocation explicitly bypassing resumption-check). Caught only via Mental Sim — table-based review of the trigger spec (signals + widget + branches) missed it because each individual row was internally consistent.
- **Design Decisions**: "MANDATORY" framing rather than "should re-run" because the Red Flags vocabulary (PAT-102 §2) treats "should" as a soft imperative. The FAIL→Fix→re-run path is where discipline matters most — soft language invites context-pressure shortcuts.

## Anti-Patterns
- **Anti-Pattern 1: Implicit re-run via the same trigger entry-point**
  - **Why Wrong**: The Fix-inline branch reads "re-run trigger after fix" but doesn't specify the bypass. Reader assumes the trigger entry-point handles re-entry correctly; resumption-check fires; re-run never happens.
  - **Example**: close-sprint §3.4 first draft: "After fix: re-run sprint-level Validate (back to step C); the verdict must improve before close." → resumption row added the same Build phase → no explicit bypass → fix would ship unvalidated.

- **Anti-Pattern 2: Overwriting the prior verdict on re-run**
  - **Why Wrong**: When the re-run verdict logs by overwriting the FAIL entry, the audit-trail loses the original finding. Future forensic review can't reconstruct what was found, what was fixed, and whether the fix actually addressed the original.
  - **Example**: re-run logs `[SPRINT-VALIDATE] PASS` overwriting `[SPRINT-VALIDATE] FAIL` → no record of the original concerns or which findings were resolved by the fix.

- **Anti-Pattern 3: Treating the retry as a continuation rather than a fresh run**
  - **Why Wrong**: If the retry is "continue from where we left off" rather than "re-execute against post-fix state," the unchanged parts of the validation aren't re-checked — the fix to one part may have invalidated assumptions in another.
  - **Example**: Sprint-level Validate Cross-cut 3 originally CONCERNS; Fix-inline addresses Cross-cut 3; re-run only re-checks Cross-cut 3 → a side-effect of the fix on Cross-cut 4 (constitution holism) goes unverified.

## Consequences
- **Benefits**: Fix-inline branches actually validate the fix; audit-trail completeness preserved across retry paths; protocol-discipline preference honored even under FAIL-then-Fix pressure; future trigger+retry designs inherit the pattern systematically.
- **Tradeoffs**: Slightly more spec verbosity at Fix-inline branches (MANDATORY language + explicit bypass); two log entries per retry instead of one (small audit-log size cost); designers must remember to add the bypass alongside resumption rows.
- **Risks**: Over-applying the pattern to triggers without retry paths (no gap to fix); confusing resumption-detection with retry-detection (different mechanisms, different purposes).

## Examples

### Before/After Comparison
**Without Pattern**: close-sprint STEP 0 Sprint-Level Validate Trigger first-draft Fix-inline branch: "After fix: re-run sprint-level Validate (back to step C); the verdict must improve before close." Resumption-check row added same phase: "trigger already run this closure (evidence: [SPRINT-VALIDATE] entry in [DECISIONS]) → skip re-prompt." Walk the path: FAIL → Fix-inline applied → re-enter STEP 0 → resumption-check sees the prior FAIL entry → skips re-prompt → close proceeds with un-revalidated fix. Gap.

**With Pattern**: close-sprint STEP 0 §3.4 post-source-fix: "Fix inline (bounded) — Only for findings small enough to resolve in current conversation without phase regression. After fix: **MANDATORY re-invocation** of `/nexus-validate SPRINT-{N}` (re-run cross-cuts on the post-fix state). The resumption-check row in STEP 0 does NOT short-circuit this re-invocation — Fix-inline always re-runs the cross-cuts before close resumes. The new verdict must be PASS or CONCERNS-with-no-blocking-findings before STEP 1 begins. Log the re-run verdict to [DECISIONS] as a fresh `[SPRINT-VALIDATE]` entry (not overwriting the prior FAIL entry — both are kept for audit-trail)."

## Notes and Observations
The pattern is cheap to apply (a few sentences of spec) and expensive to omit (silent fix-shipped-unvalidated). The cost asymmetry argues for systematic adoption at every trigger+retry design, even before a second instance accumulates. Mental Simulation is the discovery mechanism — table-based reasoning over the trigger spec is necessary but not sufficient. Pair this pattern with PAT-067 (mental simulation — absorbed the e2e-mental-simulation technique from PAT-090 in v5.1.0) at design-time for any new trigger mechanism.
