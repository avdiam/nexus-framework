# PAT-107: In-Text Verdict Anchors

*Version: 1.0.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: practice
- **Status**: active
- **Created**: 2026-05-18

## Problem

LLM-executable gates whose verdicts must be reproducible by fresh-instance reads suffer from interpretation drift: different LLM instances reading the same abstract rule produce different verdicts on the same case, especially where any judgment is involved (semantic checks, "weak vs differentiated", "trivial variation" thresholds). Out-of-band documentation, examples in adjacent files, or rationale buried in commit history do not anchor the verdict space at execution time — a fresh LLM reading only the gate text has no concrete reference to calibrate against.

## Context

- **Use When**:
  - Authoring T1/T2 gates or verdict-bearing checklists in skill files
  - Designing logic that fresh LLM instances must execute consistently across sessions and conversations
  - Creating gates where verdict thresholds carry acknowledged judgment ambiguity (LLM semantic checks, soft-warning layers)
  - Building structured templates whose output classification must reproduce across readers
- **Not When**:
  - Purely deterministic gates (regex hard-blocks, presence/absence checks) — examples add noise without anchoring value
  - Single-shot decision points used only once (cost outweighs benefit)
  - Cases where ambiguity is the intended behavior (exploratory prompts)
- **Prerequisites**: Verdict space has discrete classes (PASS / HOLD / DISCARD, or similar named outcomes)

## Solution

When authoring gate text whose verdicts must be reproducible by fresh-LLM consumers, embed **2-4 concrete worked examples directly in the gate body** — one per verdict class. Each example names a case (synthetic or retrospective), states the inputs, applies the gate logic step-by-step, and produces the canonical verdict. Examples sit inline in the gate text, not in adjacent documentation; fresh-instance readers walk them as they read the rule and inherit the verdict calibration.

### Implementation

```
Gate body structure:
  1. Verdict classes (named outcomes)
  2. Decision rule (mechanical layers + judgment layers)
  3. Worked examples — ONE per verdict class:
     • Case Name: {synthetic-A | retrospective-from-ISS-XXX}
     • Inputs: {field values}
     • Layer-by-layer application
     • Verdict: {class}
     • Why: {one-line justification anchoring the judgment}
```

Inline placement is load-bearing: examples in a separate `examples/` file are not seen by the fresh LLM executing the gate. The examples must be part of what the LLM reads at gate-firing time.

### Variations

- **Three-verdict gates** (PASS/HOLD/DISCARD): one example per verdict (3 total)
- **Multi-axis gates**: cover edge cases at each axis boundary (4-5 examples)
- **Retrospective anchoring**: when a known prior case is the canonical example (e.g., ISS-177 anchoring against SEED-013 retrospective), reference it explicitly — gives readers a known reference point in the codebase

## Rationale

- **Theoretical Basis**: LLM verdict consistency on judgment-laden classification is anchored by example proximity. Out-of-band examples decouple from the rule text at execution time; in-text examples force the LLM reading the rule to also read the calibration. The pattern exploits that LLMs interpret rules through concrete cases more reliably than through abstract thresholds.
- **Empirical Evidence**: ISS-177 STEP 1D.5 (SEED→ISS adoption gate) embedded 3 worked examples (Cases A/B/C — clean PASS, borderline HOLD, blacklisted DISCARD) directly in the gate body. Validate Tier 3 fresh-instance walks (Sprint 082 Conv 2) reproduced all three expected verdicts cleanly, including the borderline HOLD case where LLM judgment is required. Without the embedded examples, fresh-instance Validate Tier 3 retrospective replay against SEED-013 would likely have produced inconsistent verdicts under R2's gate-text-ambiguity risk.
- **Design Decisions**: Examples must include the WHY line, not just inputs+verdict. The reasoning is the calibration — verdict alone is a label; reasoning teaches the threshold.

## Anti-Patterns

- **Examples in adjacent docs**: Putting worked examples in a separate `examples.md` or in skill-level documentation.
  - **Why Wrong**: Fresh LLM executing the gate reads the gate text only — adjacent files are not loaded at firing time.
  - **Example**: A gate spec with rationale section pointing to `references/examples.md` — fresh execution gets the rule without the calibration.

- **Examples without reasoning**: "Case A produces PASS, Case B produces HOLD."
  - **Why Wrong**: Label without justification doesn't anchor the judgment threshold — fresh readers can't generalize.
  - **Example**: A bulleted list of verdict assignments with no layer-by-layer walk.

- **Too many examples**: 8+ cases attempting to enumerate the entire input space.
  - **Why Wrong**: Cognitive overhead overwhelms the gate; the LLM treats examples as exhaustive rather than illustrative.
  - **Example**: A gate body where examples are 70% of the prose and the rule is buried.

## Relationships

- **Enhances**: None
- **Synergies**: PAT-067 (mental-execution-validation — examples support the mental walk-through)
- **Conflicts**: None known
- **Alternatives**: External example files (weaker — see anti-pattern), generated-on-the-fly examples (unreliable — verdicts must be canonical)

## Consequences

- **Benefits**: Fresh-instance verdict reproducibility; gates remain self-contained (no cross-file dependency at execution); examples double as documentation.
- **Tradeoffs**: Gate text grows by ~30-60 lines per verdict class; examples need maintenance if the rule changes; example case design requires care (a misleading example anchors the wrong verdict).
- **Risks**: Example drift — if rule edits don't propagate to examples, calibration becomes contradictory. Mitigation: include example verification in [WRITE-VERIFIED] post-write checks for gate-bearing files.

## Examples

### Before / After

**Without Pattern**: ISS-177 STEP 1D.5 with rule body only ("hard-block + LLM semantic check + three verdicts"). Validate Tier 3 R2 risk: gate-text ambiguity causes verdict drift on the borderline HOLD case.

**With Pattern** (shipped): STEP 1D.5 with 3 worked examples (Cases A/B/C) inline in the gate body. Validate Tier 3 fresh-instance walks reproduce all three verdicts; R2 risk reduced from MEDIUM to LOW (gate text + examples form a consistent reading).

### Application Example

**ISS-177 SEED→ISS adoption gate** — three embedded cases:
- **Case A**: clean differentiated user_pain + vs_existing_layers naming 3 distinct safety layers → all layers clean → PASS
- **Case B**: user_pain present, vs_existing_layers restates existing layer ("this would extend that idea") → Layer 1 clean, Layer 2 catches restatement → HOLD
- **Case C**: user_pain matches blacklist regex (`would be nice`) → Layer 1 hard-fail → DISCARD

Cases A/B/C cover the three verdicts with reasoning for each, allowing fresh instances to calibrate verdict thresholds at execution time.

## Validation

- **Success Indicator**: A fresh LLM instance reading the gate (no other context) produces the canonical verdict on each embedded case and generalizes correctly to novel cases. Validated by Tier 3 fresh-instance walks (Validate methodology).
- **Edge Cases**: When the rule changes structurally, examples must be regenerated — stale examples are worse than no examples. Tie example-regeneration to version-bump discipline.

## Notes and Observations

This pattern is the author-side complement to the consumer-side mental simulation now carried by PAT-067 (mental-execution-validation), which absorbed PAT-090 at Sprint 105. That guidance says "before declaring complete, walk N scenarios through the rule." PAT-107 says "when authoring the rule, embed those walked scenarios in the rule's body so future consumers walk them automatically." The two patterns close the loop: the work the author did to verify the gate becomes the calibration the next reader inherits.
