# PAT-112: Explicit Discipline Over Implicit Assumption in Methodology Output
*Version: 1.0.0 | Date: 2026-05-22 | Sprint: 085*

## Metadata
- **Type**: methodology
- **Status**: active
- **Created**: 2026-05-22

## Problem

When methodology output (Success Criteria, status messages, audit deliverables, framing defaults) leaves an implicit default that could reasonably go either way, the wrong default is typically only caught at downstream adversarial review (Build §POST-TYPE) — late and expensive. Authoring-time silence treats the human reader as the safety net, then the safety net fires once per sprint instead of once per blueprint.

## Context

- **Use When**: Drafting methodology output where an implicit default exists and downstream interpretation is consequential — SC criteria with visibility-class shapes, audit deliverables flagging partial scope, framing defaults for SCAN vs ASSUME decisions, status messages whose phrasing seeds a later choice.
- **Not When**: Conventions universally understood by trained operators (no genuine ambiguity); routine prose that has no decision-load.
- **Prerequisites**: Methodology-output authoring context (Analysis SC drafting, Research deliverable production, Build status emission); awareness that downstream consumers may be fresh-context instances without anchoring.

## Solution

Pre-bake the desired discipline directly into the methodology output, in the form the consumer will read it:

1. **Identify the implicit default** at authoring time (Analysis Step 3 / Research Deliverable / Build status emission).
2. **Phrase the discipline explicitly** in the output itself — naming the verb the consumer should perform (SCAN, CLASSIFY, LABEL) rather than relying on the consumer to infer it.
3. **Reference the canonical definition** where one exists (cf. PAT-113 canonical-pointer-pattern) so the discipline is not paraphrased per-instance.

### Implementation

- **Analysis Step 3 (SC drafting)**: For visibility-class SC ("appendix", "flagged but not classified", "no findings unless..."), default the framing to SCAN-then-classify rather than ASSUME-then-fill — see ISS-190 nexus-create-issue STEP 3.5 §C Class 3 + nexus-analyze Research bullet surfacing.
- **Research Commit Protocol (deliverable production)**: For any SC element not completable within scope budget, emit the explicit `AUDIT-DEFERRED to ISS-{target} Analysis` label rather than silent deferral — see ISS-191 nexus-research SKILL.md Research-Mode Scope Discipline + End-of-Workflow Checklist.
- **Build status emission**: Where output seeds a downstream verdict (PASS / NEEDS-WORK / FILLED / ESCALATED), state the verdict in-text explicitly — see PAT-107 in-text-verdict-anchors.

### Quick Reference

| Authoring context | Implicit default to make explicit |
|---|---|
| Visibility-class SC ("appendix"/"flagged"/"no findings") | SCAN-then-classify (not ASSUME-empty) |
| Partial audit deliverable | `AUDIT-DEFERRED to ISS-X Analysis` label |
| Methodology status seeding a verdict | In-text verdict word (PASS/CONCERNS/FAIL) |
| Choice gate copy with multiple paths | Name the recommended path with rationale |

## Rationale

- **Theoretical Basis**: Authoring-time catch costs ~1 unit (the author thinks once and writes one extra phrase); adversarial-review catch costs ~10-50 units (independent reviewer reconstructs intent, surfaces the ambiguity, opens a finding, fix routes back through Build, registry updates, status patches). The economic asymmetry is structural — shift left.
- **Empirical Evidence**: Sprint 084 ISS-184 P2.6 R2-H1 HIGH (false-empty SC-08 appendix) caught only at parallel opus adversarial review — root cause was implicit-default authoring. ISS-190 (SCAN-then-classify) + ISS-191 (AUDIT-DEFERRED labeling) are direct methodology-refinement responses; both applied authoring-time explicit discipline and both Validate phases PASS-FILLED with zero adversarial regressions.
- **Design Decisions**: Pattern lives at methodology-output authoring (Analysis Step 3 SC drafting, Research Step 5 deliverable, Build §C status). It does not live at consumption (would re-introduce implicit-default risk per instance). It pairs with PAT-113 (canonical-pointer-pattern) when the discipline is itself a shared definition — the discipline-phrase points to a canonical source so re-statement does not drift.

## Anti-Patterns

- **Anti-Pattern 1**: "The reader will figure it out" rationalization
  - **Why Wrong**: Methodology output is consumed by fresh-context Claude instances with no anchoring — they cannot "figure it out" with the same evidence the author had. The author saw three signals; the consumer sees the output.
  - **Example**: Sprint 084 SC-08 appendix worded as "if any" — fresh reviewer interpreted as "empty appendix is acceptable"; author intended "empty appendix only after exhaustive scan returns nothing".

- **Anti-Pattern 2**: Embedding the discipline in adjacent commentary instead of the canonical output line
  - **Why Wrong**: Commentary lives in Notes / Rationale sections that downstream consumers may skip; the canonical output line (SC text, status string, audit row) is the thing that gets quoted. Discipline must travel with the quotable text.

- **Anti-Pattern 3**: Adding the discipline post-hoc after adversarial review surfaces the gap
  - **Why Wrong**: Post-hoc fix corrects this instance but the same authoring habit produces the next instance. The pattern is preventative — embed discipline in the methodology authoring skill, not in instance Validate findings.

## Relationships

- **Requires**: None (independent practice).
- **Enhances**: PAT-113 (canonical-pointer-pattern) — discipline phrases benefit from canonical sourcing; PAT-102 (discipline-enforcement-layer) — both shift catch from late to early.
- **Conflicts**: None.
- **Alternatives**: Adversarial-review-only catch (proven late and expensive); reviewer training (does not scale across fresh-context instances).

## Consequences

- **Benefits**: Reduces Build §POST-TYPE adversarial-review burden; produces output legible to fresh-context consumers; prevents the same implicit-default class from re-appearing once codified in the authoring skill.
- **Tradeoffs**: Slightly longer SC / status / audit text; requires authoring-time discipline (Analysis Step 3 cannot be skipped to Implementation faster).
- **Risks**: Over-specification — encoding every conceivable disambiguation makes output bloated. Mitigated by scoping to genuine implicit-default cases where the wrong interpretation is recoverable only at adversarial review.

## Examples

### Before/After Comparison

**Without Pattern (Sprint 084 ISS-184 P2.6)**:
- SC-08 wording: "Appendix entries flagged but not classified if any"
- Implicit default: empty appendix acceptable (reader can interpret either way)
- Result: HIGH adversarial finding at parallel opus review; structural ambiguity surfaced 2 weeks after authoring; cost = full Build-cycle catch.

**With Pattern (Sprint 085 ISS-190)**:
- SC-08 framing (nexus-create-issue STEP 3.5 §C Class 3): "Visibility-class SC criteria default to SCAN-then-classify framing — flag what exists, do not assume empty"
- Explicit default: SCAN-then-classify
- Result: Fresh-context Validate PASS-FILLED; zero regressions; authoring-time discipline propagated to the create-issue skill so the next audit-shape Research issue starts with the right default.

### Application Example

Sprint 085 ISS-191 applied the same pattern at the Research deliverable boundary: `AUDIT-DEFERRED to ISS-{target} Analysis` syntax embedded in nexus-research/SKILL.md Commit Protocol + End-of-Workflow Checklist + 3 mode-file canonical pointers. Cross-issue confirmation within a single sprint (ISS-190 SCAN-then-classify + ISS-191 AUDIT-DEFERRED) gave the pattern 2 reproductions at distinct authoring sites — graduating it from candidate to active pattern at Sprint 085 closure.

## Validation

- **Success Indicator**: Adversarial review finds zero implicit-default findings on output produced under the pattern. Fresh-context Validate confirms the discipline-phrase reads as authored.
- **Edge Cases**: Discipline-phrase itself becomes ambiguous if not canonically defined — apply PAT-113 canonical-pointer-pattern to prevent paraphrase drift.
