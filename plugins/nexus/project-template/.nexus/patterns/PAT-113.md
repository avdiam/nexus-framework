# PAT-113: Canonical-Pointer Pattern for Shared Definitions
*Version: 1.1.0 | Date: 2026-05-29 | Sprint: 092*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-05-22

## Problem

When two or more skill files reference the same definition (signal helper, taxonomy, vocabulary, threshold, enum, syntax template), the natural authoring failure mode is to **inline the definition at each reference site** for reader convenience. Inline duplication produces silent drift: when one site is updated to fix a bug or add a case, the others lag — and the drift surface is invisible until cross-file adversarial review surfaces it. The structural problem cannot be fixed by behavioral discipline (always-re-grep-on-edit) because LLM authoring naturally re-states for clarity.

## Context

- **Use When**: ≥2 skill files reference the same definition; the definition is genuinely shared (not coincidentally similar); the definition is consequential (changing one but not the others is a regression).
- **Not When**: References are coincidentally similar but semantically distinct (don't force-canonicalize); the definition is so short/stable that drift risk is negligible (single-word enum values); the shared name is purely lexical (no operational meaning).
- **Prerequisites**: A clearly-identifiable canonical home (one skill file is the natural source-of-truth); section-anchorable target so the pointer can survive future edits.

## Solution

Canonicalize the definition at ONE location and have all other references point to it via canonical-pointer phrasing. Do not duplicate the definition body inline at non-canonical sites.

1. **Identify the canonical home**: the skill file where the definition was first authored OR the skill file most semantically responsible for the concept.
2. **Anchor by section name** (not line number — line numbers drift): `[Section: Name]` or `## Heading-Anchor`.
3. **Pointer phrasing at non-canonical sites**: `Single source of truth: defined in {path}#{anchor}. Do not paraphrase or restate.`
4. **Optional execution-vs-audit distinction**: when the canonical concept has multiple senses (e.g., audit-time vs execution-time meanings of "deferred"), enumerate the distinct senses inline at the canonical home so consumers don't confuse them.

### Implementation

At authoring time (Analysis Step 3 / Build Phase X):
- Search for existing references to the concept across `.claude/skills/`, `CLAUDE.md`, `.nexus/templates/`, `.claude/agents/`.
- If ≥2 references exist, designate one canonical and refactor the others to canonical-pointers.
- Place the pointer block adjacent to the section heading at each non-canonical site so consumers see it before reading any reference text.

At Validate phase (structural drift gate):
- Grep the canonical phrase template across all reference sites; identity should be character-exact (modulo path).
- If any non-canonical site has re-stated the definition body inline, flag as drift-surface regression.

### Quick Reference

| Shared definition type | Canonical home (typical) | Pointer phrasing |
|---|---|---|
| Signal helper / detection function | The skill that first computes the signal | `Single source of truth: defined in {path} [Section: X]. Do not re-state the disjunct list here.` |
| Audit syntax template / labeling convention | The methodology skill that owns the deliverable shape | `Single source of truth: defined in {path} → Section → Sub-section. Use canonical syntax; do not paraphrase.` |
| Cross-skill taxonomy / classification | The skill that owns the taxonomy authoring | `Canonical taxonomy: {path} [Section: Y]. Reference by class name; do not duplicate class definitions.` |
| Threshold / enum / score band | CLAUDE.md or the protocol skill that defines it | `Per [Section: Protocol-Name] in CLAUDE.md.` |

## Rationale

- **Theoretical Basis**: Inline duplication creates N drift surfaces; canonical-pointer creates 1. The maintenance cost of inline duplication is O(N) per definition change; canonical-pointer is O(1). LLM authoring naturally re-states for clarity — a structural fix beats a behavioral always-re-grep discipline that depends on the author remembering each duplicate site.
- **Empirical Evidence**: Sprint 085 ISS-190 Validate Probe 1 caught nexus-analyze inline `audit_shape_signal` definition narrower than nexus-create-issue STEP 3.5 source-of-truth (omitted "scan exhaustively", "flag", "collect findings" verbs). Source-fixed inline at L207-208 by removing inline disjunct re-list and pointing to canonical helper. Caught only at adversarial review; would have shipped as drift-risk without it. ISS-191 then applied the pattern proactively at 3 mode files referencing a single SKILL.md anchor — drift surface = 0 across the 3 files at Validate verification.
- **Design Decisions**: Section-name anchors (not line numbers) because line numbers drift on unrelated edits; identical template wording across pointer sites because non-identical pointers are themselves a drift surface (the pointer can drift even when the canonical definition doesn't); execution-vs-audit-style distinction blocks at the canonical home because conflicting senses of the same term are the most common confusion source.

## Anti-Patterns

- **Anti-Pattern 1**: "Inline for readability" rationalization
  - **Why Wrong**: Readability gain at one site is paid for by drift surface across N sites. Readers can follow a one-line pointer; the cost is sub-second cognitive load. Inline duplication makes the file feel self-contained but is structurally dishonest about cross-file coupling.
  - **Example**: ISS-190 nexus-analyze inline disjunct re-list (3 verbs vs nexus-create-issue's 4) — inline felt cleaner; in practice produced silent drift caught only at adversarial review.

- **Anti-Pattern 2**: Line-number anchors instead of section-name anchors
  - **Why Wrong**: Line numbers drift on unrelated edits to the canonical file; section names are semantic and stable. A pointer to `SKILL.md L341` is stale the moment the canonical file gains a paragraph above L341.

- **Anti-Pattern 3**: Paraphrased pointer text per site ("see X for details" vs "see Y for the canonical definition")
  - **Why Wrong**: Pointer wording itself is a drift surface. Identical pointer templates across non-canonical sites make grep-based drift detection reliable; paraphrased pointers reintroduce the same drift class at the pointer layer.

- **Anti-Pattern 4**: Inline re-enumeration of the canonical *list contents* in the pointer summary
  - **Why Wrong**: A pointer MAY carry a short, high-level, **stable** summary for discoverability (naming the SoT + "do not paraphrase"), but re-enumerating the canonical list's *items* inline recreates the O(N) drift surface at the pointer layer — when the canonical list gains or loses an item, the inline enumerations lag silently. Keep the summary at the level of *what the list is for*, never *what is in it*.
  - **Disclosed-tradeoff note**: Carrying a high-level parenthetical summary alongside a pointer is an **accepted** tradeoff (discoverability for the reader skimming the consumer file) *provided* the canonical table remains the single source of truth and the pointer names it. The line not to cross is inline *enumeration of the list members*. When in doubt, the bare pointer is always safe (proven by the bare Simple-Path pointer in ISS-192).
  - **Example**: Sprint 092 ISS-195 F1 (3 nexus-research mode-pointers each restating the ~80-word audit-shape summary) + ISS-192 F1 (3 nexus-analyze type-file pointers restating the 4-class list inline; the 4th — Simple Path — is a bare pointer, proving the bare form works). Both **walked** as disclosed tradeoffs — drift risk low, SoT is the canonical table; flagged here so the threshold (high-level summary OK, inline enumeration not) is explicit.

## Relationships

- **Requires**: PAT-098 (grep-before-rename) — canonical-pointer adoption requires finding all existing reference sites; the same grep discipline.
- **Enhances**: PAT-112 (explicit-discipline-over-implicit-assumption) — discipline phrases benefit from canonical sourcing; PAT-103 (source-fix-over-downstream-bridge) — canonical-pointer is the structural source-fix when the bug is "inline duplicate is narrower than another".
- **Conflicts**: None.
- **Alternatives**: Always-re-grep behavioral discipline at every edit (fragile — depends on author memory); per-edit-time audit gate (catches but does not prevent).

## Consequences

- **Benefits**: Drift surface collapses from O(N) to O(1); structural-honesty about cross-file coupling; future audits find less drift; cross-file edits become localized (canonical edit propagates by reference).
- **Tradeoffs**: Slightly more indirection for fresh-context readers (one extra navigation step to see the definition); requires section-name anchoring discipline at the canonical home (renaming sections must propagate to pointer sites — though PAT-098 grep catches this).
- **Risks**: Over-canonicalization — forcing pointer for definitions that are coincidentally similar but semantically distinct re-introduces wrong coupling. Mitigated by the "genuinely shared and consequential" prerequisite check.

## Validation

- **Success Indicator**: Grep the canonical-pointer phrase template across all non-canonical sites returns character-identical matches; grep the canonical definition body across non-canonical sites returns zero matches; drift surface = 0 verifiable via Validate-time literal-string sweep.
- **Edge Cases**: Canonical definition is updated to add a case — pointer sites need no edit (the pointer carries the updated definition by reference); section-name at canonical home is renamed — PAT-098 grep finds all pointer sites; update pointer template at each.
