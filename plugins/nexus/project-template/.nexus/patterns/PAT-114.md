# PAT-114: Baseline-Anchored SC Calibration
*Version: 1.0.0 | Date: 2026-05-25 | Sprint: 086*

## Metadata
- **Type**: methodology
- **Status**: active
- **Created**: 2026-05-25

## Problem

Quantitative Success Criteria (line-count, file-count, complexity, density metrics) authored in research or analysis conversations drift between authoring time and execution time when source artifacts mutate. The SC target is calibrated against a baseline that no longer matches reality at execution time. Result: Validate produces false-negative verdicts on legitimately-achieved structural intent because the proxy metric was anchored to an unreachable number, not because the work fell short.

## Context

- **Use When**:
  - Authoring audit-deliverables with quantitative LOC or file-count Success Criteria
  - Multi-sprint or multi-conversation plans where research/analysis conv ≠ execution conv (cross-conv baseline drift window)
  - Refactor, simplification, or consolidation work where the source artifact will mutate (other sprints, other issues, user edits) before this issue's Build
  - CAUTION: Only applies when the source artifact is under version control (commit-hash anchorable) — without VCS, there is no verifiable baseline to anchor against
- **Not When**:
  - Qualitative-only SCs (e.g., "user can accomplish X", "verdict reads coherently")
  - Single-conversation work with no drift window between authoring and execution
  - Static, frozen reference artifacts that are not expected to change between authoring and execution
- **Prerequisites**: Source artifact under VCS; authoring conversation has access to current `wc -l` or equivalent metric tooling; execution conversation has access to git for recomputing baseline.

## Solution

At authoring time, anchor every quantitative SC component to a commit-hash-verified baseline captured inline with the SC. At execution time (Build), recompute the current baseline, derive the drift ratio, and apply proportional correction to the SC target before Validate evaluates the verdict.

### Implementation

**At authoring (Research / Analysis phase)**:

1. For each quantitative SC component, capture baseline inline:
   ```
   SC-XX: ... target delta −180 to −235L
     baseline_loc_at_audit: 1700
     baseline_commit: abc1234
     measurement: wc -l {file} @ commit abc1234
   ```
2. Embed both the absolute target AND the implied ratio (e.g., −10.5% to −13.8% of baseline) so the ratio can travel even if absolute numbers go stale.
3. If multiple files contribute, anchor each separately — aggregate ratios mask per-file drift.

**At execution (Build phase, before Validate)**:

1. Recompute current baseline: `wc -l {file} @ HEAD`
2. Compute drift ratio: `current / baseline_at_audit`
3. Apply proportional correction:
   ```
   corrected_target_lower = original_target_lower × drift_ratio
   corrected_target_upper = original_target_upper × drift_ratio
   ```
4. Surface BOTH original and corrected targets in Build's Implementation-Log under a `### SC Calibration` subsection — explicit, not implicit.
5. Hand off to Validate with the corrected target as the authoritative gate; original target stays in record for traceability.

**At Validate**:

1. Evaluate against the corrected target.
2. If verdict diverges from original-target evaluation, log the calibration as the source of divergence (not as user override of methodology).
3. If structural intent achieved but corrected target also missed: CONCERNS with explicit dual-disposition framing (calibration limit + structural divergence).

### Quick Reference

| Phase | Action |
|---|---|
| Research / Analysis | `baseline_loc_at_audit: N` + `baseline_commit: <hash>` inline with each quantitative SC |
| Build (pre-Validate) | Recompute baseline; compute drift ratio; apply proportional correction; surface in Implementation-Log |
| Validate | Gate against corrected target; original retained for audit trail |

## Rationale

- **Theoretical Basis**: Proxy metrics need stable referents. A line-count target only measures structural intent when the line-count denominator is stable. When the denominator drifts and the numerator (target) doesn't, the ratio (verdict) measures noise.
- **Empirical Evidence**: Sprint 084 §9.2 calibration finding 13 (simplification-label hit density ≠ structural change weight, mandate B5) + Sprint 086 F4 (CLAUDE.md baseline 1700L claim vs actual 1121L = 35% smaller baseline; SC-01 target −180 to −235L vs achievable ~−119 to −155L vs actual −85L). Both surfaced as CONCERNS verdicts on structurally-achieved work because the calibration axis was unstable.
- **Design Decisions**:
  - Anchoring is cheap at authoring time (one extra field per SC); drift correction is mechanical at execution time (4 lines of arithmetic).
  - Surfacing corrected target alongside original preserves audit trail — Validate readers can verify the calibration arithmetic, not just trust it.
  - Commit-hash anchoring (vs date or sprint number) gives verifiable re-grounding; date anchors are useless if the user works on a branch or stashes.

## Anti-Patterns

- **Anti-Pattern 1**: Loose baseline claims in prose ("CLAUDE.md is ~1700L")
  - **Why Wrong**: Prose claims aren't verifiable at execution time; they decay across sprints; they invite verdict noise.
  - **Example**: Sprint 084 audit-deliverable §3.1 stated "~1700L" baseline; Sprint 086 Build measured 1121L (35% smaller) — SC-01 line-delta target was calibrated against the wrong number, producing CONCERNS verdict on structurally-achieved work.
- **Anti-Pattern 2**: Recalibrating the SC target at Build instead of authoring time
  - **Why Wrong**: Build editing its own gate is a methodology smell — Validate authority is degraded if Build can move the goalposts. Authoring-time anchoring + execution-time mechanical correction keeps the calibration verifiable, not editorial.
- **Anti-Pattern 3**: Replacing quantitative SCs with qualitative ones to dodge calibration
  - **Why Wrong**: Quantitative SCs exist because qualitative ones produce vague verdicts. Removing the quantitative axis loses signal; the fix is to anchor it properly, not erase it.

## Relationships

- **Requires**: Version control on the source artifact (commit-hash anchorable); tooling to measure the chosen metric (`wc -l`, file-count, complexity tool).
- **Enhances**:
  - **PAT-105** (phase-collapse-on-pre-drafted-canonical-sources) — both address authoring-time vs execution-time calibration asymmetry; PAT-105 collapses Build authoring effort, PAT-114 calibrates the verdict gate. Pairs naturally on audit-deliverable execution sprints.
  - **PAT-112** (explicit-discipline-over-implicit-assumption-in-methodology-output) — both shift catch from late adversarial review to authoring time. PAT-114 specializes the principle to quantitative SC components.
- **Conflicts**: None known.
- **Alternatives**:
  - Recompute and rewrite SC target at Build (rejected — degrades Validate authority; see Anti-Pattern 2).
  - Replace quantitative SCs with qualitative ones (rejected — loses signal; see Anti-Pattern 3).

## Consequences

- **Benefits**:
  - Validate verdicts reflect structural intent achievement, not stale baseline arithmetic.
  - Calibration is verifiable end-to-end (commit-hash + arithmetic), not editorial.
  - CONCERNS verdicts on calibration-drift work shrink; CONCERNS reserved for genuine partial-achievement.
  - Cross-sprint audit-deliverable execution becomes more reliable (the use case where drift is largest).
- **Tradeoffs**:
  - One extra field per quantitative SC component at authoring time.
  - Build's Implementation-Log carries a small `### SC Calibration` subsection.
  - When drift is small (<5%), the correction is noise — acceptable overhead for the cases when it isn't.
- **Risks**:
  - If the baseline commit is rewritten (rebase, force-push), the anchor breaks. Mitigation: anchor to a tag or stable commit, not a feature branch tip.
  - Over-anchoring (every metric, including trivial ones) creates noise. Mitigation: apply to high-stakes quantitative SCs only.

## Examples

### Before/After Comparison
**Without Pattern** (Sprint 086 F4 reality):
- Sprint 084 audit-deliverable §3.1 wrote: "CLAUDE.md ~1700L; target removal ~−180 to −235L (~10.5% to 13.8%)."
- Sprint 086 Build measured actual baseline: 1121L (35% smaller than claimed).
- Build achieved −85L (structural intent 100% met — all 9 multi-env sections collapsed).
- Validate evaluated against original target −180/−235L → CONCERNS verdict on PASS-shaped work.
- Root cause: target arithmetic, not structural execution. Verdict noise.

**With Pattern**:
- Sprint 084 audit-deliverable §3.1 writes:
  ```
  SC-01: CLAUDE.md backbone simplification
    baseline_loc_at_audit: 1700
    baseline_commit: <sprint-084-hash>
    target_delta: −180 to −235L (−10.5% to −13.8% ratio)
  ```
- Sprint 086 Build recomputes: `wc -l CLAUDE.md @ HEAD = 1121`; drift_ratio = 1121/1700 = 0.66.
- Build applies correction: corrected_target = −180×0.66 to −235×0.66 = −119 to −155L.
- Build's Implementation-Log § SC Calibration surfaces both original and corrected.
- Validate evaluates against corrected target.
- Actual −85L still below corrected −119L → CONCERNS, but now CONCERNS reflects genuine partial achievement (delta below even drift-corrected target), not calibration noise. Dual-disposition framing in Issues Found.

### Application Example
Sprint 086 ISS-186 (this pattern's origin): Build documented the calibration finding inline as TD-3 ([Q] user routing decision: leave target unamended at Build, route F4 to Validate with calibration evidence). Validate accepted CONCERNS with explicit F4 framing. PAT-114 codifies the recurring shape so future audit-execution sprints anchor at authoring time instead of routing to user judgment.

## Validation

How to verify this pattern is working:
- **Success Indicator**: Audit-deliverable §X.x rows carry `baseline_loc_at_audit: N` + `baseline_commit: <hash>` fields; execution-sprint Build's Implementation-Log contains a `### SC Calibration` subsection with drift_ratio + corrected target; Validate evidence cites corrected target as the gate; CONCERNS verdicts citing baseline-drift root cause approach zero.
- **Edge Cases**:
  - Anchor commit rebased / force-pushed → re-anchor to a stable tag at authoring time.
  - Multiple-file aggregate SCs → anchor per file; aggregate ratios mask per-file drift.
  - Baseline grew between authoring and execution (rare) → correction increases target; same arithmetic applies.

## Notes and Observations

PAT-114 is a specialization of PAT-112 (explicit-discipline-over-implicit-assumption) for the specific case of quantitative SC components. Both shift catch from late adversarial review to authoring time, but PAT-114 prescribes a concrete mechanism (commit-hash anchor + drift correction) rather than a general posture.

The pattern arose from a recurring shape across two sprints (084 finding 13 + 086 F4); both surfaced as CONCERNS verdicts on structurally-achieved work because the calibration axis was unstable. The cost of fixing it is one extra YAML field per SC; the cost of NOT fixing it is recurring verdict noise on cross-sprint audit-execution work, eroding Validate's signal-to-noise ratio.

Adoption point: nexus-research audit modes (`adoption.md` or new `audit.md`) — the authoring side of the pattern lives there. Execution side (Build correction arithmetic) can be a small protocol addition to `/nexus-build` SKILL.md (1-2 sentences in §PRE-TYPE Pattern Matching or §POST-TYPE Quality Review).
