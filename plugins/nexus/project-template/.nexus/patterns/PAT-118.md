# PAT-118: diagnose-gap-nature-before-mechanism
*Version: 1.0.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-05-29

## Problem

A recurring discipline gap persists despite being documented (anti-pattern triplets, protocol rules, reminders). The natural response is to build an enforcement mechanism. But build effort is wasted in two distinct ways that are invisible until late:

1. **Nature mismatch** — the gap is a different *type* of problem than the chosen mechanism can address (e.g., an advisory mechanism aimed at what is actually an attention/compliance gap).
2. **Infeasible mechanism** — the platform does not expose the surface the mechanism would need to operate (e.g., a hook expected to suppress something the platform injects downstream of all hooks).

Both failures are discoverable *before* building, against primary sources — but only if the diagnosis step is run first.

## Context
- **Use When**: A recurring-discipline gap recurs despite documentation and a remediation mechanism is being considered; choosing among enforcement mechanisms (hook / skill-gate / widget / convention); any platform-integration decision where a mechanism depends on an assumed platform capability.
- **Not When**: The gap's nature and the mechanism's platform-feasibility are already proven against primary sources; a one-shot non-recurring issue where no mechanism is being built.
- **Prerequisites**: Access to primary sources (platform docs, actual source, or a live hands-on test) — not just secondary descriptions or memory.

## Solution

Before investing design/build effort in a remediation mechanism, verify TWO things against PRIMARY SOURCES:

1. **Gap NATURE** — classify the gap into one of three categories:
   - *awareness / delivery* — the actor doesn't know, or the signal isn't arriving. Advisory mechanisms (reminders, injected context) CAN close these.
   - *attention / compliance* — the signal arrives and is understood but not acted on under load. Advisory mechanisms have a hard ceiling here; only a *forcing* mechanism can close it.
   - *infeasible-mechanism* — the platform exposes no surface for the intended mechanism at all.
2. **Platform FEASIBILITY** — confirm the platform actually exposes the surface the mechanism needs, verified against primary sources (docs + a live test), not assumed from naming or secondary description.

Build only once both checks pass. If the gap is attention-class, do not ship an advisory mechanism expecting compliance; if the mechanism is infeasible, stop at analysis.

### Implementation
1. State the gap and the proposed mechanism.
2. Ask: "Which of the three categories is this gap?" — cite the evidence (reproduction transcripts, where the failure actually occurs).
3. Ask: "Does the platform expose the surface this mechanism needs?" — verify against primary source (docs + hands-on test), per `verify_external_claims`.
4. If nature ≠ mechanism-class, or feasibility fails → redesign or stop, BEFORE build.

## Rationale
- **Theoretical Basis**: Delivery ≠ compliance, and documentation ≠ capability. A mechanism's *reliability* is independent of whether it targets the right *class* of gap. A perfectly-delivered advisory reminder cannot compel an action the actor de-prioritizes under load.
- **Empirical Evidence**: ISS-200 (Sprint 091) built a 100%-reliable two-hook advisory delivery layer (verified 13/13 fires) that still hit a ~14% compliance ceiling — the gap was attention-under-autonomous-flow, which no advisory mechanism can close. ISS-199 (Sprint 091) nearly built a hook/settings suppressor for a harness reminder before primary-source verification established it was architecturally impossible (hooks only ADD context, downstream of reminder injection; no disable flag) — caught at Analysis, before build.
- **Design Decisions**: The diagnosis is two-legged (nature AND feasibility) because the two failures are independent — a feasible mechanism can still target the wrong gap-class, and a correctly-classed mechanism can still be infeasible.

## Anti-Patterns
- **Anti-Pattern 1**: Build-the-mechanism-first on a documented recurring gap.
  - **Why Wrong**: Assumes the gap is an awareness/delivery problem (the class mechanisms address) without checking. If it's an attention/compliance gap, the mechanism delivers reliably and changes nothing.
  - **Example**: Shipping an advisory reminder for a discipline that is skipped under cognitive load, then measuring single-digit compliance despite 100% delivery.
- **Anti-Pattern 2**: Treating a tool's name or secondary docs as proof it can do what you need.
  - **Why Wrong**: Platform surfaces have specific event-ordering and capability constraints; "hooks can add context" ≠ "hooks can remove injected context."
  - **Example**: Designing a hook to suppress a harness-injected reminder that is emitted downstream of all hook processing.

## Relationships
- **Requires**: access to primary sources for verification
- **Enhances**: the `verify_external_claims` behavioural preference (CLAUDE.md) — supplies the feasibility-verification leg (formerly PAT-052, retired Sprint 109 as framework-subsumed)
- **Conflicts**: none
- **Alternatives**: none (diagnostic-first is the gate, not a competing approach)

## Consequences
- **Benefits**: Avoids sunk build cost on mechanisms that structurally cannot close the gap; redirects effort toward the right class of solution (or a conscious accept-the-ceiling decision); catches infeasible mechanisms at Analysis.
- **Tradeoffs**: Adds a diagnosis step before build — a small front-loaded cost on every enforcement-mechanism decision.
- **Risks**: Mis-classifying the gap nature (mitigated by citing reproduction evidence, not intuition); over-applying to trivial one-shot fixes where no mechanism is being built.

## Examples

### Before/After Comparison
**Without Pattern**: A recurring status-line skip is documented; a hook is built to inject corrective reminders. Delivery is verified reliable, yet compliance stays ~14% — the gap was attention, not awareness. Build cost spent; gap remains.
**With Pattern**: The gap is first classified as attention/compliance; the team recognizes advisory mechanisms have a hard ceiling here and either accepts the ceiling consciously or pursues a forcing mechanism — no surprise after build.

### Application Example
ISS-199: proposed mechanism = hook/settings suppression of a harness TaskCreate reminder. Feasibility check against primary sources (hooks docs + live evidence) showed hooks cannot remove harness-injected reminders → mechanism infeasible → pivoted at Analysis to a satisfy-and-leverage convention, avoiding a doomed build.

## Validation
- **Success Indicator**: Before any enforcement-mechanism build, the ISS Analysis records both the gap-nature classification (with reproduction evidence) and a primary-source feasibility confirmation.
- **Edge Cases**: Gaps that are genuinely awareness/delivery — there the advisory mechanism is the correct fit and the pattern simply confirms it quickly.
