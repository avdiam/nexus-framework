# PAT-119: Issue-Premise Drift-Check at Execution

*Version: 1.1.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-05-29

## Problem

An issue (ISS) is a hypothesis written at creation time. By the time it reaches execution — often many sprints later — the landscape has drifted: a named file may never have existed or been renamed, a cited pattern number may have been reassigned to a different pattern, a stated design fork may rest on an assumption that is no longer true, and a sibling issue may have *already delivered the need* under a different banner. The same drift afflicts any **parked design decision** — a deferred plan, a design set aside while other work proceeded — not only a formal ISS document; and the load-bearing premise is often **quantitative** (a size, count, or threshold the design was justified on) that has silently moved while the design sat. The natural failure mode is to treat the issue's own framing (its pre-specified design options, named artifacts, asserted premises, and the numbers that justified them) as ground truth and design the solution directly on top of it. This bakes stale assumptions into the solution and is caught — if at all — only at downstream adversarial review, after design effort is already sunk.

## Context

- **Use When**: At Analysis, before locking design direction, whenever the issue *pre-specifies* any of: design options/forks, concrete artifact references (file paths, section names, pattern/issue numbers, placement targets), or a premise about the current state of the system.
- **Use When**: An issue was created in an earlier sprint and is only now being executed (drift window is large).
- **Use When**: Activating or RESUMING a design parked across intervening work — a deferred decision or a plan set aside while other work proceeded — not only a formal ISS document.
- **Use When**: The load-bearing premise is QUANTITATIVE — a size, count, or threshold the design was justified on. These drift silently as the system grows, with no event marking the change; re-measure at activation.
- **Use When**: The issue says "do X to file Y" or "use PAT-NNN as the carrier" or "place this in A or B" — any concrete claim that is cheap to verify and expensive to get wrong.
- **Not When**: The issue carries no pre-specified premises/artifacts (pure open-ended exploration); or the premise is trivially self-evident and stable (no plausible drift).
- **Prerequisites**: Access to primary sources — actual file contents, current registry state, live skill code — not memory or the issue's own summary.

## Solution

Before designing, surface the issue's **load-bearing premises** and verify each against a **primary source**:

1. **Enumerate the stated premises**: list every concrete artifact the issue names (paths, section names, pattern/issue IDs) and every design fork it pre-specifies.
2. **Verify each against primary sources**: grep/read the actual file, check the live registry entry, read the current skill code. Do NOT trust the issue's description, your memory, or a derived summary.
3. **Reconcile**: where a premise has drifted (file absent, ID reassigned, need already met, assumption false), *reframe the design before proposing it* — and record the reframe so the redirect is visible.
4. **Then** lock direction and proceed to design.

The discipline is upstream of design, not a downstream check: a reversed premise should change what you build, not be patched in after.

### Implementation

At Analysis (findings-before-edits): treat the issue as a set of claims to test, not instructions to follow. Pair this with PAT-098 (grep-before-rename) — the same grep discipline produces the convergence signal that proves a named cross-reference still resolves. Where a fork reverses, present the reframe to the user as a finding *before* requesting approval-to-proceed.

## Rationale

- **Theoretical Basis**: An issue is a point-in-time snapshot of intent and context. Intent is durable; the *factual scaffolding* (which file, which pattern number, what already exists) is perishable. Verifying the perishable scaffolding at execution time is cheap (one grep/read) and the error it prevents is expensive (a design built on a false premise, caught only at adversarial review or shipped as drift). **Quantitative premises are the most perishable of all**: a size/count/threshold drifts *continuously* as the system grows, with no discrete event signalling that the number the design was justified on no longer holds — so a parked design's numeric justification must be re-measured at activation, not assumed.
- **Empirical Evidence**: Sprint 092 — **ISS-195**: the issue named placement targets "modes/adoption.md OR a new audit.md" and cited "PAT-115" as the pattern carrier. Primary-source check at Analysis found `audit.md` never existed, `PAT-115` was already assigned to a different pattern (harness-reminder-suppression), and `PAT-112` had since appeared and already encoded the principle — **both** design forks reversed before any code was written. **ISS-201**: the issue proposed trimming two CLAUDE.md sections; grep-verifying the stated cross-references against primary sources found the sole live inbound anchor was a single BOOTSTRAP line (0 skill/hook refs) and the compaction hook was self-sufficient — making the trim provably safe rather than risky.
- **Design Decisions**: Verification targets the *issue's own claims* (internal premises), which distinguishes it from verifying system behaviour (the Verification core principle; formerly PAT-029, retired) or external capabilities (`verify_external_claims`). It is upstream of reframing (PAT-087) — you cannot reframe a fork correctly until you know which of its premises are false.

## Anti-Patterns

- **Anti-Pattern 1**: Designing directly on the issue's stated options/artifacts as given
  - **Why Wrong**: The issue is a hypothesis, not a spec. Trusting its named files/IDs/forks bakes stale facts into the design; the error surfaces only at adversarial review after design effort is sunk.
  - **Example**: Building ISS-195's solution into a phantom `audit.md` (named in the issue, never existed) instead of verifying placement first.

- **Anti-Pattern 2**: Verifying premises *after* designing (downstream check instead of upstream gate)
  - **Why Wrong**: A reversed premise should change *what you build*. Discovering it after the design is drafted means rework, not redirection — and the redirect opportunity (findings-before-edits) is lost.

- **Anti-Pattern 3**: Verifying against the issue's summary, memory, or a derived artifact instead of primary sources
  - **Why Wrong**: Summaries and memory carry the same drift the premise check exists to catch. Only the live file/registry/code is authoritative.

## Relationships

- **Requires**: PAT-098 (grep-before-rename) — the grep discipline that produces the convergence signal proving a named cross-reference still resolves.
- **Enhances**: PAT-087 (reframe-before-design) — premise verification is the upstream step that tells you *which* fork to reframe.
- **Synergies**: PAT-118 (diagnose-gap-nature-before-mechanism) — both verify against primary sources before committing, different scope.
- **Conflicts**: None.
- **Alternatives**: Trust-then-fix-at-review (the failure mode this prevents).

## Consequences
- **Benefits**: Stale premises caught at Analysis (cheapest correction point); design built on verified ground; reframes surface as findings the user can redirect before any write; turns a risky change into a provably-safe one.
- **Tradeoffs**: A few extra grep/read operations at Analysis before design begins.
- **Risks**: Over-verification of trivially-stable premises adds noise — gated by the "load-bearing premise" + "plausible drift" filter.

## Examples

### Before/After Comparison

**Without Pattern**: ISS names "use PAT-115 as carrier, place in audit.md." Designer builds on both as given → discovers at Build/Validate that audit.md doesn't exist and PAT-115 is a different pattern → rework.

**With Pattern (Sprint 092 ISS-195)**: Designer enumerates the two premises (placement, pattern carrier), greps primary sources, finds both stale, reframes the design (SKILL.md home + cite PAT-112/098/113) *before* writing — zero rework, both forks reversed at Analysis.

### Application Example

Sprint 092 ISS-201: the issue's trim proposal hinged on the premise "these sections have live cross-references." Grep against primary sources showed the sole live anchor was one BOOTSTRAP line and the compaction hook was self-sufficient — the verification *was* what made the trim safe to lock at Analysis.

## Validation
- **Success Indicator**: Every concrete artifact/ID/fork the issue names has been checked against a primary source before design is locked; any drift is reframed and recorded as a finding before approval-to-proceed.
- **Edge Cases**: Issue created in the same conversation as execution (drift window ~0 — lightweight check suffices); issue with no concrete premises (nothing to verify — skip).

## Notes and Observations

This pattern is the methodology-practice counterpart of the recurring user behavior BI-203 ("insists on verifying premises before locking direction, even mid-flow"). It targets the issue document's *own* stated premises — the internal scaffolding — which is what distinguishes it from the external-claim and current-behavior verification disciplines. Pairs naturally with the findings-before-edits protocol: a reversed premise is exactly the kind of finding to surface before proposing a write.
