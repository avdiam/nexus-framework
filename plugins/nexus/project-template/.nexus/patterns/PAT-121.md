# PAT-121: Match Remedy Form to Failure Cause

*Version: 1.0.0 | Date: 2026-06-02 | Sprint: 095*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-06-02

## Problem

When designing the fix for a recurring or systemic failure, the remedy's *form* is often chosen by convenience (fold it into an existing step, add a "must remember to check" note, widen an adversarial sweep) rather than by what the failure's *cause* actually requires. A remedy whose form does not match the cause leaves the failure mode reachable — the check can be skipped, rationalized away, or simply forgotten, exactly as the original failure was.

## Context
- **Use When**: Designing a remedy for a failure that has happened before or could recur; choosing where/how to encode a new check, gate, or safeguard; deciding between a standalone deterministic step vs. folding a check into an existing judgment step.
- **Not When**: One-off fixes with no recurrence risk; failures whose cause is a simple typo or value error (the form is obvious); when the cheapest correct form is also the convenient one (no tension to resolve).
- **Prerequisites**: A diagnosed failure *cause* (not just a symptom) — you must know *why* the failure was reachable to match the remedy form to it.

## Solution

Before encoding a remedy, name the failure's cause-class, then choose the remedy form that structurally closes that class:

| Failure cause | Remedy form that matches |
|---|---|
| Implicit assumption ("a later phase will handle it") | An **explicit, deterministic checkpoint** that must produce output — not a judgment step |
| Incomplete manual enumeration (missed a surface) | An **executable predicate** over the whole item-class (grep/test), not a re-read of a list |
| Easy-to-skip soft imperative | A **hard gate** with a mandatory marker, not a "should" note |
| Ambiguity / drift | A **single source of truth** that consumers reference, not parallel copies |

### Implementation
1. State the cause in one sentence: "this failed because ___."
2. Classify the cause: implicit-assumption / incomplete-enumeration / skippable-imperative / ambiguity / other.
3. Pick the remedy form whose structure makes that cause-class unreachable (see table).
4. Reject convenient-but-mismatched forms explicitly — if you're folding a check into an existing judgment step, confirm the cause was *not* "a judgment step got skipped/rationalized."

## Rationale

A remedy only removes a failure mode if its form is incompatible with the mechanism that produced the failure. An implicit-assumption failure cannot be cured by another implicit step — it requires an explicit, output-producing checkpoint, because the cure must be impossible to satisfy without actually doing the work. ISS-203's origin failure (ISS-189: "Phase D will handle the dangling deferral") was an unverified implicit assumption; the fix was a standalone deterministic `§POST-TYPE: Deferral-Target Validity` step rather than folding the check into Decision Drift or Adversarial Review, precisely because those judgment steps are where such a check would again be rationalized away.

- **Theoretical Basis**: A control is only as strong as its weakest skip-path; matching form to cause eliminates the skip-path rather than adding a parallel one.
- **Empirical Evidence**: ISS-203 (Sprint 095) — standalone checkpoint chosen over fold-in; paired with PAT-098's executable-predicate variant for the enumeration cause-class.
- **Design Decisions**: Prefer deterministic/executable forms for assumption- and enumeration-class causes over judgment-embedded forms.

## Anti-Patterns

- **Anti-Pattern 1**: Folding a safeguard into an existing judgment/adversarial step for convenience.
  - **Why Wrong**: If the failure's cause was "a judgment step was skipped," the remedy inherits the same skip-path and the failure remains reachable.
  - **Example**: Curing a forgotten cross-surface update by adding "remember to check all surfaces" to a review checklist — instead of a grep that fails loudly when a surface is missed.
- **Anti-Pattern 2**: Choosing remedy form before diagnosing the cause.
  - **Why Wrong**: Without the cause-class, form selection defaults to convenience, not fit.

## Consequences
- **Benefits**: Remedies actually close the failure mode they target; fewer re-reproductions of "fixed" failures.
- **Tradeoffs**: A matched remedy (standalone deterministic step, executable test) is often more verbose/structural than a convenient note — slightly higher upfront cost.
- **Risks**: Over-application could add ceremony to trivial fixes — gated by the Not-When (recurrence risk required).

## Examples

### Before/After Comparison
**Without Pattern**: Dangling-deferral failure "fixed" by adding it to an adversarial-review must-find list → recurs because the list item is skipped under context pressure.
**With Pattern**: Same failure fixed with a standalone deterministic `§POST-TYPE` checkpoint that must emit a validity verdict → cannot complete the phase without performing the check.

### Application Example
ISS-203 (Sprint 095): origin cause = implicit assumption. Remedy form chosen = explicit deterministic checkpoint (not fold-in). Result: the check is structurally unskippable within the workflow.
