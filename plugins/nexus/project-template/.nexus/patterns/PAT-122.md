# PAT-122: Honest Green Across All Branches and Environments

*Version: 1.0.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-06-04

## Problem

A test or check suite reports "green" while one or more of its branches never actually executed, or while its pass depends on environment state the author happened to have provisioned. Both produce a false sense of validation: a conditional branch (degrade path, error handler, fail-open fallback) that the author's run never entered ships its assertions untested, and a "green" that depends on a hand-installed dependency or a CLI tool present only on the author's machine collapses the moment the suite runs in a clean environment. The suite's own report cannot distinguish "all paths verified everywhere" from "the one path I happened to hit, on the one machine I happened to use."

## Context
- **Use When**:
  - "Before declaring a test suite, harness, or check 'green' / passing — especially one with conditional branches (degrade, error, fail-open, skip paths)"
  - "When a test's outcome could depend on environment state (installed dependencies, available CLI tools, interpreter version, OS)"
  - "When authoring or reviewing fail-open / graceful-degradation logic, where the degrade branch is exactly the one a healthy author environment never triggers"
  - "When inheriting or re-running a suite that was previously declared green in a different environment than the current one"
- **Not When**:
  - "Trivial single-branch checks with no conditional logic and no environment dependency"
  - "Pure unit tests over deterministic in-process logic with no I/O or external tooling"
- **Prerequisites**: The suite must have observable branch outcomes (exit codes, recorded actuals) and a way to run it in a clean/fresh environment.

## Solution

Treat "green" as a claim that must be earned on two axes, not a single suite-reported boolean:

1. **Branch completeness** — Enumerate every branch the suite *can* take, including degrade, error, and fail-open paths. A branch whose assertions never executed is untested even if the overall run reports pass. Force-exercise each branch (provision the failing precondition, mock the missing dependency, induce the error) before claiming the branch is validated.
2. **Environment honesty** — Run the suite in a clean environment that lacks any dependency you hand-provisioned during development. If "green" disappears, the green was contingent, not real. Either make the suite genuinely environment-independent, or assert the *honest* contract (e.g., "fails open with exit 0 when dependency absent") so the clean-environment outcome is itself the expected green.

### Implementation
- Before declaring green: list branches → for each, confirm it was actually entered in at least one run (check recorded actuals / exit codes, not just the summary line).
- For any branch not yet entered, construct the input/environment that forces it, run, and assert.
- Re-run the whole suite once in a fresh environment (no author-provisioned deps). Reconcile any divergence by fixing either the suite or the asserted contract — never by re-provisioning the environment to restore green.
- When the correct behavior IS degradation (fail-open), make the degrade branch's assertion encode that contract so a dependency-less environment passes durably.

## Rationale
- **Theoretical Basis**: A test exercises only the code paths its inputs and environment select. Coverage is a property of *executed* paths, not of *written* assertions — unexecuted assertions carry zero evidence. Likewise, a result is only as portable as the environment it secretly depends on.
- **Empirical Evidence**: ISS-086 (Sprint 096) shipped a hook-test harness reported as "13/13 green." Build ran it only in a PyYAML-provisioned environment, so the BLOCK branch ran and the degrade branch never did; its assertion was wrong but untested. A fresh Validate session with neither jq nor PyYAML took the degrade/fail-open branch and went RED 12/1. The defect was invisible until the suite ran in an environment the author hadn't provisioned.
- **Design Decisions**: Pairing the two axes is deliberate — environment differences are the most common *cause* of an unexecuted branch, so "exercise every branch" and "be environment-honest" reinforce each other.

## Anti-Patterns
- **Anti-Pattern 1**: Declaring green from the summary line without checking which branches actually ran.
  - **Why Wrong**: The summary aggregates only executed assertions; a skipped branch silently contributes nothing and looks identical to a passing one.
  - **Example**: "13/13 passed" where 1 assertion belonged to a degrade branch that was never entered.
- **Anti-Pattern 2**: Restoring a broken green by re-provisioning the environment (`pip install ...`) instead of fixing the suite or contract.
  - **Why Wrong**: The install is ephemeral and machine-local; it masks both the test defect and the real degradation the next clean environment will hit.
  - **Example**: Re-installing a dependency to turn red back to green, then shipping — the next fresh checkout fails identically.

## Consequences
- **Benefits**: Catches untested degrade/error paths and environment-contingent results before they reach users; produces suites that are durably green in any environment.
- **Tradeoffs**: Requires extra effort to force-exercise branches and to run in a clean environment; slower than trusting the summary line.
- **Risks**: Over-mocking to force a branch can make the branch's assertion drift from real behavior — assert the genuine contract, not a contrived one.

## Examples

### Before/After Comparison
**Without Pattern**: Harness reports 13/13 green on the author's machine (deps provisioned); ships; fails 12/1 in CI / fresh checkout because the degrade branch was never exercised and its assertion was wrong.
**With Pattern**: Author enumerates branches, force-runs the degrade path, finds the wrong assertion, fixes it to assert the true fail-open contract; suite is durably 12/12 green with or without the optional dependency.

### Application Example
A hook fails open (exit 0) when `jq` is absent. The author has `jq` installed, so the fail-open branch never runs. Applying the pattern: temporarily remove `jq` from PATH (or run in a clean container), confirm the hook exits 0, and write the degrade-branch assertion to expect exit 0 — making "no jq" a passing, expected state rather than a hidden red.

## Validation
- **Success Indicator**: Every branch has at least one run with recorded actuals, AND a fresh-environment run reproduces green without any author-provisioned dependency.
- **Edge Cases**: Branches gated on rare external failures (network, disk-full) may need fault injection; if genuinely infeasible to exercise, document the unexecuted branch explicitly rather than counting it as green.
