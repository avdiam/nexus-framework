# PAT-124: verify-relocation-target
*Version: 1.0.0 | Date: 2026-06-07 | Sprint: 098*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-06-07

## Problem
Content relocation and work-deferral both **write into a named target** — a file, section, issue, reference, pattern, or future shared home. Authors routinely treat that target as given: they defer "to Phase D", "to ISS-X", or "into `references/common.md`" without confirming the target exists and is live. When the target is archived, resolved, retired, renamed, wrong-scoped, or not-yet-created, the relocated/deferred content is **silently orphaned** — and the gap is invisible until someone later looks for work that was nominally "handled."

## Context
- **Use When**:
  - Relocating content into a `references/` file, shared module, or another skill during a refactor or externalization
  - Deferring work to a named target (a later phase, follow-up issue, future sprint, section) in research deliverables or Build/Validate deviations
  - An audit or synthesis recommends moving content into a target that does not yet exist (verify-or-create-target-first)
  - Citing or pointing to a pattern/issue/section by ID — confirm the referent is still active, not retired/archived/renamed
  - CAUTION: skip for trivial in-file moves where the target is self-evidently present and live
- **Not When**:
  - Trivial in-file moves with a self-evidently present, live destination
  - The target was just created/verified earlier in the same conversation
- **Prerequisites**: the target is namable (path, ISS-ID, section anchor, pattern-ID) and its registry/file/lifecycle state is checkable.

## Solution
Before committing any relocation or deferral, treat the named target as a **hypothesis** and verify **two** things:
1. **EXISTENCE** — the target file/section/issue/reference actually exists; OR, if it is a planned new home, that creating it is an enumerated step of the *current* plan.
2. **LIFECYCLE STATE** — the target is **live**: active issue (not Resolved/Rejected/archived), current file (not deprecated/retired), in-scope phase (the named phase's Files-Affected actually includes this artifact), active pattern (not retired).

Only after **both** pass, commit the move. If the target is a not-yet-existing shared home, the verification resolves to "**create-target-first** within this plan," not "defer blindly."

### Implementation
1. **Name the target explicitly** (path, ISS-ID, section anchor, pattern-ID).
2. **Existence check** — Glob/Read the file, grep the section anchor, look up the ISS/PAT in its registry. For a planned new home, confirm its creation is an enumerated step of the current plan.
3. **Lifecycle check** — Is the ISS active (not Resolved/Rejected/archived)? Is the file current (not deprecated)? Is the named phase's Files-Affected actually inclusive of this artifact (cf. Build §POST-TYPE Deferral-Target Validity)? Is the pattern active (not retired)?
4. **Disposition** — On pass → commit with the verified target. On fail → re-target, fold the artifact into a live target's scope, create the target first, or track it explicitly (new ISS / hand-off).

### Quick Reference
`Name target → exists? (or create-in-plan?) → live? (not resolved/archived/retired/out-of-scope) → both pass → commit; else re-target / fold / create-first / track-explicitly.`

## Historical Context
Origin: **ISS-205 (Sprint 097)** framework-audit playbook **Lesson 5** — the CLAUDE.md pilot nearly deferred content into **ISS-199** (Resolved/archived) and preserved a **stale PAT-115 reference** (retired Sprint 093). Reinforced by **ISS-206 (Sprint 098)**: the methodology/agent audit's externalization recommendations defer into `references/methodology-common.md` + `references/*.md` targets that **do not yet exist**, making "verify-or-create-target-first" a live guard. Operationally related to the Build §POST-TYPE **Deferral-Target Validity** check (ISS-189 SI-2 dangling-deferral, Sprint 094), which realizes the lifecycle-check for intra-plan phase targets.

## Rationale
- **Theoretical Basis**: A named target is a reference, and a reference is only as good as the referent's existence and liveness. Deferral and relocation are *writes into a referent*; an unverified referent is an unverified write.
- **Empirical Evidence**: ISS-205 near-miss (ISS-199 archived); stale PAT-115 reference (retired Sprint 093); ISS-189 SI-2 dangling-deferral (deferred to "Phase D," which rebuilt a *different* file, silently losing the cleanup).
- **Design Decisions**: Two checks (existence **and** lifecycle), because existence alone misses the archived-but-present case and the wrong-scope case — the most dangerous failures look present.

## Anti-Patterns
- **Anti-Pattern 1 — Defer-and-forget**: writing "deferred to Phase D" / "handled in ISS-X" without checking Phase D's scope includes the artifact or ISS-X is still open.
  - **Why Wrong**: the deferral reads as resolved but the work is orphaned.
  - **Example**: ISS-205 pilot nearly deferred into ISS-199, already Resolved/archived.
- **Anti-Pattern 2 — Point-at-a-corpse reference**: citing a pattern/section/issue by ID that has since been retired/renamed.
  - **Why Wrong**: the pointer resolves to nothing, or silently drifts.
  - **Example**: preserving a stale PAT-115 reference retired Sprint 093.
- **Anti-Pattern 3 — Relocate-into-the-void**: an audit recommends "move X into `references/common.md`" that doesn't exist, and execution treats the move as if the home were already there.
  - **Why Wrong**: the move has no destination; the recommendation must include creating the target first.

- **Conflicts**: none

## Consequences
- **Benefits**: prevents silent work-loss on deferral; keeps cross-references resolvable; converts blind deferral into a verified hand-off.
- **Tradeoffs**: a small verification step at each relocation/deferral moment.
- **Risks**: over-applied to trivial in-file moves it becomes ceremony — hence the CAUTION in Context.

## Examples

### Before/After Comparison
**Without Pattern**: "Deferred §3.5 cleanup to Phase D." Phase D rebuilt a different file; the cleanup was silently lost, caught only at Validate (ISS-189 SI-2).
**With Pattern**: "Deferred §3.5 cleanup to Phase D — verified Phase D Files-Affected includes this file ✓" — or, on fail, "Phase D scope excludes it → re-targeted to new ISS-XXX."

### Application Example
ISS-206 externalization recommendations defer content into `references/methodology-common.md` (does not exist yet). PAT-124 resolves the deferral to "the execution issue must **create** the target before relocating," and the recommendation is logged with that precondition rather than as a blind move.

## Validation
- **Success Indicator**: every deferral/relocation in a deliverable names a target that a reader can open and find live; zero dangling-deferral findings at Validate.
- **Edge Cases**: forward targets with no enumerable scope yet ("next sprint", not-yet-created issue) → cannot fully verify; track explicitly so the artifact isn't lost (mirrors Build §POST-TYPE "cannot verify" verdict).

## Notes and Observations
The shared meta-principle with PAT-119 ("a named entity is a hypothesis until verified") is real but the two apply to opposite directions at different moments: PAT-119 verifies the *inbound* premises an issue hands you (Analysis); PAT-124 verifies the *outbound* target you are about to write into (any relocation/deferral moment — Build, research synthesis, Validate, closure). Kept separate to preserve PAT-119's Analysis-phase premise-drift identity.
