# PAT-126: Calibrate-Then-Schema-Enforce
*Version: 1.1.0 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: methodology
- **Status**: active
- **Created**: 2026-06-12

## Problem

Multi-agent collection via prose-template instruction is structurally unreliable. Agents may wrap JSON in prose, substitute estimated numerics for counts, or add unsolicited status lines — all while technically "following instructions." Calibrating the dispatch prompt before the fan-out catches these prompt-obedience failures, but without mechanical enforcement the fan-out itself still depends on per-agent compliance. A calibration-only approach reduces failures; schema enforcement eliminates the failure class entirely at the tool layer. The two problems (prompt ambiguity vs. structural contract enforcement) require different remedies, and deploying only one leaves the other open.

## Context
- **Use When**:
  - Dispatching N≥5 parallel agents where structural contract compliance is required and cannot be manually reviewed per-agent
  - Any multi-agent result collection where prose-template instructions alone have proven unreliable (calibration catches this; a prior calibration failure is the highest-signal trigger)
  - Fan-out workflows where result schemas are fixed (audit digests, classifier outputs, structured evaluations) and non-conforming results must not propagate to main-context consolidation
  - When coverage proof is required — the deterministic-script reconciliation step integrates naturally alongside schema-enforced collection
  - CAUTION: calibration requires a representative group; if all groups are structurally identical, one calibration pass is sufficient before the full fan-out
- **Not When**: Small fan-outs (N<5 agents) where per-agent review is practical; or when the result format is free-text/prose where schema enforcement would be over-constraining
- **Prerequisites**: A fan-out task where (a) results have a fixed structure expressible as a JSON schema, and (b) a Workflow or equivalent tool-layer mechanism supports schema-enforced agent calls with automatic retry on non-conformance
- **⚠️ PLATFORM DEPENDENCY (Sprint 109 pattern-maintenance)**: Phase 2 (ENFORCE) is currently **unexecutable in this harness** — the `Workflow` tool that supplied tool-layer schema enforcement is ABSENT from the tool list (loaded and deferred alike); it was live at Sprint 103 / ISS-219. This is the same vanished-external-capability class as SEED-031 / ISS-238. Phase 1 (CALIBRATE) and the deterministic reconciliation step remain fully executable. The pattern's zero applications are explained by this dependency, NOT by low value — do not read the usage count as a value signal until the dependency is re-verified.

## Solution

Deploy a two-phase harness:

**Phase 1 — CALIBRATE (plain-agent pass)**: Run one plain Agent call on a representative group before the full fan-out. Do NOT use schema enforcement here — the calibration's purpose is to surface what the current prompt produces naturally. Review the calibration output for:
- Packaging deviations (prose wrapping JSON, status-line additions, markdown fencing)
- Estimation instead of counting (numeric fields approximated rather than mechanically measured)
- Spurious or missing fields
- Criterion interpretation mismatches

Amend the dispatch prompt for each failure found. Gate: do not authorize the fan-out until the calibration output passes schema validation AND at least one findings spot-check.

**Phase 2 — ENFORCE (schema-enforced fan-out)**: For the full fan-out, use schema-enforced agent calls (Workflow `agent()` with a JSON schema argument, or equivalent). Tool-layer schema validation retries non-conforming responses automatically before they reach the main context. Human review becomes a one-time gate (calibration), not a per-agent burden (fan-out).

**Mechanical reconciliation** (independent): After collection, run a deterministic script (not an LLM) over all results vs. a frozen manifest to close the coverage gap. The script catches silently-dropped results that schema enforcement cannot detect (a schema-valid response that covers the wrong targets).

### Implementation
1. Generate frozen manifest (what the fan-out should cover, mechanically derived).
2. Run calibration on 1 representative group (plain Agent call, no schema enforcement). Review and amend prompt.
3. Gate: schema validation + spot-check pass on calibration output before authorizing fan-out.
4. Dispatch fan-out via schema-enforced Workflow (all remaining groups in parallel).
5. Post-collection: run deterministic reconciliation script (results vs. frozen manifest).

### Quick Reference
| Phase | Mechanism | Purpose |
|-------|-----------|---------|
| Calibrate | Plain Agent call (1 group) | Surface prompt-obedience failures |
| Amend | Update dispatch prompt | Fix failures before scale |
| Gate | Schema validate + spot-check | Authorize fan-out |
| Enforce | Schema-enforced Workflow | Eliminate structural contract failures at tool layer |
| Reconcile | Deterministic script | Close coverage gap |

## Historical Context
Evolved from the pilot-then-batch arc applied to multi-agent collection (formerly PAT-123; retired as framework-subsumed, its guidance now carried by the `pilot_before_batch` preference). That discipline validates WHAT the procedure produces (content calibration, playbook derivation); this pattern validates and enforces HOW the agent returns results (structural contract enforcement). Both fire on the same fan-out, at different levels.

## Rationale
- **Theoretical Basis**: Prose-template contracts rely on prompt obedience — the agent's willingness to follow formatting instructions. Tool-layer schema contracts enforce at the JSON/schema validation layer — the model cannot return a response that fails the schema without an automatic retry. These operate at different levels of the stack, and failures at one level are not caught by the other.
- **Empirical Evidence**: ISS-207 Sprint 102 — calibration (plain Agent, G1) exposed two failures: the agent packaged the response with prose wrapping and estimated line counts (~10-20% under actual). The fan-out dispatch prompt was amended for both. The schema-enforced Workflow fan-out (7 groups) returned zero conformance errors. In the same calibration, the agent violated the literal "return only JSON" instruction despite it appearing verbatim in the prompt — only tool-layer enforcement prevented this at scale.
- **Design Decisions**: Calibration stays plain (no schema enforcement) precisely so it surfaces what the current prompt produces naturally. Schema enforcement at calibration would mask exactly the failures calibration is meant to find.

## Anti-Patterns

- **Anti-Pattern 1: Schema-Enforce Without Calibrating**
  - **Why Wrong**: Schema enforcement prevents structural contract violations, but it cannot fix prompt ambiguity. If the dispatch prompt is unclear about criteria (interpretation, measurement method, edge cases), schema-valid responses can still contain systematically wrong values.
  - **Example**: Schema enforcement produced zero conformance errors in ISS-207, but criterion ambiguity still caused a 9d third_person miscount — schema enforcement and calibration target different failure classes.

- **Anti-Pattern 2: Calibrate Without Schema-Enforcing the Fan-Out**
  - **Why Wrong**: Calibration catches failures for that one agent in that one context window. At scale, other agents may behave differently. Without enforcement, the fan-out falls back to prompt-obedience — the same failure mode calibration was designed to detect.
  - **Example**: ISS-207 calibration agent violated "JSON only" despite literal instruction; only Workflow schema enforcement prevented this from recurring across 7 fan-out agents.

- **Anti-Pattern 3: LLM-Based Reconciliation**
  - **Why Wrong**: Coverage proof is a presence/completeness check, not a semantic task. An LLM reconciler introduces a new judgment layer with its own failure modes. A deterministic script running over frozen-manifest IDs is cheaper, more reliable, and produces an auditable diff.

- **Enhances**: PAT-095 (isolated-context-advantage — defines result contracts precisely; this operationalizes contract enforcement), PAT-125 (negative-space-verification — schema enforcement ensures coverage; negative-space sampling handles validity)
- **Conflicts**: []
- **Alternatives**: Manual per-agent result review (eliminates conformance issues but O(N) human cost); prose-template only (simplest, highest conformance risk at scale)

## Consequences
- **Benefits**: Eliminates structural contract failures at scale; calibration surfaces prompt ambiguity before it compounds across N agents; human gate runs once, not N times; mechanical reconciliation provides auditable coverage proof
- **Tradeoffs**: Adds a calibration step before the fan-out (time cost, one extra agent spawn); requires a schema expressible as JSON Schema or equivalent; Workflow/schema infrastructure must support automatic retry
- **Risks**: Calibration may not expose all failure modes if the calibration group is unrepresentative; schema enforcement catches structural violations but not value-level misclassification (that's PAT-125)

## Examples

### Before/After Comparison
**Without Pattern**: Fan-out dispatched directly with prose-template instructions. Some agents wrap responses in prose. Some estimate line counts. One adds a status line. Results require per-agent cleanup in main context before consolidation. Coverage must be tracked manually.

**With Pattern**: Calibration run exposes prose-wrapping and numeric-estimation failures. Prompt amended. Schema-enforced Workflow fan-out: all 7 groups return conforming JSON on first response. Mechanical script reconciles 44/44 coverage against frozen manifest. Main context receives clean results.

### Application Example
ISS-207 Sprint 102 fan-out: calibration (G1 plain agent) caught packaging deviation and estimation habit; both amended. Schema-enforced Workflow (wf_505034c0-c37, 7 groups): zero conformance errors, 724K tokens, ~11 min. Python reconciliation: 44/44 exact, zero drift. Zero per-agent manual conformance checks required.

## Validation
- **Success Indicator**: Calibration output produces at least one failure that required a prompt amendment (if calibration found nothing wrong, the prompt was already good, or the calibration group was unrepresentative); fan-out conformance errors = 0; reconciliation reports exact coverage
- **Edge Cases**: If calibration group is the lowest-risk group, it may not surface failures that appear in higher-risk groups — choose the highest-risk/most-complex group for calibration, per the `pilot_before_batch` preference (formerly PAT-123)

## Notes and Observations
The calibration/enforcement split maps to a well-known testing principle: test the thing you're shipping with the mechanism that catches the failure you care about. Calibration is a manual test under real conditions; schema enforcement is a contract check at the API level. Neither replaces the other.
