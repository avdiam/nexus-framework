# PAT-127: fan-out-batch-economics

*Version: 1.0.0 | Date: 2026-06-14 | Sprint: 103*

## Metadata
- **Type**: methodology
- **Status**: active
- **Created**: 2026-06-14

## Problem

Sub-agent / Workflow fan-out cost is dominated by **fixed per-spawn overhead** (measured ~31K tokens per agent call in NEXUS), not by the size of the task each agent performs. The intuitive cost model — "cost scales with how much work each agent does" — is wrong, so the naive architecture (one agent per micro-unit of work) silently multiplies the fixed overhead by the unit count and produces a prohibitive bill. A corpus sweep designed this way can balloon to tens of millions of tokens before anyone notices the overhead, not the task, is the driver.

## Context
- **Use When**: Designing any sub-agent or Workflow fan-out where work decomposes into many small, independent units (per-skill, per-file, per-query, per-target decisions); at a cost fork where the default instinct is one-agent-per-unit; planning a corpus-scale measurement, audit, or transformation sweep.
- **Not When**: The per-unit task is itself large (each unit already saturates an agent's useful context — overhead is then a small fraction, batching buys little); units have genuine cross-dependencies that forbid co-locating them in one call; N is small enough (≤ a handful) that total overhead is negligible.
- **Prerequisites**: Units of work are independent and uniform enough to batch many into a single agent prompt with a structured (e.g. schema-forced) return.

## Solution

Before scaling a fan-out, **batch many micro-decisions into each agent call** rather than spawning one agent per micro-unit. Treat units-per-call — not trials or agent count — as the primary cost lever. Concretely:

### Implementation
1. **Estimate the fixed overhead first.** Run one representative agent call, read its `total_tokens`, and identify how much is spawn/context overhead vs. task work. If overhead dominates, batching is the lever.
2. **Pack the call.** Have each agent process K units per invocation (K decisions, K targets, K queries) with a structured/schema-forced output enumerating all K results — rather than K separate agents.
3. **Cost-model on calls, not units.** Total ≈ (call_count) × (per_call_overhead + per_unit_work × K). Raising K amortizes the fixed overhead across more useful work; raising trials/agent-count multiplies it.
4. **Scale breadth via more units-per-call, depth via more calls** — choose deliberately. When you need more samples cheaply, add units to existing calls; only add calls when you genuinely need independent draws.

## Rationale

The wisdom: **a fixed cost is amortized by maximizing useful work per occurrence, not by shrinking each occurrence.** Per-spawn overhead (model load, system prompt, tool schemas, context priming) is paid once per agent regardless of how trivial the task — so the cost-minimizing move is to do more real work between spawns, not to make each spawn smaller.

- **Theoretical Basis**: Fixed-cost amortization — when a per-event fixed cost dominates a variable cost, throughput-per-event is the optimization target.
- **Empirical Evidence**: ISS-217 (Sprint 103) trigger-accuracy measurement. Naive design (1 agent per query: ~19 skills × 3 variants × ~10 queries × 5 trials ≈ 2,850 calls) projected ≈ **88M tokens** — prohibitive. Batched design (6 decisions/call) → ~5.3K/decision, a **6× reduction**; the actual scale run executed in 120 calls = **4.04M tokens**. Confirmed at pilot (Conv 3) and scale (Conv 4).

## Anti-Patterns
- **Anti-Pattern 1**: One agent per micro-unit at scale.
  - **Why Wrong**: Multiplies the fixed per-spawn overhead by the unit count; the overhead (not the task) becomes the bill.
  - **Example**: Spawning 2,850 agents to make 2,850 yes/no routing decisions (~88M tokens) instead of 120 batched calls (~4M).
- **Anti-Pattern 2**: Optimizing the wrong lever — trimming each agent's task or model tier while leaving the call count untouched.
  - **Why Wrong**: Per-call overhead is roughly constant; shrinking already-small tasks barely moves total cost while batching would cut it manyfold.

## Relationships
- **Requires**: []
- **Enhances**: None
- **Conflicts**: []
- **Alternatives**: Direct (non-agent) tooling when the work fits the main context (see `prefer_direct_tools` / `llm_over_tools` preferences) — no fan-out at all is the cheapest fan-out.

## Consequences
- **Benefits**: Order-of-magnitude token reduction on corpus-scale fan-outs; makes otherwise-prohibitive measurement/audit sweeps affordable; cost becomes predictable from call count.
- **Tradeoffs**: Batched prompts are larger and need structured outputs to keep per-unit results separable; a single failed call loses K units' work (mitigate with moderate K and idempotent retries).
- **Risks**: Over-packing a call can exceed useful context and degrade per-unit quality — size K to stay within the agent's reliable working set.

## Examples

### Before/After Comparison
**Without Pattern**: ISS-217 naive estimate — one agent per query × variants × trials ≈ 2,850 calls ≈ 88M tokens. Abandoned as infeasible.
**With Pattern**: 6 decisions per call, modest trials, representative subset → 120 calls / 4.04M tokens for the same verdict. 6× per-decision reduction, ~20× total reduction vs. naive.

## Validation
- **Success Indicator**: Projected fan-out cost drops by a multiple roughly equal to the batch factor K after re-architecting from per-unit to per-call; measured per-call token cost is dominated by overhead, confirming the model.
- **Edge Cases**: Large per-unit tasks (overhead is already a small fraction — batching buys little); cross-dependent units that cannot share a call.
