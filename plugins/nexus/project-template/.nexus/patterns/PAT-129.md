# PAT-129: additive-diff-proof

*Version: 1.0.0 | Date: 2026-06-14 | Sprint: 103*

## Metadata
- **Type**: methodology
- **Status**: active
- **Created**: 2026-06-14

## Problem

A purely mechanical or structural change — closing code fences, reformatting, reordering imports, renaming a symbol, a bulk find-replace — is defined by a **token-class invariant**: only a specific class of lines should change, and no content should be lost. Verifying such a change by re-reading each edit for authorial intent is slow, subjective, and weakest exactly where it matters: a *compensating* error (e.g. two mis-paired fences that still leave the count even, a rename that also clobbers a nearby token) hides from intent-reading and from coarse aggregate checks alike. An even count, a passing parse, "it looks right" — these certify the surface, not the invariant.

## Context
- **Use When**: Verifying a purely-mechanical or structural fix at Build or Validate (fence balancing, whitespace/format normalization, import reordering, mechanical rename, bulk find-replace, generated-code regeneration); proving a change is additive-only or confined to one intended token-class; independently re-deriving a Build's structural claim at adversarial review.
- **Not When**: The change alters logic, behavior, or content — there the token-class invariant doesn't hold and intent-reading / functional tests are required; trivial single-line edits where the diff is self-evidently the whole change.
- **Prerequisites**: The change is under version control (diffable against a known baseline commit) and is genuinely defined by a token-class invariant you can state in advance.

## Solution

Verify the change by **classifying the diff's changed-line set**, not by re-reading intent. State the invariant up front (which token-class may change; whether any content may be removed), then prove the diff satisfies it mechanically:

### Implementation
1. **State the invariant.** E.g. "only ` ``` ` fence lines and version-header lines may be added; zero content lines removed; zero reorders."
2. **Scan the diff against a baseline commit.** Use `git diff`/`numstat` + an `awk`/`grep` classifier over added and removed lines: assert every added line matches the intended class, every removed line matches the allowed-removal class (often empty), and counts reconcile per file.
3. **Reconcile counts per file**, not just globally — per-file added/removed must match the expected (e.g. closes+1 added / 1 deleted for an additive fence-fix with a version swap). Global totals can mask a file that gained and another that lost.
4. **Pair with a targeted render/spot-check of the highest-risk artifacts.** A clean diff-class proves no *unintended class* changed; spot-rendering the worst cases proves the intended change achieved its *effect* (e.g. directive prose now renders outside the block). Both together close the gap an even count leaves open.

## Rationale

The wisdom: **for a change defined by a structural invariant, the proof is structural — assert the diff touches only the intended token-class with no content loss, and let structure verify structure.** Re-reading intent asks "did the author mean this?"; diff-class classification asks "does the change set provably belong to the allowed class?" The latter is mechanical, independent of the author's reasoning, and immune to compensating errors that preserve a surface aggregate. An even count is *necessary but not sufficient*; the additive/class-confined diff is the sufficient condition.

- **Theoretical Basis**: Invariant-based verification — when correctness is expressible as a closed property over the change set, checking the property dominates inspecting each element.
- **Empirical Evidence**: ISS-214 (Sprint 103) — 18 closing fences across 7 skills. Build proved SC-02 ("diff shows only added ` ``` ` lines") via an additive-only git diff. Independent Validate (Conv 9) re-derived it via an `awk` scan of commit `b3ecaaf7`: 18 fence lines + 7 version swaps added, **zero** non-fence/non-version content added, **zero** content removed; per-file numstat matched (closes+1 added / 1 deleted). The proof was fully reproducible by a reviewer with no knowledge of Build's reasoning.

## Anti-Patterns
- **Anti-Pattern 1**: Trusting an even/aggregate count as proof.
  - **Why Wrong**: A compensating mis-pairing keeps the count even (or the parse passing) while the structure is wrong. The aggregate certifies coverage, not correctness.
  - **Example**: Fence count is even, but two fences are mis-paired against each other — the swallowed-prose bug persists despite the "balanced" count.
- **Anti-Pattern 2**: Re-reading every changed line for intent on a bulk mechanical edit.
  - **Why Wrong**: Slow, subjective, and blind to compensating errors; replaces a mechanical proof with a fallible human pass exactly where mechanical proof is strongest.
- **Anti-Pattern 3**: Diff-class proof *without* an effect spot-check.
  - **Why Wrong**: Proves no unintended class changed, but not that the intended change produced its effect — pair the two.

- **Requires**: Version control (diffable baseline).

## Consequences
- **Benefits**: Fast, mechanical, reproducible proof of a structural change; independent of the author's reasoning (ideal for adversarial Validate); catches compensating errors that aggregate counts and intent-reading both miss.
- **Tradeoffs**: Requires stating the invariant precisely up front and a small amount of diff-scripting (awk/grep over the diff); only applies to changes genuinely defined by a token-class invariant.
- **Risks**: Mis-stating the invariant (too permissive) lets unintended changes pass — state the allowed class tightly; skipping the effect spot-check leaves the "did it work" question open.

## Examples

### Before/After Comparison
**Without Pattern**: Reviewer re-reads 18 fence insertions across 7 files for intent, eyeballs the fence counts as even, and signs off — a compensating mis-pair could survive.
**With Pattern**: Reviewer runs an `awk` classifier over the commit diff: asserts all added lines are ` ``` ` or version-header lines, zero content removed, per-file numstat reconciles — then spot-renders the highest-fence-count files to confirm prose renders outside blocks. Both pass independently of Build's claims.

## Validation
- **Success Indicator**: A diff-classifier script over the change set returns "all changed lines ∈ intended class, zero disallowed removals, per-file counts reconcile," and a spot-render of the riskiest artifacts confirms the intended effect.
- **Edge Cases**: Changes that mix a mechanical edit with a content edit — split them into separate commits so the mechanical part remains diff-class-provable.
