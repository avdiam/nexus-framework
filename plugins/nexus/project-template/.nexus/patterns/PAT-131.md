# PAT-131: Tag by Application-Moment, Not Subject
*Version: 1.0.0 | Date: 2026-06-18 | Sprint: 105*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-06-18

## Problem
A classification or routing field whose job is "surface this item *when* it's relevant" — `use_when`, `trigger`, `phase_affinity`, `context`, `when-relevant` tags — only works if it is keyed to the **moment you would apply the item**. The natural authoring reflex is to tag by the **subject** the item is *about* (what it describes). Subject-tagging reads as obviously correct, but it mis-files the item so it never surfaces at the moment of need: the retrieval silently fails and nobody notices, because the tag *looks* right. The error is invisible precisely because subject and "looks-correct" coincide — only a retrieval miss (or careful review) exposes that the tag answers the wrong question.

## Context
- **Use When**:
  - Authoring or reviewing a `use_when`, `trigger`, `context`, `when-relevant`, or `phase_affinity` field — anything whose purpose is retrieval-at-the-right-moment
  - Designing a classification schema whose categories drive WHEN items surface, not merely how they are filed
  - A "looks correct" tag isn't bringing items to the surface at the moment of need (silent retrieval miss)
- **Not When**:
  - The field's purpose is genuinely descriptive/archival — a topic label for browsing or indexing by subject, not retrieval-at-a-moment
  - Subject and application-moment coincide (a thing about X is also only ever needed when doing X) — then either tagging is equivalent
- **Prerequisites**: The field is consumed by a matcher/retriever that fires on situation, not just read by a human browsing topics.

## Solution
When authoring any surface-when-relevant field, ask: *"At what MOMENT would I need this to fire?"* and tag by that trigger-moment — not by the topic the content covers. Validate each tag with the consumer's test: *"If I were in situation X, would this tag bring the item to me?"* If a tag only answers "what is this about?", it is mis-keyed; rewrite it as the situation that should trigger retrieval.

### Implementation
- **Authoring move**: for each tag, write the *situation the consumer is in* when they need the item ("Before making any file modification"), not the *topic of the item* ("File-modification safety").
- **Review cue**: scan a `use_when`/`trigger` list and ask of each entry "is this a moment or a topic?" Topics ("validation", "menu design", "about X") are the tell.

## Rationale
- **Theoretical Basis**: A retrieval tag's value is realized at the moment of retrieval, so its key must match what is true at THAT moment — the situation the consumer is in — not what is true of the content (its topic). Subject-tagging optimizes for the author's vantage ("what did I just write?") over the consumer's vantage ("what do I need right now?"); the consumer is exactly who the tag serves, so the author's vantage is the wrong default.
- **Empirical Evidence**: ISS-225 (Sprint 105) — 16 of 16 corrections made during the issue were this exact error class: fields tagged by what-they-describe instead of when-they-fire. A unanimous error rate signals a strong, systematic reflex, not a one-off slip.
- **Design Decisions**: Named for the corrective move ("application-moment, not subject") rather than the symptom, so it reads as authoring guidance. Scoped to retrieval-purpose fields (with an explicit not-when for genuinely descriptive labels) to avoid over-applying it to archival metadata.

## Anti-Patterns
- **Anti-Pattern 1: Tag by topic because it "looks right"**
  - **Why Wrong**: A topic tag matches the content but not the consumer's situation, so the item never surfaces when needed — and the failure is silent because the tag appears correct.
  - **Example**: A `use_when` entry "menu design" (topic) instead of "When creating or restructuring a menu interface" (moment) — a matcher scanning for the consumer's situation won't fire on a bare topic noun.
- **Anti-Pattern 2: Author-vantage phrasing**
  - **Why Wrong**: Phrasing the tag from "what this item is" centers the author; the retriever needs "what situation calls for it."
  - **Example**: `trigger: "effectiveness-formula reference"` vs `trigger: "When recomputing a pattern's effectiveness at closure."`

## Consequences
- **Benefits**: Retrieval fires at the moment of need; silent mis-filing is prevented at authoring time rather than discovered as a missed match later; classification schemas align with consumer situations.
- **Tradeoffs**: Requires the author to mentally simulate the consumer's situation, which is more effort than naming the topic.
- **Risks**: Over-applying to genuinely descriptive/archival labels where subject-tagging is correct; phrasing moments so narrowly that legitimate situations don't match.

## Examples

### Before/After Comparison
**Without Pattern**: A pattern's `use_when` is authored as topic labels — "validation", "pattern effectiveness", "classification". A future situational match ("I'm about to author a use_when field") never fires because no entry names that moment. The pattern exists but is unreachable.
**With Pattern**: The same `use_when` is authored as moments — "When authoring or reviewing a use_when/trigger/context field." A situational matcher now surfaces it exactly when an author is in that situation.

### Application Example
ISS-225 (Sprint 105): 16/16 corrections converted fields from subject-keyed to application-moment-keyed. Each correction took a tag that described *what the item was about* and rewrote it as *the situation in which the item should fire* — restoring the field's retrieval purpose.

## Validation (Optional)
- **Success Indicator**: Every entry in a surface-when-relevant field reads as a situation/moment ("When...", "Before...", "While..."), not a topic noun.
- **Edge Cases**: Genuinely descriptive index labels are exempt; subject == moment cases need no change.

## Notes and Observations
The unanimity of the ISS-225 evidence (16/16) is the strongest signal: this isn't a careless slip but a default reflex — the author's natural answer to "how should I tag this?" is "by what it's about," which is the wrong question for a retrieval field. The pattern's job is to substitute the right question ("when would I need it?") at authoring time. Relationship to PAT-066 is general→instance: PAT-066 already encodes the right move for menus (classify by user-need-moment); PAT-131 names the underlying principle so it transfers to any surface-when-relevant field.
