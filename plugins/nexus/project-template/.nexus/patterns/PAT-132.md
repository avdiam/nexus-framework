# PAT-132: Source-Defect Census Before Migration
*Version: 1.0.0 | Date: 2026-08-07 | Sprint: 107*

## Metadata
- **Type**: practice
- **Status**: active
- **Created**: 2026-08-07

## Problem

Success Criteria for a migration are written against an *imagined* source — clean, uniformly formatted, complete, one record per entity. A long-lived accreted artifact is none of those. It was written across multiple format eras by authors following conventions that changed underneath them, and it carries structural outliers, duplicates that conflict rather than merely repeat, and voids where a record should be but never was.

The SC is therefore not wrong about *intent* — it is wrong about the *world*. And because nobody discovers this until the transform is already designed, the criterion is resolved one of two bad ways: quietly violated (the migration ships a gap nobody names), or quietly fabricated over (the migration invents a plausible value to satisfy the letter of the criterion).

## Context

- **Use When**:
  - Migrating or backfilling an artifact that accreted over many development cycles
  - A Success Criterion asserts a property of source data that nobody has verified against the source
  - Retiring a long-lived free-form file into a structured store
  - Any transform whose completeness claim depends on a count derived from the source
- **Not When**:
  - Greenfield schema design — there is no accreted source to census
  - Machine-generated data with an enforced schema, where format uniformity is guaranteed upstream
  - The source is small enough to read end-to-end as part of normal analysis (the census *is* the read)
- **Prerequisites**: Access to the full source artifact, and authority to amend the issue's Success Criteria before Build begins.

## Solution

Before designing the transform, census the source's **defects** — not its schema. The schema census tells you what fields to map; the defect census tells you whether the criterion you are being measured against is achievable at all.

Then **amend the Success Criterion to one the real source can satisfy**. The usual amendment shifts from an absolute to a documented-exception form: `"no X"` becomes `"no UNDOCUMENTED X"`. This is not a weakening. It is strictly stronger, because it forbids the silent-tolerance and silent-fabrication escapes that the absolute form leaves open — the void must now be explained, in the artifact, where a future maintainer will find it.

### Implementation

1. **Read the source end-to-end.** Not sampled, not grepped — read it. A parser over an accreted artifact inherits whatever convention the parser's author assumed, and the outliers are precisely the records that convention does not describe.
2. **Enumerate defect classes**, at minimum:
   - *Format eras* — where did the convention change, and which fields simply did not exist yet?
   - *Structural outliers* — records at the wrong nesting level, invisible to a level-anchored scan
   - *Duplicates* — and critically, whether they merely repeat or actually **conflict**
   - *Voids* — entities referenced elsewhere that have no record here at all
3. **Re-read every Success Criterion against the census.** For each, ask: can the real source satisfy this literally? Mark the ones that cannot.
4. **Amend before Build**, with the census as the stated evidence. Route the amendment through the normal approval gate — an SC change is a scope decision, not a Build-time judgment call.
5. **Write era-sparse fields present-and-empty, with the reason recorded.** A field that is absent because its concept did not exist yet is not missing data; encode that distinction so thinness reads as honest rather than as damage to repair.
6. **Record the anomalies redundantly** — in the schema documentation *and* inside the anomalous records themselves. A maintainer who reads neither the schema nor the archived source must still be unable to mistake a documented void for data loss.

### Quick Reference

| Step | Output |
|---|---|
| Read source end-to-end | Format-era boundaries, anomaly locations |
| Enumerate defect classes | eras · outliers · conflicting duplicates · voids |
| Test each SC against census | List of unmeetable criteria |
| Amend SC | `"no X"` → `"no UNDOCUMENTED X"` |
| Encode era-sparseness | present-and-empty + reason |
| Record anomalies redundantly | schema doc + in-record provenance |

## Rationale

- **Theoretical Basis**: A criterion can fail in two distinct ways — it can be wrong about the *intent* (the wrong goal) or wrong about the *world* (the right goal, impossible as stated). Ordinary review catches the first. Only contact with the actual source catches the second, and the cost of catching it late is that the transform is already built around the false premise.
- **Empirical Evidence**: ISS-228 (Sprint 107) censused a 199 KB / 3235-line accreted artifact before designing its migration and found three realities the SC had not anticipated: one record at the wrong heading level and therefore invisible to a level-anchored scan; one entity duplicated with *conflicting* content, reading as a corrected entry appended without removing the original; and one entity with no record anywhere — an empty folder and zero references project-wide. SC-01 as originally written was literally unmeetable. Amending it to the documented-exception form forced the void to be explained rather than tolerated or fabricated over.
- **Design Decisions**: The amendment direction matters. Weakening the criterion ("no more than N gaps") would license silence. Requiring documentation of each exception keeps the criterion binding while making it satisfiable.

## Anti-Patterns

- **Anti-Pattern 1 — Schema census mistaken for defect census**
  - **Why Wrong**: Cataloguing the source's fields tells you how to map, not whether the mapping can be complete. The defects live between the fields — in level, in duplication, in absence.
  - **Example**: Confirming the source has "sprint number, mode, conversation count" for every entry, without noticing that entries from the first fourteen cycles predate two of those three concepts.
- **Anti-Pattern 2 — Parser-first discovery**
  - **Why Wrong**: A parser encodes the convention its author believes the source follows. Records that violate that convention are exactly the records it silently drops, and the drop is invisible because the parser reports a plausible count.
  - **Example**: A `^## Entry` scan that returns a confident total while a record sitting at `###` level never enters the count.
- **Anti-Pattern 3 — Satisfying an unmeetable criterion by invention**
  - **Why Wrong**: Fabricating a value to close a void converts a documented gap into undetectable corruption. The gap was recoverable; the fabrication is not.
  - **Example**: Synthesising a record for an entity that never existed, so the count matches.

## Relationships
- **Requires**: Access to the full source; authority to amend SCs pre-Build
- **Enhances**: PAT-114 (baseline-anchored SC calibration — that one corrects *quantitative drift* from artifact mutation; this one corrects *premise error* from unverified source assumptions); PAT-097 (multi-source verification — supplies the independent-arithmetic technique for validating the census count)
- **Conflicts**: None identified
- **Alternatives**: Designing the transform first and handling defects as they surface at Build — cheaper up front, and the reason the criterion gets quietly violated

## Consequences
- **Benefits**: Converts an unmeetable criterion into an amendable one before it becomes a Build-time judgment call; surfaces the anomalies while there is still authority to decide how to represent them; produces a migration whose gaps are documented rather than either hidden or invented.
- **Tradeoffs**: Front-loads an end-to-end read into Analysis, which for a large artifact is a real cost in a phase that often wants to move quickly.
- **Risks**: The census itself can be incomplete. Guard it with two independent arithmetics that reach the same total by different routes — a dropped record breaks one while leaving the other intact.

## Examples

### Before/After Comparison
**Without Pattern**: SC reads "every entity in the source has a corresponding record; no gaps." Build discovers mid-transform that one entity has no source record. With the plan already locked and the criterion absolute, the options are to ship a silent gap or to invent a record. Either way the SC is marked met.

**With Pattern**: The census surfaces the void during Analysis. SC is amended to "no *undocumented* gap." Build ships 104 records, the void explained in the schema documentation and again inside the neighbouring records. The criterion is met honestly, and a maintainer three sprints later cannot mistake the gap for data loss.

### Application Example
Retiring a free-form historical log into a structured store: the census finds three format eras, one heading-level outlier, one conflicting duplicate, and one void. Two independent counts — `header-entries − duplicate` and `entity-numbers − void` — both land on the same total by different routes, and that agreement becomes the Build-phase guard against a silent record drop.

## Validation
- **Success Indicator**: Every Success Criterion was tested against a written census before Build began, and any criterion the real source could not satisfy was amended with the census cited as evidence.
- **Edge Cases**: When the source is small enough to read fully during normal analysis, the census is not a separate step — but the SC re-test still is.

## Notes and Observations

The insight that makes this worth remembering is not "investigate before designing" — that is obvious and would fail the non-obvious gate. It is the specific direction of the correction: **the criterion moves, not the data**. The instinct on discovering messy source data is to clean it, or to work around it, or to note it as a caveat. Amending the acceptance criterion so that honesty about the mess *is* the passing condition is a different move, and it produces a stronger criterion than the one it replaces.
