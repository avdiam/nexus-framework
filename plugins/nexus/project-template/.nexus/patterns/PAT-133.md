# PAT-133: Assert Before Destructive Write
*Version: 1.0.0 | Date: 2026-08-07 | Sprint: 107*

## Metadata
- **Type**: practice
- **Status**: active
- **Created**: 2026-08-07

## Problem

A one-shot bulk overwrite that silently produces a **short** output is indistinguishable from a correct one. The file is well-formed. Its size is plausible. Every record it does contain is valid. Nothing about the artifact announces that records are missing — and the natural verification, an aggregate count, is exactly the signal a miscount corrupts.

The standard discipline is write-then-verify. On a one-shot destructive write, that ordering is structurally too late: by the time verification runs, the previous state is gone and the only witness to what *should* have been written is the same derivation that just produced the wrong answer. Worse, a human spot-check of a large generated file is not a real check — sampling twenty of a hundred records confirms that the twenty are good, which is what a short file would also show.

## Context

- **Use When**:
  - A one-shot bulk overwrite where the output's own shape is the only completeness signal
  - Generating N records where N was *derived* from a source rather than given
  - Any destructive write whose correctness a human would have to spot-check to trust
  - Consolidating many inputs into a single artifact that later reads as authoritative
- **Not When**:
  - Incremental or append writes, where each addition is individually verifiable and the prior state survives
  - Purely mechanical, no-content-delta changes such as reformatting or bulk find-replace — those are better proved by classifying the diff's changed-line set (PAT-129)
  - The output is cheap to regenerate and trivially comparable against its source
- **Prerequisites**: The completeness property must be expressible as an arithmetic invariant over the source, computable before the write.

## Solution

**Encode the completeness invariants as assertions inside the writer**, so that a miscount aborts the write rather than emitting a short file. Verification moves from *after* the destructive step to *within* it — a failed assertion leaves the previous state intact and names the discrepancy, where a post-hoc check can only report damage that already happened.

Prefer **two independent arithmetics that reach the same figure by different routes**. A single count is self-confirming: whatever the derivation produced becomes both the expectation and the result. Two derivations that share no intermediate step cannot both absorb the same dropped record — one breaks while the other holds, and the disagreement is the alarm.

### Implementation

1. **State the invariants before writing any generation code.** What must be true of the output for it to be complete? Record count, per-partition counts, identifier continuity, the absence of duplicates.
2. **Derive the expected total twice, by routes that share nothing.** If both derivations pass through the same parse or the same intermediate list, they are one arithmetic wearing two hats.
3. **Assert inside the writer, before the destructive step executes.** The assertion guards the write; it does not follow it.
4. **Fail loudly and specifically.** The abort message must name which invariant broke and by how much — a bare failure sends the operator back to re-derive from scratch.
5. **Keep the assertions in the artifact that performs the write**, not in a separate validation pass that a hurried operator can skip or that can drift out of sync with the writer.
6. **Then verify from disk anyway.** This pattern makes the write safe; it does not replace the standing read-back discipline.

### Variations
- **Variant A — Generation**: assert the derived record count and per-partition subtotals before serialising.
- **Variant B — Consolidation/merge**: assert that the union's cardinality equals the sum of inputs minus the explicitly enumerated overlaps, so an unnoticed collision cannot silently shrink the result.

## Rationale

- **Theoretical Basis**: Verification placed *after* a destructive action can only report damage; verification placed *inside* it can prevent damage. The distinction only matters when the action is irreversible and the damage is silent — which is precisely the one-shot bulk overwrite. And a single count is not evidence, because the same error that dropped the record also lowered the expectation.
- **Empirical Evidence**: ISS-228 (Sprint 107) protected its single destructive step — one overwrite of a consolidated store — by encoding four arithmetic invariants as assertions inside the writer. The anti-drop guard was two independent arithmetics reaching the same total by different routes: `header-entries − duplicate` and `entity-numbers − void`. A dropped record breaks one while leaving the other intact. Validate later re-derived both from scratch and they still agreed.
- **Design Decisions**: The assertions live in the writer rather than in a companion validator. A separate validator is a step that can be skipped, and one that drifts as the writer changes.

## Anti-Patterns

- **Anti-Pattern 1 — Aggregate count as sufficient proof**
  - **Why Wrong**: Compensating errors hide inside an aggregate. A total that matches can still be wrong in both directions at once, and a total derived from the same parse that produced the output confirms nothing.
  - **Example**: "The file has 104 records and we expected 104" — where both figures trace back to one parse that never saw the outlier record.
- **Anti-Pattern 2 — Human spot-check as the completeness check**
  - **Why Wrong**: Sampling verifies that the sampled records are good. A short file's surviving records are also good. The check cannot distinguish the two cases it exists to distinguish.
  - **Example**: Reading twenty records of a hundred, finding them faithful, and concluding the migration is complete.
- **Anti-Pattern 3 — Verify-after on an irreversible write**
  - **Why Wrong**: The correct ordering exists to catch errors when correction is cheapest. After a one-shot overwrite, correction is no longer cheap — the prior state is gone.
  - **Example**: Overwriting the store, then reading it back and discovering the count is short, with no baseline left to diff against.

## Relationships
- **Requires**: A completeness property expressible as arithmetic over the source
- **Enhances**: PAT-129 (additive-diff-proof — that one proves a *mechanical* change after the fact by classifying the diff; this one guards a *content-generating* write before it commits. They are the post-hoc and pre-commit halves of the same concern and share the finding that an even aggregate count is necessary but not sufficient); PAT-132 (the source census supplies the invariants this pattern asserts)
- **Conflicts**: None identified
- **Alternatives**: Dry-run to a preview file for human inspection before merging — rejected as the primary guard where the output is large enough that human inspection degenerates into sampling

## Consequences
- **Benefits**: A miscount fails loudly instead of shipping a short file that later reads as complete; the invariants become durable documentation of what completeness meant; re-validation in a later phase is cheap because the invariants are already written down.
- **Tradeoffs**: Requires stating the invariants up front, which is real design work before any code is written; and a genuinely novel legitimate case can trip an assertion and need the invariant revised.
- **Risks**: Assertions derived from a single flawed premise inherit that flaw. This is exactly why independence between the two arithmetics is load-bearing rather than decorative.

## Examples

### Before/After Comparison
**Without Pattern**: A script transcribes records from a source into a consolidated store and overwrites it. One record sat at an unexpected nesting level and was never picked up. The store is written with 103 records, is valid, is plausibly sized, and every record in it is correct. The loss surfaces sprints later, when someone looks for the missing entity and cannot tell whether it was dropped or never existed.

**With Pattern**: The same script asserts, before writing, that the record count equals both `header-entries − duplicate` and `entity-numbers − void`. The dropped record breaks the first while the second still reads 104. The write aborts, names the discrepancy, and the outlier is found in minutes with the prior state untouched.

### Application Example
Consolidating an accreted historical log into a structured store: four invariants asserted inside the writer (total count, per-era subtotals, identifier continuity, no duplicate identifiers), with the total cross-checked by two independent derivations. The write is the last thing that happens, and only if all four hold.

## Validation
- **Success Indicator**: The writer aborts cleanly on a deliberately corrupted input, naming the broken invariant — test this once rather than assuming it.
- **Edge Cases**: When the source legitimately changes between derivation and write, the invariants must be computed against the same snapshot the write consumes, or they will report a false failure.

## Notes and Observations

A near neighbour of this pattern was proposed and rejected in Sprint 106 (recorded as RP106-1): *script-based backfill with a dry-run diff before commit*. It failed the non-obvious gate — preview-before-destructive-write is near-universal engineering practice. This pattern is the second appearance of that problem class and clears the bar on a specific distinction: RP106-1's remedy is **an artifact a human inspects**, and human inspection of a large generated file degrades into sampling, which is precisely the check that cannot detect a short file. This pattern's remedy is **machine-checked invariants that abort the write**. The problem was recurring; the remedy form is what changed.
