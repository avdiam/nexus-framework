# PAT-134: Grep the File-Class for the Defect Shape
*Version: 1.0.0 | Date: 2026-08-07 | Sprint: 107*

## Metadata
- **Type**: practice
- **Status**: active
- **Created**: 2026-08-07

## Problem

A defect is reported against one file. The instinct is to fix that file — the report names it, the reproduction uses it, and the fix is bounded and satisfying.

But members of a homogeneous file-class are rarely written independently. They are written by copy-adapt: someone wrote the first one, and every subsequent member started as a copy with the specifics changed. That authorship history distributes defects the same way it distributes correctness. So a defect in one member is evidence about the **class**, not about the file — and, symmetrically, some sibling may already handle the same concern correctly, because it was written after someone had already hit the problem.

Fixing the reported file alone leaves the other instances live and invents a solution that may already exist twenty lines away in a neighbour.

## Context

- **Use When**:
  - A defect surfaces in one member of a homogeneous file-class — hooks, skills, templates, agents, migrations, handlers, config fragments
  - Before designing a fix whose blast radius has not been established with an actual command
  - When "is this the only one?" has been answered by reasoning rather than by a grep
  - When the correct form of the fix is not obvious and inventing one feels necessary
- **Not When**:
  - Genuinely singleton files with no siblings sharing structure or purpose
  - The defect is provably specific to one file's unique logic, not to the shape the class shares
  - The class is large and heterogeneous enough that "same shape" has no meaning
- **Prerequisites**: The file-class must be identifiable — a directory, a naming convention, or a shared structural signature that a predicate can express.

## Solution

Before designing the fix, **grep the whole file-class for the defect's shape** — its structural signature, not its literal text. Ask two questions, not one:

1. **Where else does this defect live?** The answer sets the fix's real scope, and it is an answer produced by a command, not by recollection.
2. **Does a sibling already implement the correct form?** If one does, adopt it. An existing implementation has survived real execution that new code has not, and adopting it keeps the class converging instead of adding a third dialect.

The predicate matches on shape because the text will differ — variable names, paths, and messages are exactly what copy-adapt changes. Match on the structure that makes the defect possible: the missing guard, the unchecked call, the assumption about an ambient value.

### Implementation

1. **Name the class explicitly.** A directory, a glob, a naming convention. Write it down — it becomes the predicate's scope and the fix's declared blast radius.
2. **Characterise the defect as a shape.** Not "this file calls `foo` without checking" but "any member that calls `foo` without a preceding availability guard."
3. **Run the predicate over the whole class**, including the reported file, and **record the literal command with its per-member hit count** — including zero-hit members. The recorded command is what distinguishes a real sweep from an eyeballed one.
4. **Classify every hit** as a real instance of the defect or as correct-by-scoping. Do not fold a correct-by-scoping hit into the fix; manufacturing a change to a correct artifact corrupts it.
5. **Search the same class for the correct form.** Members that lack the defect may lack it deliberately — read one and find out whether it is an accident or an implementation worth copying.
6. **Scope the fix to the class**, applying the adopted form per-member rather than blanket-copying it. Members differ; a sibling's extra rigor may be unnecessary complexity elsewhere.

### Quick Reference

| Question | Produced by | Output |
|---|---|---|
| What is the class? | Naming the directory/glob | Declared blast radius |
| What is the defect's shape? | Structural characterisation | The predicate |
| Where else does it live? | Running the predicate | Per-member hit counts, zero-hits included |
| Which hits are real? | Classifying each hit | Real-defect vs correct-by-scoping |
| Does the cure exist already? | Reading a clean sibling | Adopted form, or none |

## Rationale

- **Theoretical Basis**: Copy-adapt authorship makes a file-class statistically coupled. Any property of one member — defect or correctness — is prior evidence about the others. Surveying the population therefore answers two questions in a single pass: the *extent* question (how big is this fix?) and the *design* question (what should the fix look like?). Treating a class member as an isolated file discards that prior.
- **Empirical Evidence**: ISS-232 (Sprint 107) found an unguarded dependency in one hook. Grepping the whole hook directory for the same shape found a **second live instance** carrying the identical defect — one whose failure mode was silent, so no report would ever have named it — *and* two sibling hooks that already implemented the correct guard. The design work collapsed from "invent a resolution ladder" to "apply the house idiom," and the fix's scope doubled from what the report had named.
- **Design Decisions**: The predicate matches on shape rather than text because copy-adapt varies the text by construction. And the second question — does the cure already exist — is the half that is easiest to skip and often the more valuable, because it turns design work into adoption.

## Anti-Patterns

- **Anti-Pattern 1 — Fixing the reported file**
  - **Why Wrong**: The report names where the defect was *noticed*, which is a fact about observation, not about distribution. The unreported instances are frequently the dangerous ones, because their failure mode was silent enough to avoid a report.
  - **Example**: Patching the hook that threw a visible error while its sibling, which fails by silently doing nothing, stays broken.
- **Anti-Pattern 2 — Inventing a fix without checking the neighbours**
  - **Why Wrong**: Adds a third dialect to a class that already contains a working one, and forfeits the real-execution evidence the existing implementation carries.
  - **Example**: Designing a novel guard while two siblings already implement the house idiom correctly.
- **Anti-Pattern 3 — Eyeballed sweep recorded as a sweep**
  - **Why Wrong**: A claim of "checked the class" that no command backs is indistinguishable from not having checked. Record the literal predicate and its per-member counts.
  - **Example**: "I looked through the directory and this is the only one" as the completeness evidence.
- **Anti-Pattern 4 — Folding correct-by-scoping hits into the fix**
  - **Why Wrong**: A hit is not a defect. Some members legitimately lack the guard because their code path cannot reach the failure. Changing them adds unnecessary complexity and corrupts a correct artifact.
  - **Example**: Adding a version assertion to a member that has no code path requiring it, purely because the predicate matched.

## Relationships
- **Requires**: An identifiable file-class expressible as a predicate
- **Enhances**: PAT-098 (grep-before-rename — that one establishes completeness of *a known change's* footprint, asking "did my edit miss a site?"; this one is *diagnostic*, running before the change is designed and asking "is this defect elsewhere, and is the cure already written?"); PAT-058 (documentation-driven discovery — shares the finding that systematic reading over a class surfaces more than expected)
- **Conflicts**: None identified
- **Alternatives**: Fixing the reported instance and waiting for the others to be reported — viable only when every instance fails loudly, which is the case this pattern exists to disprove

## Consequences
- **Benefits**: Establishes the fix's real scope with evidence rather than assumption; frequently converts design work into adoption of a proven sibling implementation; catches silent-failure instances that would never generate their own report; leaves the class more uniform than it was.
- **Tradeoffs**: Widens the issue's scope beyond what was reported, which can turn a bounded fix into a larger one and may warrant a scope conversation before proceeding.
- **Risks**: A predicate that is too narrow under-reports and produces false confidence — enumerate naming and punctuation variants of anything being matched. A predicate that is too broad floods the classification step with correct-by-scoping hits.

## Examples

### Before/After Comparison
**Without Pattern**: A hook is reported as failing when an optional dependency is absent. The fix guards that hook. A sibling hook carrying the identical defect keeps failing silently — it emits an allow verdict and returns, so nothing ever surfaces — and the protection it was supposed to provide has been inactive for an unknown number of sprints.

**With Pattern**: Grepping the hook class for the shape "invokes the dependency without a resolution ladder" returns two live instances and identifies two clean siblings. The clean siblings' ladder is read and adopted. Both defective hooks are fixed with the house idiom, and the extra rigor one of them needs is applied only there.

### Application Example
A methodology skill is found to assert a false ordering. Before editing, the predicate is run over all skills in the class: two other members carry the same assertion, and one has already been corrected. The corrected member's phrasing is adopted; the finding that the remaining members diverge is recorded as scoped-out with evidence rather than silently absorbed.

## Validation
- **Success Indicator**: The issue record carries the literal predicate and its per-member hit counts, zero-hit members included, and each hit is classified real-defect or correct-by-scoping.
- **Edge Cases**: A low hit count on a class you expected to be contaminated is a signal to suspect the predicate before concluding the class is clean.

## Notes and Observations

The two halves of this pattern have different characters and different failure modes. The first — *where else does this live* — is a completeness discipline, and it is skipped through overconfidence. The second — *does the cure already exist* — is an economy discipline, and it is skipped through eagerness to start building. The second half is the one more often lost, and it is frequently worth more: adopting a sibling's proven implementation is both cheaper and safer than inventing an equivalent, and it keeps the class converging on one idiom instead of accumulating dialects.
