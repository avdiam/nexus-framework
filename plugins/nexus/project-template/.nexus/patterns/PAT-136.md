# PAT-136: Extend the Positioned Mechanism
*Version: 1.0.0 | Date: 2026-08-19 | Sprint: 108*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-08-19

## Problem

A discipline gap needs enforcement, or recurring work needs a cadence — and the instinct is to build a new mechanism for it. New mechanisms arrive with three costs that are invisible at design time: their own ceremony, their own skip-path, and a clock chosen by the designer rather than derived from the work being governed. The new mechanism is then measured against the problem it was built for, where it looks correct, rather than against the mechanisms that already run, where it looks redundant.

## Context

- **Use When**:
  - About to add a gate, checkpoint, marker, or enforcement step because an existing discipline was skipped or produced a wrong result
  - About to register a scheduled operation, tracked cadence, or maintenance cycle for recurring hygiene work
  - An existing mandatory mechanism sits at the right point in the workflow but reports the wrong thing, or reports too little
  - Designing where a new judgment should live, as distinct from what the judgment should be
- **Not When**:
  - No existing mechanism sits at the right position or runs at the right frequency — then a new one is genuinely required
  - Extending would overload one mechanism with unrelated concerns, making it a grab-bag whose failure modes are no longer legible
  - The existing host is itself scheduled for retirement or is known to be drifted
- **Prerequisites**: An inventory of what already runs, with each candidate host's position in the workflow and its firing frequency made explicit.

## Solution

Before adding a mechanism, inventory what already runs at the right **position** or the right **frequency**, and prefer extending it.

Two forms of the same move:

- **Position (enforcement)** — if an existing *mandatory* mechanism already sits at the correct point in the workflow but reports the wrong thing, amend its required fields rather than adding a gate beside it. The amendment inherits the host's unskippability at zero cost; a new gate must earn unskippability from scratch and brings a fresh skip-path with it.
- **Frequency (cadence)** — if an existing pass already opens the artifact at the right interval, host the new judgment on that read. It inherits the correct clock; a separately scheduled operation runs on whatever cycle its subsystem happens to use, which is rarely the cycle the decay demands.

### Implementation

1. **State the required position or frequency** — at which point must this fire, or how often? Answer before looking at candidates, so the answer is not shaped by what is convenient.
2. **Inventory existing mechanisms** that already fire at that point or interval. Include mechanisms owned by other subsystems.
3. **For each candidate host, ask what it already guarantees** — is it mandatory? does it already emit? does it already open the artifact?
4. **Test the extension** — can the new requirement be expressed as additional required *fields* of an existing output, or an additional *judgment* on an existing read? If yes, extend.
5. **If extending, name what is inherited** — unskippability, clock, existing reader attention — so the choice is defensible later.
6. **If no host fits, build new and record why** — which position/frequency was required and which candidates failed it.

### Variations

- **Variant A — Under-specified gate**: the host is correct and mandatory but its required fields report a proxy (size, presence, count) rather than the property that matters (structure, equivalence, coverage). Amend the fields.
- **Variant B — Free-riding judgment**: the host already reads the artifact for another purpose. Add the judgment to that read; the marginal cost is the judgment itself, not the read.

## Rationale

- **Theoretical Basis**: An enforcement point's value is *position × unskippability*; a cadence's value is *frequency × coverage*. Both factors are properties of the **host**, not of the check being added. A new mechanism must earn both from zero. An extension inherits both for the price of the check alone.
- **Empirical Evidence**: Sprint 108 reached this from two independent directions. ISS-235 found `nexus-checkpoint`'s CP-1/CP-3 already mandatory, already unskippable, already emitting — they simply reported *size*, which is exactly the check that passes on a structurally mutilated file. Amending their required fields cost one edit. ISS-233 found that registering seed grooming as a sixth tracked maintenance operation would have run it on the 8-sprint maintenance cycle with an urgency class that never triggers early — a disposal path on a clock 8× slower than the decay it governs — and would have cost a `/6 → /7` formula cascade across five files plus a skill that did not exist. Hosting the judgment on `organize-sprint` STEP 1D, which already opened every seed every sprint, cost two judgments on an existing read.
- **Design Decisions**: The pattern deliberately covers both axes rather than splitting into a gate-pattern and a cadence-pattern, because the deciding question is identical — *what does the host already guarantee that I would otherwise have to build?*

## Anti-Patterns

- **Anti-Pattern 1**: Adding a new gate beside a correct one because the existing gate "isn't about this".
  - **Why Wrong**: Position is the expensive property and it is already paid for. Two gates at one point means two things to skip, and the new one has no track record of being obeyed.
  - **Example**: Adding a post-write verification step next to an existing mandatory post-write marker, instead of adding the missing fields to that marker.
- **Anti-Pattern 2**: Registering recurring hygiene as a tracked operation because a scheduling subsystem exists and "owns scheduled work".
  - **Why Wrong**: Subsystem ownership is an organisational fact, not a frequency argument. The subsystem's cycle was calibrated for its own workload, not for the decay rate of the new artifact.
  - **Example**: Putting a per-sprint hygiene judgment on an 8-sprint maintenance cycle because maintenance is where hygiene "belongs".
- **Anti-Pattern 3**: Extending a host that is drifted, deprecated, or already overloaded.
  - **Why Wrong**: Inheriting a host's properties means inheriting its problems. Verify the host is live and coherent before hanging anything on it (see PAT-124).

## Consequences
- **Benefits**: New disciplines inherit unskippability and correct timing for free · fewer mechanisms to learn, audit, and maintain · the extension is discovered by anyone already reading the host.
- **Tradeoffs**: The host grows, and a host that accumulates many extensions eventually needs splitting · the extension's origin is less visible than a dedicated mechanism's would be, so the amendment should cite it inline.
- **Risks**: Over-application produces omnibus mechanisms whose individual guarantees become hard to reason about · inheriting a drifted host propagates its drift.

## Examples

### Before/After Comparison

**Without Pattern**: A checkpoint's verification cannot detect structural destruction, so a new structural-verification gate is designed, positioned, given its own mandatory-output marker, and wired into the workflow. It is now a second thing that can be skipped, and its obedience is untested.

**With Pattern**: The existing CP-3 marker already fires at exactly the right moment and is already unskippable. It reports size. Add tag-pair and conversation-field values to its required fields. One edit; the failure mode is now detected by a gate with an existing compliance record.

### Application Example

Seed files decay and need periodic disposal review. The "proper" home is the maintenance subsystem, which owns scheduled hygiene and has velocity and scoring machinery. But `organize-sprint` STEP 1D already globs every seed every sprint and already makes one free-text semantic judgment per file. Two additional judgments ride that read at zero marginal cost and inherit a per-sprint clock. The maintenance route would have delivered the same judgments on an 8-sprint cycle — 8× slower than the decay it governs.

## Validation
- **Success Indicator**: The design record names the host, states what was inherited (unskippability / clock / existing read), and shows the marginal cost as the check itself rather than check-plus-scaffolding.
- **Edge Cases**: When two hosts each satisfy half the requirement (right position, wrong frequency), the pattern does not resolve the choice — fall back to which property is load-bearing for the failure being prevented.
