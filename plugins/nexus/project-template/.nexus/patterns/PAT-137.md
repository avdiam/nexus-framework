# PAT-137: Check the Other Writer
*Version: 1.0.0 | Date: 2026-08-19 | Sprint: 108*

## Metadata
- **Type**: practice
- **Status**: active
- **Created**: 2026-08-19

## Problem

A change makes a component the **second** writer to a shared artifact — a log, an append-only store, a registry, a counter, a queue. The visible work is updating whatever documentation names the writers, and that update feels like completion. The other writers are never opened. Each of them was written when it was the sole writer, so each carries unstated exclusive-ownership assumptions — id sequences, counters, ordering, uniqueness — that were true until this change and are now false. The resulting defect is latent: it needs a specific interleaving to fire, and it usually passes every validity check the system has, because a colliding record is still a well-formed record.

## Context

- **Use When**:
  - A change adds a writer to any artifact that already has one — append-only stores, JSONL logs, registries, sequence files, shared state
  - A change moves a write from one component to another, or duplicates a write path for a new route
  - Updating documentation that enumerates the writers of a shared artifact — treat that edit as the *signal*, not the fix
  - Reviewing a design whose diagram shows two arrows into the same box
- **Not When**:
  - The artifact is genuinely single-writer after the change, or writes are serialised through one owner
  - The artifact carries no allocated namespace, sequence, counter, or ordering guarantee — nothing to collide over
  - Writers operate on provably disjoint key spaces enforced by the store itself
- **Prerequisites**: The full writer set is enumerable — you can list every component that writes the artifact, not just the ones the documentation names.

## Solution

When a change makes a component a second (or Nth) writer to a shared artifact, **open every other writer and check what each assumes it owns exclusively.**

Enumerate for each existing writer:

- **Namespace / id allocation** — does it derive ids from its own state, or from the artifact's current contents? Sole-writer code usually does the former.
- **Sequence and counters** — does it assume its last-written number is the artifact's highest?
- **Ordering** — does it assume records appear in the order it wrote them?
- **Uniqueness** — does anything *downstream* resolve through a key this writer assumes it alone allocates?
- **Read-modify-write windows** — does it read, compute, and write assuming nothing intervened?

Fix the assumptions in the writers. Updating the map is bookkeeping; the writers are the territory.

### Implementation

1. **Enumerate writers from source, not from documentation.** Grep for writes to the artifact path across the codebase. The documentation is the thing most likely to be stale — it is what motivated this check.
2. **For each existing writer, read its allocation and ordering logic.** Ask literally: *what does this code believe it is the only one doing?*
3. **Add the missing guard at the point of allocation** — derive from the artifact's current contents (e.g. scan for the highest existing id and continue from it) rather than from local state.
4. **Check the downstream resolvers.** Anything that resolves a pointer through the allocated key inherits the collision. In an append-only store there is no clean withdrawal, so a collision is permanent.
5. **Confirm the validity gate cannot catch it.** If the store's own validation would pass a colliding record, say so explicitly — that is the reason the guard has to exist rather than be delegated.
6. **Then** update the documentation that names the writers.

## Rationale

- **Theoretical Basis**: Documentation about writers is a *map*; only writers *collide*. A map can be corrected without touching the territory, which is precisely why correcting the map feels like completion — the visible artifact of the problem has been addressed while the mechanism producing it is untouched.
- **Empirical Evidence**: ISS-233 (Sprint 108) made `/nexus-plug-seed` a second writer to `discoveries.jsonl`. Build correctly source-fixed CLAUDE.md's Memory-Layer writer table — and stopped there. A full phase later, adversarial review found that the co-writer `/nexus-index-sprint` still allocated `{nn}`-sequenced ids with no uniqueness step, safe only while it was sole writer; the first sprint to plant a finding mid-sprint and then close would have produced a duplicate id. Critically, `json.loads` **passes** on a duplicate id, so the skill's own parse-validate gate could not have caught it — and `id` is the unique anchor every `contradicts` / `superseded_by` / `related_to` pointer resolves through, in a store that is append-only. The same review found the canonical schema file — the one the *producer* points its reader at — still naming the old sole writer.
- **Design Decisions**: The check is scoped to *what an existing target assumes*, deliberately distinct from verifying that a cited target *exists* (PAT-124). Existence is a property of the target; exclusive-ownership assumptions are properties of the code around it.

## Anti-Patterns

- **Anti-Pattern 1**: Fixing the writer table and closing the item.
  - **Why Wrong**: The table is documentation. It has no effect on allocation, ordering, or uniqueness at runtime.
  - **Example**: Naming the new writer in a Memory-Layer table while the existing writer keeps allocating ids from `01`.
- **Anti-Pattern 2**: Trusting the store's validity gate to catch collisions.
  - **Why Wrong**: Validity and uniqueness are different properties. A duplicate id is still valid JSON, a duplicate key is still valid YAML in many parsers, a duplicate row is still a row.
  - **Example**: Relying on a `json.loads` write-verify to detect a duplicate `id`.
- **Anti-Pattern 3**: Enumerating writers from the documentation you are about to update.
  - **Why Wrong**: Circular. That document's staleness is the reason you are here.
  - **Example**: Reading a "Written by:" column to decide which writers to inspect.

## Relationships
- **Requires**: none
- **Enhances**: PAT-098 (grep-before-rename — supplies the enumerate-from-source discipline), PAT-083 (structured-persistence-ownership — the design-time counterpart to this change-time check)
- **Conflicts**: none
- **Alternatives**: PAT-124 (verify-relocation-target) checks that a cited target **exists** and is live; this pattern checks what an existing target **assumes**. Complementary, not substitutable.

## Consequences
- **Benefits**: Catches latent multi-writer defects at the change that introduces them, when the cost is one guard · surfaces downstream resolvers that inherit the collision · forces the honest statement that the existing validity gate cannot catch it.
- **Tradeoffs**: Requires reading code outside the change's declared scope, which reads as scope creep until the defect is found · the check is cheap only when the writer set is small.
- **Risks**: In an append-only store the defect is irreversible once it fires, so a missed check has no clean remedy — this raises the cost of skipping, not of applying.

## Examples

### Before/After Comparison

**Without Pattern**: A new route is wired to append findings to a shared JSONL store. The Memory-Layer writer table is updated to name it. The existing indexer keeps starting its id sequence at `01` each sprint. The first sprint in which both writers run produces two records with the same id; every pointer resolving through that id now resolves ambiguously, permanently.

**With Pattern**: Adding the second writer triggers a read of the first. Its id allocation is found to derive from local assumption rather than from the file. A lead-in step is added: scan the target for existing ids of this prefix and continue from the highest. The collision never occurs.

### Application Example

`.nexus/memory/discoveries.jsonl` gained a second writer. Opening the co-writer surfaced the id-allocation gap; opening the canonical schema surfaced that it still documented a single writer — the very document the new producer directs its reader to as authoritative. Both were latent, neither was in the change's declared scope, and both were consequences of the same one-way (append-only) property that the design had already identified for the *write* and missed for the *namespace*.

## Validation
- **Success Indicator**: The change record lists every writer of the artifact, states what each was found to assume, and names either the guard added or the reason no guard was needed.
- **Edge Cases**: When the "other writer" is an ad-hoc or human-invoked route rather than a skill or module, it is easy to omit — enumerate routes, not just components.

## Notes and Observations

The non-obvious half is not the collision — collisions are a familiar hazard. It is that **fixing the documentation feels like discharge**. The pattern earns its keep by naming that specific false-completion signal, so the writer-table edit becomes the trigger for the check rather than its conclusion.

A related generalisation from the same issue: when a one-way door is identified, enumerate every property that inherits from the same irreversibility. The append-only property was correctly traced for the write (a misclassified record cannot be withdrawn) and missed for the id namespace, which inherits from the identical property. The recorded door is usually the most visible instance, not the only one.
