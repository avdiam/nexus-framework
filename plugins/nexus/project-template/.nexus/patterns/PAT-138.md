# PAT-138: Check the Instrument Before the Reading
*Version: 1.1.0 | Date: 2026-08-25 | Sprint: 110*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-08-19

## Problem

A measurement comes back and the instinct is to act on the thing measured. A failing test reads as a claim about the implementation. A clean before/after delta reads as a claim about the file. But every reading is the joint product of a subject and an instrument, and the instrument is usually the newer, less-reviewed, more-assumption-laden artifact of the two. Worse, an under-specified instrument fails toward **clean**: it reports a pass on a broken subject rather than an error on itself, so nothing signals that the instrument is the problem.

## Context

- **Use When**:
  - A test, check, or harness returns a failure against work believed correct — before editing the implementation
  - Designing or reviewing a gate that compares a BEFORE figure against an AFTER figure
  - A verification reports clean and the result is more reassuring than the evidence warrants
  - A checker, parser, or scripted verification returns **zero findings** — before trusting the zero, assert it consumed rows
  - Auditing a check whose evidence line is produced by a command written in prose rather than reproduced literally
  - Reviewing someone else's verification claim without a second independent source to compare against
- **Not When**:
  - The instrument is machine-generated, externally maintained, or has a long track record on this exact subject
  - Multiple independent sources are already available and disagree — then compare sources (PAT-097) rather than auditing one
  - The reading is being used for orientation only, with no decision hanging on it
- **Prerequisites**: The instrument is inspectable — the fixture, oracle, or literal command can be read.

## Solution

Before acting on a reading, audit the instrument that produced it.

**On a failure**, treat the red result as a claim about **two** artifacts — the implementation and the harness — and check the harness first, because it is cheaper:

- Does the **fixture** actually carry the condition under test? A fixture lacking the hazard makes the good and bad methods agree, and the test proves nothing either way.
- Does the **oracle** measure the right thing? An oracle scoring a legitimate behaviour as damage produces a red result against correct code.

**On a comparison gate**, require that both figures come from **one identically-written command, reproduced verbatim at both sites**:

- Prose agreement that both sides "use the same convention" is exactly what permits drift, because it reads as sufficient specification while binding nothing.
- Any corruption whose signature the narrower side cannot see produces a clean delta and a confident PASS on a broken subject.

### Implementation

1. **Name the instrument** explicitly — the harness, the fixture, the oracle, the literal grep, the counting rule.
2. **On a failure**: verify the fixture carries the condition, then verify the oracle measures the intended property. Only after both pass, treat the failure as a claim about the implementation.
3. **On a comparison**: write out both sides' commands literally and diff them as strings. If they are not character-identical, they are not the same instrument.
4. **Construct the corruption the instrument cannot see** — not the one it obviously catches. This is the test of a verification gate; catching the obvious case proves nothing about coverage.
5. **Record the literal instrument alongside the reading**, so a later reader can re-derive rather than re-trust.

**On a zero-finding result**, prove the checker consumed input before accepting the zero:

- A checker that **parses nothing** is indistinguishable from a clean run. Where a false finding gets caught by its implausible magnitude, the vacuous pass has no magnitude at all — it looks exactly like success.
- Assert the **row count** the checker actually read, alongside the finding count: *16/16 filepaths examined, 88/88 references resolved, 120 changelog entries parsed*. A zero over a denominator is evidence; a bare zero is not.
- This is the same failure as `&&`-chaining a detector run (a zero-hit grep exits non-zero, so the chain truncates and a partial pass reads as a complete one) reached by a different route: wrong parse instead of early exit.

### Variations

- **Variant A — Red-result triage**: applies at test failure. Cheapest first move; distinct from "adjust test expectations", which presumes the implementation is right rather than diagnosing which artifact is wrong.
- **Variant B — Comparison-gate specification**: applies at gate design and review. The failure is silent, so it must be caught by construction rather than by observation.

## Rationale

- **Theoretical Basis**: A reading is subject × instrument. Attributing the whole reading to the subject is a category error, and it is asymmetrically costly: an under-specified instrument fails toward clean, so instrument defects are invisible exactly when they matter. Auditing the instrument is also the cheaper branch — it is smaller, newer, and inspectable.
- **Empirical Evidence**: ISS-235 (Sprint 108) produced both halves. Its T1 harness returned FAIL against a *correct* implementation: the fixture checked for a prose-mention hazard in a file that had none (so both the good and bad methods agreed), and the oracle scored a legitimate tail-truncation as damage. Rewritten with a landing-position oracle across two real fixtures, it passed decisively and surfaced 7 genuine divergences. Separately, the checkpoint's CP-1 baseline prescribed one grep (open tags) while STEP 4's reconciliation prescribed two, with the two sites agreeing only in prose that they used "the same convention". Demonstrated on a sandbox copy: deleting a single close tag left open=14 (delta 0, reads CLEAN), close=13, duplicates 0, conversation fields consistent — **all three prescribed post-write checks passed on a structurally broken file.**
- **Design Decisions**: Both halves are held in one pattern because the corrective move is identical — stop, inspect the measuring apparatus, and only then interpret the number. Splitting them would file the same discipline under two triggers and surface neither reliably.

## Anti-Patterns

- **Anti-Pattern 1**: Editing the implementation because the test went red.
  - **Why Wrong**: Presumes the harness is correct. The harness is typically the newer artifact and has itself been reviewed less.
  - **Example**: Rewriting a working method to satisfy an oracle that was measuring the wrong property.
- **Anti-Pattern 2**: Adjusting test expectations to make a red test green.
  - **Why Wrong**: Skips the diagnosis entirely. The question is *which artifact is wrong*, and "adjust expectations" has already answered it without evidence.
  - **Example**: Loosening an assertion until it passes, without establishing that the fixture carried the condition.
- **Anti-Pattern 3**: Specifying a comparison gate's two sides in prose.
  - **Why Wrong**: "Both sides use the same convention" binds nothing and reads as sufficient. The drift it permits is silent by construction.
  - **Example**: One site prescribing an open-tag count and the other a matched-pair count, both described as "tag counting".
- **Anti-Pattern 4**: Testing a verification gate with the corruption it obviously catches.
  - **Why Wrong**: Confirms the gate does something, not that it covers the class. Coverage is proven at the boundary, not at the centre.
- **Anti-Pattern 5**: Reporting a zero-finding result without the denominator.
  - **Why Wrong**: A checker that parsed nothing and a checker that found nothing produce identical output. Unlike a false *positive*, which an implausible magnitude can betray, the vacuous pass carries no tell.
  - **Example**: A checker reporting "63 of 64 references untracked" was caught because the number was absurd; the same checker returning "0 untracked" would have been accepted without question. Two such checkers ran in one conversation.

## Relationships
- **Requires**: none
- **Enhances**: PAT-122 (honest-green-all-branches-all-environments), PAT-135 (evidence-artifact-proves-execution-not-adequacy), PAT-129 (additive-diff-proof)
- **Conflicts**: none
- **Alternatives**: PAT-097 (multi-source-verification) resolves a doubtful reading by **adding independent sources** and locating the divergence. This pattern resolves it by **auditing the single instrument**, and applies precisely where PAT-097 cannot — a test harness or a gate command has no sibling source to compare against. Try this one first; it is cheaper and needs no second source.

## Consequences
- **Benefits**: Prevents correct implementations being edited to satisfy defective harnesses · turns silent comparison-gate drift into a construction-time check · produces re-derivable evidence rather than re-trustable claims.
- **Tradeoffs**: Adds a step before acting on every red result, which is pure overhead when the harness is in fact fine · writing commands literally at both sites is more verbose than describing the convention once.
- **Risks**: Can be used to rationalise ignoring genuine failures ("it's probably the harness") — the discipline is to *check* the instrument, not to *assume* it is at fault.

## Examples

### Before/After Comparison

**Without Pattern**: A structural-verification gate specifies its baseline in one step and its reconciliation in another, both described as counting tags. A file loses a single close tag. Baseline and reconciliation each report their own number, the delta is zero, and the gate returns PASS with full confidence on a structurally broken file.

**With Pattern**: The gate's two sides are written as one literal command reproduced verbatim. The missing close tag produces a non-zero delta at the first comparison, and the gate fires.

### Application Example

A harness returned FAIL against a correct fix. Instead of editing the fix, the harness was audited: the fixture did not carry the hazard under test, and the oracle scored legitimate truncation as damage. Both were repaired, the fixture set broadened from 2 to 6, and the rewritten harness then produced 9 real divergences and 0 false landings — evidence the original red result could never have yielded.

## Validation
- **Success Indicator**: On a failure, the record names which artifact was found at fault and what was checked to establish it. On a comparison gate, both sides' commands appear as identical literal strings.
- **Edge Cases**: Where the instrument genuinely cannot be inspected (opaque third-party tooling), fall back to PAT-097 and obtain a second source.

## Notes and Observations

The reviewer's corollary is the sharpest operational form of this pattern: **to test a verification gate, construct the corruption the narrower command cannot see, not the one it obviously catches.** Applied to the Sprint 108 case, that meant deleting a close tag rather than mangling the file — the quiet failure, not the loud one.

Also worth carrying: an asymmetric structural loss is invisible to a one-sided count, and a regex applied identically to both sides keeps the *delta* correct while leaving non-conforming items invisible to the count entirely. That is under-coverage, not mis-counting — a distinction that changes the remedy.
