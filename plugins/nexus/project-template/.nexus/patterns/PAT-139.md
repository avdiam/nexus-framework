# PAT-139: Dogfood the Mechanism on Its Own Change
*Version: 1.0.1 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: practice
- **Status**: active
- **Created**: 2026-08-19

## Problem

A new check, gate, census, or validation mechanism ships, and its first real exercise is left to whatever work happens to trigger it next. That may be sprints away, and it will be run by someone who did not design it — so a design flaw in the mechanism surfaces late, in unrelated work, where it is expensive to diagnose and easy to misattribute to the triggering change. Meanwhile the two changes best positioned to test it go untested: the change that *authored* the mechanism, and any later change that *repairs* it.

## Context

- **Use When**:
  - A change authors a new completeness check, census, audit step, gate, or validation mechanism — before calling the work done
  - A change amends or repairs an existing mechanism — this is the higher-value case
  - The authoring or amending change itself meets the mechanism's own trigger conditions
  - Reviewing a newly-shipped mechanism whose only evidence of correctness is that it was written carefully
- **Not When**:
  - The mechanism's trigger genuinely does not fire on its own authoring change (a single-file, single-section edit against a multi-file trigger)
  - The mechanism operates on runtime data the authoring change does not produce
  - Self-application would require the mechanism to exist before the step that writes it, with no way to run it afterwards — note the bootstrap case explicitly instead of forcing it
- **Prerequisites**: The mechanism's trigger conditions are stated explicitly enough to evaluate against the current change.

## Solution

Run a new mechanism against the very change that created it — and again against any later change that repairs it.

- **Authoring case**: after writing the mechanism, check whether the current change meets its own trigger. It usually does: a check built for multi-file changes is typically authored by a multi-file change. Run it. A clean result costs nothing; a dirty one exposes a design flaw before any other work depends on it.
- **Repair case** (higher value): whoever amends a mechanism holds its design in mind and therefore feels the *least* need to search for prior art. That is precisely the person most likely to author a duplicate authority instead of a citation. Run the mechanism against the amendment before writing it.

### Implementation

1. **State the mechanism's trigger conditions** as written, not as remembered.
2. **Evaluate the current change against them.** If it qualifies, the self-test is mandatory, not optional.
3. **Run the mechanism literally** — the actual command or procedure, not a mental approximation.
4. **Record the result either way.** A clean result is evidence the mechanism runs; a dirty result is a finding against the mechanism's design, not against the change.
5. **For the repair case, run it before writing the amendment** — the point is to discover prior art while the amendment is still editable.
6. **If the mechanism cannot fire on its own authoring change, say so and name why** (the bootstrap case). An unexamined skip is indistinguishable from a failed run.

## Rationale

- **Theoretical Basis**: A mechanism's first execution is its first real specification test — everything before it is authorial intent. The authoring and repairing changes are the two cheapest available test cases, because they are already in scope and already in the author's context. They are also the two most *diagnostic*: the authoring change reveals whether the trigger and procedure are executable as written, and the repair change reveals whether the mechanism finds prior art that its own author would skip searching for.
- **Empirical Evidence**: ISS-230 (Sprint 108) supplied both halves. Its Build authored a touchpoint-census check and then self-applied it to its own 3-file change, which met the check's own ≥2-file trigger; the result was clean, but a dirty result would have caught a design flaw before any other issue exercised it. More decisively, at Validate the F-2 fix to that same check was **rewritten by its own census**: running sub-check A over `.claude/skills/` before writing the amendment returned 11 external hits including `nexus-analyze/references/scope-investigation.md:261`, which already stated the governing rule verbatim. The amendment became a citation of the existing authority instead of a second, competing one. That was the first time the new check changed an outcome rather than confirming a clean one.
- **Design Decisions**: Both halves are held together because they share the trigger ("a mechanism was just written or modified") and differ only in which change is being tested. Filing them separately would surface the weaker (authoring) case more often than the stronger (repair) one.

## Anti-Patterns

- **Anti-Pattern 1**: Declaring a new check complete once its steps exist.
  - **Why Wrong**: Existence is not executability. Steps that read correctly can be unrunnable, ambiguous, or trigger on nothing.
  - **Example**: Shipping a census with a trigger table nobody has evaluated against a real change.
- **Anti-Pattern 2**: Amending a mechanism without running it against the amendment.
  - **Why Wrong**: The amender is the person most confident and therefore least likely to search — exactly the condition the mechanism exists to correct.
  - **Example**: Authoring a "choosing the class" rule from scratch when a sibling reference file already states it, creating two authorities that will drift.
- **Anti-Pattern 3**: Silently skipping the self-test because the mechanism "obviously" applies or "obviously" doesn't.
  - **Why Wrong**: An unconsidered self-test is indistinguishable from a skipped one. Record the trigger evaluation either way.

## Consequences
- **Benefits**: Free test case already in scope · design flaws surface at authoring time rather than sprints later in unrelated work · the repair case converts duplicated authorities into citations · produces a first execution record for a mechanism that would otherwise ship untested.
- **Tradeoffs**: The self-test can feel redundant to whoever just wrote the mechanism, which is the same bias the pattern targets · a clean result yields no new information beyond "it runs".
- **Risks**: A self-test on an unusually favourable change can produce false confidence — the mechanism ran, but not against a hard case. Pair with a genuinely adversarial application when the stakes justify it.

## Examples

### Before/After Comparison

**Without Pattern**: A completeness check ships. Its first genuine exercise happens two sprints later, on unrelated work, and the failure it produces is initially diagnosed as a defect in that work rather than in the check's own class-selection rule.

**With Pattern**: The check is run against its own authoring change (which meets its trigger) and later against its own repair. The repair run finds the rule already stated in a sibling file, and the amendment cites it rather than restating it — eliminating a drift surface that would otherwise have been created by the fix.

### Application Example

A repair was being written to a newly-shipped census check. Running the census over the skill file-class *before* writing the repair returned hits including a reference file that already stated the governing rule verbatim. The amendment was rewritten to restate the rule inline (the consuming path loads no external files) while citing the existing authority as its origin — one authority preserved, one duplication avoided, discovered by the mechanism under repair.

## Validation
- **Success Indicator**: The change record shows the mechanism's trigger evaluated against the change itself, the literal run, and the result — including "N/A, because {reason}" when the trigger legitimately does not fire.
- **Edge Cases**: The **bootstrap case** — a mechanism cannot be invoked at its own pre-execution call site during the step that writes it, because the mechanism does not exist yet. Run it retrospectively as a sanity pass and record that the call site was structurally unavailable, rather than claiming the normal path.

## Notes and Observations

The repair half is the non-obvious one and carries most of the value. The intuition it corrects is specific: *the person amending a mechanism holds its design in mind, and therefore feels the least need to check for prior art* — while being, structurally, the person most likely to duplicate an existing authority. The authoring half is closer to common sense and is included mainly because it is free.

The bootstrap case is a genuine hole in the workflow rather than in this pattern: an issue that authors a Build-phase check cannot invoke that check's own "before step execution" call site on its own change, because the section does not exist until partway through the step that writes it. Naming it here keeps it from being rediscovered as a defect.
