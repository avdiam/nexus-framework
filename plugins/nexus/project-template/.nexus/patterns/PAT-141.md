# PAT-141: Kill Condition For External Contracts
*Version: 1.0.0 | Date: 2026-08-20 | Sprint: 109*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-08-20

## Problem

An artifact that depends on an external capability — a tool, skill, library, API, platform feature, or sandbox path — records that dependency as a **citation**: a name, a path, a version string. A citation asserts that the capability exists. It cannot detect when the capability stops existing.

External capabilities disappear, get renamed, change contracts, or turn out never to have existed in the current environment at all. The citing artifact keeps reading as valid the entire time, because nothing about a name goes stale on its own. The failure surfaces only when someone finally tries to execute the artifact — often several cycles later, after plans, schedules, and success criteria have hardened around it.

The exposure is worst for artifacts that **wait**: a backlog issue, a parked design, a documented guide. The longer an artifact sits, the wider its drift window, and the less likely anyone re-derives a premise that reads as settled.

## Context

- **Use When**:
  - Authoring an issue, plan, spec, or success criterion whose completion depends on an external tool, skill, library, API, or platform capability
  - Activating or scheduling a backlog artifact that names an external capability — before committing a sprint to it
  - Recording a dependency as a bare path, tool name, or version string, with no statement of what would make it false
  - Reviewing an artifact that has waited several cycles and rests on something outside the project's own version control
- **Not When**:
  - The dependency lives inside the project's own repository, where a change is visible in the same diff and the citation cannot silently rot
  - The dependency is genuinely ephemeral and the artifact is consumed within the same session
- **Prerequisites**: the condition must be checkable by inspection — a path that can be tested for existence, a tool that can be probed, a version that can be compared

## Solution

**When an artifact asserts an external capability contract, attach a verifiable kill condition alongside the citation.**

A kill condition is a concrete, inspectable statement of what would make the dependency false — *"this is void if X is absent from Y"* — positioned where a routine pass will actually read it.

Four requirements:

1. **Executable by inspection, not prose.** "Assumes tool T is available" is a caveat. "Void if `which T` returns nothing" is a condition. Only the second can be checked without a human deciding to care.
2. **Positioned on a path something already walks.** A condition nobody reads is a citation with extra words. Host it on a pass that already opens the artifact on its own clock — the grooming step, the activation gate, the periodic scan.
3. **Re-checked at activation, not only at authoring.** Validity is re-derived, never inherited. The environment changes independently of the artifact.
4. **Owned by the author, not the reader.** The author knows what the artifact assumed; the future reader does not, and may never reach the step where the assumption is tested.

Scope the condition to the *contract*, not the *name*. A capability that still exists under a different name has not been killed; one that exists under the same name with an incompatible contract has.

### Implementation

1. Identify every external capability the artifact's success depends on.
2. For each, write the falsifying check as a command or an inspectable assertion.
3. State the consequence explicitly: what part of the artifact becomes void — a success criterion, a plan step, or the whole thing.
4. Place it where a routine pass reads it.
5. On activation, run the check *before* accepting the artifact's scope — treat the citation as a hypothesis.

## Rationale

- **Theoretical Basis**: A citation is an assertion with no expiry. A kill condition is a falsifiable claim with an owner and a clock. Since the environment changes independently of the artifact, validity has to be re-derived rather than inherited — and re-derivation only happens reliably when someone wrote down what to re-derive.
- **Empirical Evidence**: Sprint 109 (NEXUS) produced the same story twice, one sprint apart, with opposite outcomes. `SEED-031` carried a plant-time kill condition; when the Workflow tool vanished from the harness, the condition fired correctly at the next routine grooming pass — the first prune condition in the corpus to fire on an *external-environment* change rather than on project action. `ISS-089`, the scheduled distribution gateway, cited a `web-artifacts-builder` skill at six places including two success criteria and an implementation-plan step, recording a `/mnt/skills/examples/…` sandbox path meaningless in the current environment. The skill was verified absent; four of ten success criteria rested on it. Nothing had detected this, and it surfaced only because a comprehensive-tier deep validation happened to land one sprint before that issue opened. One was caught by mechanism, the other by coincidence — and the coincidence had an unknown number of sprints of exposure behind it.
- **Design Decisions**: The condition is author-side deliberately. A reader-side premise check (PAT-119) fires at execution, which is exactly the moment a long-waiting artifact has *not* yet reached — so it structurally cannot protect a backlog.

## Anti-Patterns

- **Anti-Pattern 1 — The prose caveat**
  - **Why Wrong**: A note reading "depends on tool T being installed" carries no check and no consequence. It reassures the author that the risk was handled while leaving the artifact exactly as undetectable as before.
  - **Example**: Recording an external skill's sandbox path in a Notes section and treating that as documentation of the dependency.

- **Anti-Pattern 2 — Condition with no host**
  - **Why Wrong**: A perfectly written kill condition placed in a file nothing routinely opens fires never. The condition's value comes from its position as much as its content.

- **Anti-Pattern 3 — Verifying once at authoring**
  - **Why Wrong**: The check confirms the state on the day it was written, which is the day the risk is lowest. The whole exposure lives in the interval afterwards.

- **Anti-Pattern 4 — Killing on the name**
  - **Why Wrong**: A renamed-but-equivalent capability trips a name-based condition and wastes a cycle; a same-named capability with a changed contract passes it and preserves the failure. Bind the condition to the contract.

## Relationships

- **Requires**: none
- **Enhances**: PAT-119 (execution-time premise verification — this is its authoring-time counterpart), PAT-124 (verify a named target exists and is live), PAT-136 (host the condition on a mechanism already positioned at the right frequency)
- **Conflicts**: none
- **Alternatives**: PAT-119 alone, accepted knowingly for artifacts consumed shortly after authoring

## Consequences

- **Benefits**: Converts a silently rotting dependency into a check any routine pass can run; scales to artifacts that wait indefinitely; makes the blast radius explicit at authoring, when it is cheapest to scope.
- **Tradeoffs**: A small authoring cost on every externally-dependent artifact, and conditions themselves need occasional maintenance as environments evolve.
- **Risks**: Over-application to internal dependencies adds ceremony without protection; a poorly scoped condition produces false kills that erode trust in the mechanism.

## Examples

### Before/After Comparison

**Without Pattern**: An issue's success criteria depend on an external skill. The dependency is recorded as a path in a Notes section. The skill is not present in the current environment. The issue is scheduled as a sprint gateway, and the gap surfaces only because an unrelated deep-validation pass happens to run one sprint earlier.

**With Pattern**: The same issue carries, next to the citation, *"Void if `web-artifacts-builder` is absent from `.claude/skills/` or `~/.claude/skills/` — SC-03, SC-04, SC-07, SC-09 and plan step 5 all become unmeetable."* Any pass that opens the issue can run the check, and the issue announces its own invalidity instead of waiting to be discovered.

### Application Example

The contrast within a single sprint is the pattern's best teaching case: a seed with a kill condition fired on an external-environment change with no one looking for it, while an issue with only a citation went undetected for an unknown number of sprints and was rescued by luck. Same dependency class, same project, same month — the only difference was whether the author wrote down what would make it false.

## Validation

- **Success Indicator**: For every external capability the artifact names, there is a corresponding condition stating a runnable check and the specific consequence of its firing.
- **Edge Cases**: Capabilities with no inspectable surface (a behavioral guarantee, a rate limit) — fall back to a dated re-verification requirement with a named owner, and record that a hard check was unavailable.

## Notes and Observations

The generalisation worth carrying beyond this project: any specification, plan, or backlog item that names something outside its own version control is making a claim it has no mechanism to retract. The cost of the mechanism is one line at authoring; the cost of its absence is whatever was built on the dead dependency before anyone tried to run it.

Note also the failure's shape — it is not that the dependency was undocumented. It was documented six times over. Documentation of a dependency and detection of its death are different mechanisms, and the presence of the first reliably creates the impression that the second exists.
