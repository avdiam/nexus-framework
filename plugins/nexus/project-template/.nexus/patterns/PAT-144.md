# PAT-144: Separate a Rule's Signal From Its Diagnosis
*Version: 1.0.0 | Date: 2026-08-25 | Sprint: 110*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-08-25

## Problem

Rules are routinely authored in the form **"if X then STOP, because X means Y"** — a mechanical trigger bundled with a stated diagnosis. The bundling is what makes the rule persuasive: the threshold sounds principled because it comes with a cause.

It fails silently the moment X fires for a reason other than Y. The operator sees the trigger, sees that the stated diagnosis does not fit the situation in front of them, and overrides. And the override is **locally correct every single time** — so nothing ever marks it as drift. There is no failing run, no complaint, no accumulating error. The rule decays into ceremony while continuing to read as enforcement, and the only record is a series of individually justified exceptions that nobody aggregates.

## Context

- **Use When**:
  - Authoring or reviewing any threshold rule that names a cause — escalation limits, lint severities, alert runbooks, circuit breakers, code-review size caps, save-mode triggers
  - A rule has been overridden more than once and each override was defensible on its own terms
  - Writing a STOP condition that another person or agent will execute without the author present
  - A gate's stated rationale and its actual firing condition are drifting apart
- **Not When**:
  - The trigger has exactly one possible cause, so signal and diagnosis are genuinely the same claim
  - The rule is advisory with no stop semantics and no override cost
  - The cost of a false stop is trivially low, making a fenced proceed-path more machinery than the situation warrants
- **Prerequisites**: The trigger is mechanical (measurable without judgment) and its possible causes can be enumerated.

## Solution

Author the trigger and the diagnosis as **separate elements**, with a classification step between them.

1. **The signal** stays mechanical and unchanged — the measurement that fires.
2. **A classification step** asks which cause produced this firing, from an enumerated list.
3. **Each cause gets its own route.** The rule keeps its hard stop for the cause it was written for. Every other cause gets a bounded proceed-path — a **fence**, with its own explicit conditions, not an exemption.

A fence differs from an exemption in that it constrains: it names what may be done under it, what must be recorded, and what invalidates it. An exemption only names who may skip.

When an existing bundled rule fires and its diagnosis does not fit, the correct move is neither to obey it nor to override it — it is to **amend it at a gate**: split the signal from the diagnosis, enumerate the causes found, and give the new cause a fence. Record the amendment. An override leaves the rule intact and the drift unrecorded; an amendment is the only action that improves it.

### Implementation

1. Write the trigger as a bare measurement, with no "because" clause.
2. Enumerate the causes that can produce it — including the ones that are not the reason the rule exists.
3. For each cause: STOP, or a fence with stated conditions and a recording requirement.
4. Make the classification step a required output, so which branch was taken is visible in the record.
5. When a new cause appears in practice, add a branch rather than logging an override.

## Rationale

- **Theoretical Basis**: A trigger *measures*; a diagnosis *explains*. Bundling them makes the measurement inherit the explanation's failure rate — the rule is now only as correct as the causal claim attached to it, but it is enforced with the confidence of the measurement. The failure is unobservable by construction: because every individual override is right, the aggregate drift produces no error signal, and a rule overridden every time it fires looks identical to a rule that is working.
- **Empirical Evidence**: ISS-089 (Sprint 110) both broke a rule of this shape and validated its amended form. A 40%-replacement escalation rule read "if a target's replacement volume exceeds 40%, STOP — because that means the detector class list is wrong." On the first long target it measured ~45%, and the stated diagnosis was **falsified at the gate**: all eleven detectors fired and every finding mapped to an existing class. The rule was split into *detector-failure* (STOP, the cause it was written for) versus *density* (proceed under a four-rule fence). It then fired **twice in one batch wave and produced opposite, correct routes** — one target classified as density and folded in under the fence, the other classified as a premise collision and stopped for hand-restructuring. Applying one uniform rule to both would have either wasted a worker run or attempted a 544-line restructure at the wrong moment. Independently, the same sprint recorded a save-mode trigger overridden twice on defensible grounds, each override logged as a miscalibration note that no mechanism ever aggregated — the pure form of the silent-drift failure.
- **Design Decisions**: The fence, rather than an exemption, is the load-bearing choice. An exemption removes the rule's grip for a class of cases; a fence keeps a grip of a different shape. That is what allows the STOP branch to stay sharp — it is no longer being asked to cover cases it was never written for.

## Anti-Patterns

- **Anti-Pattern 1**: Writing "if X then STOP, because X means Y" as one atomic rule.
  - **Why Wrong**: The measurement inherits the causal claim's failure rate, and the failure is invisible because each override is individually correct.
  - **Example**: "Replacement volume >40% means the class list is wrong" — fired at 45% on a target where the class list was demonstrably complete.
- **Anti-Pattern 2**: Overriding a rule whose diagnosis does not fit, and logging the override.
  - **Why Wrong**: The log records the exception, not the defect. The rule is unchanged and will misfire identically next time, and the log grows into evidence nobody reads.
  - **Example**: The same trigger overridden repeatedly across one sprint, each time with a fresh note observing that it is miscalibrated.
- **Anti-Pattern 3**: Obeying a rule whose diagnosis has been falsified in front of you.
  - **Why Wrong**: It converts a known-wrong causal claim into an action, at the cost the rule's own rationale does not justify.
  - **Example**: Stopping and re-deriving a detector list that has just been shown to be complete.
- **Anti-Pattern 4**: Replacing the bundled rule with a threshold tweak.
  - **Why Wrong**: Moving 40% to 55% changes when the wrong diagnosis is asserted, not whether. The defect is structural, not numeric.

## Consequences
- **Benefits**: Keeps a STOP condition sharp for the case it was written for · gives every other cause a bounded, recorded route instead of an override · makes rule drift observable, because a new cause becomes a new branch rather than a note.
- **Tradeoffs**: More authoring work up front, and an enumeration that is never complete on the first pass · a classification step adds a decision where a bare threshold had none.
- **Risks**: A fence can be widened until it is an exemption in all but name. Its conditions and recording requirement are what make it a fence — drop those and the rule has simply been weakened.

## Examples

### Before/After Comparison

**Without Pattern**: "Replacement volume above 40% means the class list is wrong — STOP and re-derive it." The rule fires on a target whose class list is provably complete. The operator overrides, correctly, and notes the exception. Six targets later the rule fires again on a genuinely broken class list and is overridden by habit.

**With Pattern**: The trigger stays at 40%. A classification step asks *why* it fired, from an enumerated list. `detector-failure` → STOP and re-derive. `density` → proceed under a four-rule fence with the fence conditions recorded. Both branches then fire in a single wave and produce opposite, correct routes.

### Application Example

A rule fired at ~45% and its stated diagnosis was tested rather than assumed: all eleven detectors had fired and every finding mapped to an existing class, so the diagnosis was false while the measurement was true. The rule was amended at the gate into signal + classification + two routes, and the amendment was recorded as a decision rather than as an override.

## Validation
- **Success Indicator**: The rule's text contains a bare measurement, an enumerated cause list, and one route per cause — and its execution record names which cause was classified, not merely that the rule fired.
- **Edge Cases**: A trigger whose causes genuinely cannot be enumerated in advance still benefits from the split — the classification step becomes "name the cause and route it", with an explicit fallback branch for unrecognised causes that requires a gate.

## Notes and Observations

The diagnostic tell is a rule that has been overridden more than once with a defensible reason each time. That is not a discipline problem and not an inconvenience — it is the signature of a bundled rule whose diagnosis does not cover its trigger's causes. Count the overrides; the count is the only aggregate signal this failure mode ever produces.
