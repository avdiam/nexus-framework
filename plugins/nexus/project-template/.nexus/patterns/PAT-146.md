# PAT-146: Constrain Figure Production Path
*Version: 1.0.0 | Date: 2026-08-27 | Sprint: 111*

## Metadata
- **Type**: principle
- **Status**: active
- **Created**: 2026-08-27

## Problem
A contract that mandates a reported figure as proof of some property — consumption, coverage, verification — constrains WHAT must be reported but not HOW that figure is produced. Authors then satisfy the letter of the contract without the substance: the same variable printed twice, two counters incremented in lockstep, or a denominator asserted as if measured. The contract reads as followed in every deployment while its own central check — a comparison between two figures — can never structurally fire. Nine of fifteen deployments of one such contract shipped this way in the same sprint that wrote the contract, and each author believed they were complying.

## Context
- **Use When**: Authoring or reviewing a verification/audit contract that requires a "did this actually consume its input" figure (a bound/candidates pair, a coverage count, a hit-count against a denominator); auditing an existing verification mechanism whose reported proof figure never seems to move, or always agrees exactly with the figure it is supposed to be proof against; designing any check whose pass condition depends on comparing two counted quantities.
- **Not When**: The figure IS the denominator itself, with nothing to compare it against. Probing whether an existing, already-produced metric can respond to real change — that is detection after the fact (PAT-140), not a constraint on authoring. A one-off, hand-run report with no repeated or automated production path, where a human reads the number directly rather than trusting a pass/fail verdict.
- **Prerequisites**: A contract or spec that already mandates SOME figure be reported as evidence — this pattern adds a constraint on that figure's production, it does not invent the reporting requirement.

## Solution
When a contract mandates a proof figure, add a production-path constraint alongside the reporting requirement: the proof counter must be INDEPENDENTLY DERIVED — never assigned from the thing it is meant to prove, never a second variable holding the same value as another reported figure — and it must be incremented AFTER the specific step that can fail or be skipped, never alongside or before it. If two figures are meant to be compared, verify at authoring time that they are counted over the same population, using different code paths, so agreement is possible evidence rather than a certainty by construction.

### Implementation
1. For any mandated proof figure, ask: "if the thing this figure proves never happened, could the figure still print the same value?" If yes, the production path is unconstrained.
2. Require the counter to increment strictly after the fallible step (the parse, the file open, the match) — not at loop entry, not alongside a sibling counter.
3. When two figures are compared (e.g. `bound` vs `candidates`), derive them from genuinely different operations over the same corpus, never from the same loop counter read twice.
4. State the constraint IN the contract text itself, not only in a reviewer's checklist — the constraint must travel with the mandate, or every new deployment re-discovers the gap independently.

### Quick Reference
- Reported figure that can't move independently of its counterpart → unconstrained production, contract is satisfiable by construction.
- Reported figure incremented only after a step that can fail → constrained production, the contract's comparison is load-bearing.

## Rationale
A correct rule that constrains only WHAT must be reported, not HOW it is produced, is defeated by the cheapest available form of compliance: copying a value or incrementing two counters together. This is not a failure of the rule's content — the rule can be entirely correct — but a failure of its ENFORCEABILITY, because nothing in it distinguishes a genuine consumption proof from a decorative one. Constraining the production path moves the check's substance into the authoring step itself, rather than leaving every future deployment to be independently and adversarially re-audited to discover the same gap.
- **Theoretical Basis**: A contract is only as strong as its least-constrained satisfaction path; a mandate on output content alone leaves the production path free, and cheap compliance fills that space by default.
- **Empirical Evidence**: Nine of fifteen deployments of one project's verification contract (VC-2) satisfied its letter with an inequality unsatisfiable by construction — seven printed one variable for both figures, two shared a constant incremented in lockstep — discovered only when an independent review executed each predicate against a deliberately broken input. A second, independent instance of the same shape existed one contract-generation earlier in a sibling issue.
- **Design Decisions**: The remedy targets the PRODUCTION PATH of the figure, not the figure's presence or its comparison logic — the comparison logic in both source instances was already correct; only the inputs feeding it were unconstrained.

## Anti-Patterns
- **Anti-Pattern 1**: Two counters incremented in the same loop body, one intended as the denominator and one as the numerator, with no guard between them that can fail.
  - **Why Wrong**: If nothing between the two increments can fail or skip, they are mathematically guaranteed to stay in lockstep — the pair can never disagree, so a contract requiring them to be compared certifies nothing.
  - **Example**: `candidates += 1; bound += 1` in the same unconditional loop body, with the fallible parse happening after both.
- **Anti-Pattern 2**: Crediting `bound` (or any consumption-proof counter) before the operation that could fail.
  - **Why Wrong**: A counter incremented before its fallible step measures attempts, not successes — a predicate that never actually reads its input can still report a full count.
  - **Example**: Incrementing a "files read" counter at loop entry, before the file is opened, so an unreadable file is still counted as read.

## Relationships
- **Requires**: []
- **Enhances**: A verification contract that already mandates SOME reported figure (this pattern strengthens the mandate, it does not create the reporting requirement)
- **Conflicts**: []
- **Alternatives**: PAT-140 (probe-metric-responsiveness) — detects an already-produced insensitive figure by testing whether it moves under a known change; this pattern prevents the figure from being insensitive in the first place, at authoring time. The two are complementary: PAT-140 for auditing figures you did not author or cannot re-derive; this pattern for authoring or reviewing a contract before it ships.

## Consequences
- **Benefits**: Moves the check's substance to authoring time, where one fix closes the gap for every future deployment, rather than requiring each deployment to be independently and adversarially rediscovered.
- **Tradeoffs**: Requires the contract author to specify a production-path constraint in addition to a reporting requirement — more up-front specification work than mandating a bare figure.
- **Risks**: A constraint stated only in prose ("must be independently derived") without a checkable test can itself be satisfied by construction — pair with an executed sabotage arm (deliberately break the fallible step and confirm the figure changes) rather than trusting the stated constraint alone.

## Examples

### Before/After Comparison
**Without Pattern**: A contract states "report `bound` and `candidates` for every verdict." An author writes `cand=1; bound=1` as literals at the top of the predicate and never touches either variable again — the verdict is `FILLED: 0 findings / 1 bound / 1 candidates` on the live tree, on a renamed consumer, and on a completely empty input file, identically.
**With Pattern**: The contract additionally states "`bound` must be independently derived — never assigned from `candidates`, never a duplicate of another reported number — and incremented only after the guard that can fail." The same predicate, rewritten to this constraint, now reports different verdicts across the three cases above because the increment site actually depends on the guard succeeding.

### Application Example
ISS-240's Evaluation phase (Sprint 111) re-measured a "9 of 15 edges non-conforming" finding and found the remedy could not be a uniform fix: two edges' denominators were schema-fixed with a separate positive guard already proving consumption, so manufacturing an independent counter there would have corrupted a correct predicate. The other six were repaired by moving the `bound` increment to after their fallible step, and every repair was validated with an executed sabotage arm before being trusted.

## Notes and Observations
Distinguished from PAT-121's "incomplete manual enumeration → executable predicate" remedy-form row and from PAT-140's probe-metric-responsiveness at the 4Q gate before creation: PAT-121 is about ensuring an enumeration's COVERAGE is complete; this pattern is about ensuring a reported figure's PRODUCTION cannot be satisfied by copying or lockstep incrementing. PAT-140 detects an already-produced insensitive metric after the fact; this pattern prevents one at authoring time. All three can apply to the same verification-contract work at different points — authoring (this pattern), coverage (PAT-121/PAT-142), and post-hoc audit (PAT-140/PAT-138).
